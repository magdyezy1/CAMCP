# Product, website and workflow expansion audit

Reviewed source: CAMCP Work-here c615cb7. Review/proposal only. No production edits.
This supplement maps existing behavior to an implementable product direction. The
[master blueprint](../PRODUCT-BLUEPRINT-2026-10-01.md) records the separate local synthetic rendering observations.
Layout specifications here are proposals, not claims that redesigned pages already exist.

## 1. Product direction

AMCP should be a connected advertising workspace with a shared object model across the website and MCP:
workspace -> authorized account -> client/profile -> plan or report -> review/run -> receipt/evidence.
The website is the human planning, review and recovery surface; MCP is another way to operate the same saved
objects. Neither should invent a second campaign engine, permissions model, report definition or approval process.

The largest useful expansion is exposing capabilities already present in the backend through clear human workflows.
Examples: whole-plan approval/run, cloning, safe step amendment, accepting a verified observed state, searchable
capability contracts, asynchronous upload progress, and support bundles. These are interface work, not new APIs.
New persistent monitoring and incident-delivery capabilities should be identified separately from existing pacing
and anomaly analysis.

## 4. Proposed information architecture

Keep seven task-oriented primary groups. These are proposed routes/views, not routes that already exist.

| Primary group | Child views | Existing destinations reused |
|---|---|---|
| Home | Work needing attention; recent plans/reports; readiness | `/dashboard` |
| Campaigns | Plans; New plan; Plan detail; optional later account inventory | `/campaigns` and existing campaign MCP objects |
| Creative | Asset library; Prepare & push; Ad previews | `/media` components |
| Reporting | Campaign reports; Report builder/results; Evidence & analysis; Schedules | `/reporting-overview`, `/reports`, delivery dialog |
| Clients & templates | Profiles; campaign/report templates; defaults | `/profiles`, report-template library |
| Connections | Platforms & accounts; AI tools; account detail | `/connections`, `/connectors`, manage dialog |
| Operations | Needs attention; jobs/recovery; activity; capability reference | `/activity`, existing health, jobs, receipts and contracts |

Workspace management stays in a lower navigation group: Team, Account policies, Retention, and Deployment setup
(instance owner only). Personal profile/security stays under the avatar. Legal links stay in the footer.
The workspace selector is persistent and explicitly names the active workspace; user identity and workspace role
are distinguishable. A client filter is a saved organizational filter, never a new grant of account access.

Detail views should have stable URLs containing object IDs so MCP can link a user directly to a plan, review,
snapshot, schedule or failed job. Navigation should retain only permitted state within the current identity.
The command palette should index the same role-filtered destinations and objects, not a separate stale route list.

## 8. Capability expansion boundaries and useful measures

- Extend channel/objective recipes only when required business inputs, native contracts, ownership, money units,
  parent status, creative requirements and read-back evidence are qualified. Current recipes are bounded; a single
  universal form must not silently substitute one provider's semantics for another's.
- A live account explorer would be a new website view over existing authorized native inventory; keep it visibly
  distinct from AMCP saved plans. Search and viewing do not authorize mutations.
- Bulk edit previews should group existing reviewed families and show per-account effects; do not introduce raw
  batch passthrough or treat an aggregate confirmation as approval of changed later inputs.
- Personal-data controls, plan approval and cap acknowledgements already have policies. Exposing them in UI should
  implement those policies faithfully, not reopen settled owner decisions or enable capabilities by default.
- Alerting should begin with in-product read-only insights; external messages require explicit destination and
  authorization. No automatic budget control is proposed.

Measure each improvement against a representative synthetic journey: time to first correct readiness result;
number of required round trips; ability to explain a review's money/status effects; time to diagnose a failed job;
successful return after refresh/navigation; report definition-versus-snapshot comprehension; schedule timezone
accuracy; keyboard task completion; and provider/API request count. Qualify visual changes with real rendering
and keep synthetic, CI/container and live-provider results distinct.
