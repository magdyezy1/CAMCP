# AMCP comprehensive review and improvement plan

**Review date:** 1 October 2026, Africa/Cairo. **Repository:** `magdyezy1/CAMCP`.
**Sole working branch:** `Work-here`. **Reviewed commit:** `c615cb7`.
**Status at assessment:** review first. The owner subsequently authorized implementation; see the
[implementation record](IMPLEMENTATION-2026-10-01.md) for current repairs, delivered product scope and qualification.
The findings and measurements below preserve the baseline and are not a statement of the current implementation.

**Start with the [full product blueprint](PRODUCT-BLUEPRINT-2026-10-01.md) for the expanded product direction,
workflows, contract integration, website layouts and capability roadmap.** This document is the engineering
assessment and evidence base. The blueprint and its three specifications complete the broader product review.

## 1. Executive assessment

AMCP already has substantial engineering behind it: reviewed advertising writes, account boundaries, durable
duplicate-submission protection, native reporting, resumable media, and a large synthetic test suite. A wholesale
rewrite would discard useful safeguards and is not justified by this review.

The highest-value next work is to make its existing promises hold under failure and concurrency. Several protections
work when a request begins but do not remain effective while it waits. The report pipeline also has arithmetic and
empty-result defects that can undermine otherwise useful reporting. In the browser, private state and delayed
responses can outlive the user or workspace that created them.

**Fix first:**

1. Personal-data redaction on rejected requests and provider errors.
2. Workspace pause and personal-data authorization immediately before dispatch, including later media chunks.
3. Browser state isolation across logout, expiry, and workspace changes.
4. X report boundary-hour double counting and valid custom metrics failing on empty or sparse results.
5. Report pagination, stale page responses, and media completion after removal.

**Then improve the product:** show a readable change summary before approval; preserve useful backend recovery
guidance in the website; make reporting definitions and evidence easier to understand; add repeatable browser
qualification; and build a concise account-readiness and operations experience around capabilities that already
exist. Full Arabic localization, pacing alerts, and a broader campaign planner are useful later investments.

**Do not equate coverage with live acceptance.** The ledger contains 3,247 actions, including 1,712 native reads,
800 reviewed writes, and 502 blocked writes. Its live-qualification fields remain `unverified`. Local tests passing
does not establish production OAuth, provider permission, account eligibility, or successful live execution.

This review identifies **18 new finding groups** in the register below. Eleven groups were reproduced with synthetic
tests or probes; the others are source-traced usability/operations issues, a dependency-advisory finding, and stale
documentation. Additional investigations and product opportunities are deliberately listed separately.

## 2. Scope, method, and limits

The review covers every major area in the engineering brief: code organization, responsiveness, resilience,
website design and workflow, MCP usability, platform contracts, reporting, media, security calibration, privacy,
testing, documentation, deployment readiness, and possible new capabilities.

Methods:

- Read the project overview, architecture, threat model, findings, roadmap, progress, platform and calibration
  records, then inspect the relevant implementation and tests across the main trust and data boundaries.
- Inventory all 348 core/server TypeScript modules and the shipped browser assets; inspect high-risk paths in depth.
- Install the pinned dependencies and run the complete check pipeline in a fresh sanitized copy of the unchanged
  branch, with synthetic fixtures and an empty generated historical-sample file.
- Reproduce new failures with in-memory databases, fake provider responses, deterministic asynchronous waits, and
  the actual browser scripts in a VM DOM adapter.
- Measure local construction, metadata response sizes, and static asset weight; audit production dependencies and
  read the corresponding public advisories.

This is a comprehensive review by system area, **not a line-by-line certification of every provider module**.
No advertising provider account, production database, credential file, OAuth grant, Railway setting, or DNS setting
was inspected or changed. Public GitHub/npm reads were used for repository and dependency verification. The later
product expansion pass rendered five entry/workspace views in a local synthetic browser fixture; its limited visual
observations are in the product blueprint. No screen-reader session, production load test or live-provider acceptance
test was performed. Historical accessibility and provider records are context, not fresh verification.

When the owner requested the review first, the tentative reporting edit was saved as an ignored proposal patch and
restored. New failing regression probes were moved out of the tracked test suite into local review evidence.
Only review documentation and its index are changed in the working tree.

Evidence labels used below:

| Label | Meaning |
|---|---|
| Reproduced | The intended behavior failed against this branch using a synthetic test or focused probe |
| Traced | Source establishes the behavior; a targeted runtime/browser regression is still needed |
| Advisory verified | Installed dependency matches a published advisory; application exploitability is not established |
| Investigation | A plausible gap requiring additional measurement, contract evidence, or a regression |
| Opportunity | A proposed product or engineering improvement, not an assertion of a defect |

Priority describes implementation order: **P0** security, privacy, money, or report correctness; **P1** operational
reliability; **P2** enabling architecture, test, and workflow work; **P3** wider UX, performance, and new capabilities.
It is not a CVSS severity score. Effort is relative: **S** a narrow change, **M** several interacting modules,
**L** a larger product or architectural project. Estimates require planning; no delivery dates are implied.

## 4. Findings that should drive the first batches

Source line references below are against `c615cb7`. All findings remain open.

### F-118 — Personal-data error redaction leaves identifying object keys

**P0 · high · reproduced · S–M.** `src/personal-data.ts:426` recursively scrubs values but preserves object keys.
A provider error containing a person's hash or email as an `invalid_entry_samples` key survives in the returned
error. The error path also reaches the audit writer through `src/transport.ts:698`, `src/write-review.ts:870`, and
`src/service.ts:350`.

**Improve:** project safe error fields for personal-data operations, retaining useful codes and counts while
excluding people in both keys and values. Merely adding another regex is weaker than a narrow projection.
**Prove:** rejected uploads with identifiers in keys, nested arrays, text, and values must leave none in returned
errors, documents, audit, idempotency records, or jobs. Do not lose diagnostic counts through redacted-key collisions.

### F-119 — Refused inline personal-data payloads can persist raw phones

**P0 · high · reproduced · S–M.** `src/personal-data.ts:407–417` uses hash/email redaction on personal-action
arguments. An incorrectly supplied inline PHONE payload is refused without provider egress, but its phone remains
in the stored error-audit input. Refusing the action does not make storing its input safe.

**Improve:** withhold personal-action payloads from audit by default; retain only allowlisted action/account metadata
and safe aggregate diagnostics. Apply this before validation failures can be logged.
**Prove:** malformed direct and wrapped arguments, raw phones, hashes, emails, empty/oversized inputs, and permission
failures never retain people. A valid upload still produces an informative aggregate review.

### F-120 — Pausing writes does not stop requests that are still waiting to be sent

**P0 · high · reproduced · M.** `src/write-review.ts:681` checks pause before asynchronous state/credential work.
Dispatch authority at `:187` does not recheck it. Two tests pause during state retrieval and transport admission;
both still send one mutation. Media has the same problem: initial pause at `src/media-upload.ts:1180`, but later
send/Google/LinkedIn authority hooks at `:1342`, `:1448`, and `:1596` omit it. A Google multipart test pauses after
the first confirmed chunk; the second chunk is still sent.

**Improve:** check the current workspace pause immediately before each mutation/chunk/finalization dispatch.
**Prove:** zero subsequent submissions after a pause, while preserving IDs, offsets, sessions, receipts, and uncertain
outcome protection. Reads and verification should remain usable. A pause cannot undo a request already sent.
This extends F-24; the original startup-only pause defect was fixed, but these asynchronous gaps remain.

### F-121 — Disabling personal-data uploads has a dispatch-admission gap

**P0 · high · reproduced · S.** `src/write-review.ts:787` checks the per-account switch before transport admission.
Disabling the switch during the transport wait still allows one upload.

**Improve:** revalidate personal-data authority at the final mutation boundary, using the exact current actor,
account, direction, and reviewed batch. Preserve operator removals under the existing account controls.
**Prove:** a disabled addition sends no people; operator removal authorization and received-receipt retention keep
their intended behavior. The current account switch applies to both directions; this proposal does not bypass it.

### F-122 — Private browser state survives logout, expiry, and workspace changes

**P0 · high · reproduced · M.** Logout (`web/app.js:623`), 401 handling (`:103`), and workspace switching
(`web/account-security.js:195`) do not clear the complete private UI state. Reporting retains its previous
configuration through `web/reporting-overview.js:157`. Synthetic tests retain prior report configuration, selected
reports/destinations, connector lists, and account selections across all three transitions.

**Improve:** centralize identity-scoped state and invalidate pending responses when user or workspace changes.
**Prove:** the next identity sees no prior client's state and late responses cannot repopulate it. A refresh of the
same identity should preserve legitimate unsaved work. This is a browser disclosure/stale-state defect, not evidence
that the backend's tenant filters can be bypassed.

### F-123 — Old page responses can overwrite a newer route

**P1 · medium · reproduced · M.** Activity rendering at `web/app.js:421–428` and error handling at `:524–595` do
not bind commits to the navigation that started them. Tests show old activity appended to Connections, old errors
replacing a newer page, and a first-visit response arriving after leaving and returning to the same path.
Related patterns exist at `web/workspace.js:51–58` and `web/reporting-overview.js:154–163`.

**Improve:** navigation and identity generations, with guards before committing data, errors, polling, and focus.
**Prove:** delayed success/failure, back/forward, same-path return, and logout cannot corrupt the current view.
Cancellation of UI work must never imply that an already submitted mutation is safe to resend.

### F-124 — Valid native custom metrics fail on empty or sparse successful reports

**P0 · medium · reproduced · S.** Configuration accepts valid native dependencies, but work-time validation at
`src/reporting-overview.ts:650–660` uses only native fields observed in returned rows, plus a failed-source exception.
A successful empty source with a native custom formula fails the job. So does a successful source where the requested
native field is absent from every row.

**Improve:** preserve the valid dependency contract through execution. Keep missing values `null`; do not invent zero
or pretend a metric was observed. **Prove:** empty reports complete with the existing no-data explanation, sparse rows
preserve nulls, invalid formulas still fail, and empty exports remain blocked as currently intended.

### F-125 — X calendar reports double-count shared boundary hours

**P0 · high · reproduced · M.** `src/x-campaign-report.ts:19–22` widens each period to whole UTC hours.
`src/report-periods.ts:55` collects calendar periods independently, and the adapter sums all returned buckets.
For two adjacent days in `Asia/Kolkata`, the synthetic fixture returns **25 + 25 = 50** impressions/spend units,
while the same combined range returns **49**; all results report `complete: true`.

**Improve:** use one documented ownership rule for boundary hours across total, daily, weekly, and monthly reporting.
The existing workflow uses midpoint ownership; the Overview adapter needs consistent semantics and checkpoint
versioning. Clarify that hourly provider granularity approximates sub-hour local boundaries.
**Prove:** additive metrics reconcile across adjacent periods, including half-hour/quarter-hour offsets and DST;
non-additive reach/ratios are not summed. This exposes a remaining path beneath F-114's broader fixed claim.

### F-126 — Removing a media source during inspection can resurrect an unusable record

**P1 · medium · reproduced · S–M.** `src/media-sources.ts:155–177` carries a source record across asynchronous
inspection, and `finish()` at `:285–288` writes it without checking that removal at `:379–384` occurred.
A deferred-inspection probe removes the source, then releases inspection: completion reports `complete`, the source
reappears in the list, but opening its bytes fails with `REVIEW_EXPIRED`.

**Improve:** fence finalization on current ownership, existence, and the expected source/manifest generation.
Removal must win. **Prove:** remove/disconnect/revoke during inspection does not resurrect records or lose cleanup;
ordinary completion and retries remain idempotent.

### F-127 — Report pagination advances before success and permits overlapping requests

**P1 · medium · reproduced · S.** At `web/reporting-overview.js:326–333`, handlers change the page before the fetch
succeeds. A failed Next leaves internal page 1 while displaying page 0; rapid Next clicks request offsets 100 and 200.

**Improve:** commit page state only after success, serialize/disable paging during requests, and retain a recoverable
error and keyboard focus. **Prove:** retry requests the same missing page, double clicks do not skip rows, and an old
page response cannot overwrite a new report selection.

### F-128 — Homepage section links scroll to the top instead of the section

**P3 · low · reproduced · S.** `web/identity.js:26–28` links to homepage fragments, but `web/app.js:125–130`
always scrolls to `(0,0)` after intercepted navigation.

**Improve:** honor valid decoded fragments after destination rendering. **Prove:** same-page and cross-page links,
missing fragments, normal modifier-key behavior, and reduced-motion preferences work predictably.

### F-129 — The lockfile includes two packages with moderate advisories

**P1 · medium · advisory verified · S.** `npm audit --omit=dev --json` reports `fast-uri@3.1.7` through
`ajv@8.20.0`, and `ip-address@10.7.0` through `@modelcontextprotocol/sdk → express-rate-limit`.

- `fast-uri`: inconsistent host normalization; the advisory identifies **3.1.8** as a patched version in this major.
  [Maintainer advisory](https://github.com/fastify/fast-uri/security/advisories/GHSA-hrr3-gc8f-f4qj).
- `ip-address`: cross-family subnet comparisons and an unbounded IPv6 parse diagnostic; **10.7.1** is identified as
  patched. [Subnet advisory](https://github.com/beaugunderson/ip-address/security/advisories/GHSA-j6r3-76f7-8jcv),
  [diagnostic advisory](https://github.com/beaugunderson/ip-address/security/advisories/GHSA-h3mg-xc3c-68pw).

Read on 2026-10-01 Cairo time. The audit verifies dependency exposure, **not an AMCP exploit**. The inspected
rate-limit path first uses Node's `isIPv6` and compares IPv6 objects; Ajv uses `fast-uri` for schema URIs.
These observations limit the demonstrated attack surface but do not replace a full reachability analysis.

**Improve:** make a narrow lockfile update after compatibility review, rerun schema/auth/rate-limit tests and the
full suite, then add a periodic dependency-advisory check with a documented exception process. Avoid blind major
upgrades or an automatic `audit fix --force`.

### F-130 — Current-state review documentation contains historical facts and settled decisions

**P2 · medium · traced · S–M.** `docs/review/THREAT-MODEL.md` still lists several fixed gaps and recommends
out-of-band spending approval, although `ROADMAP.md` records that the owner declined it. `SUMMARY.md` still names
57 registered families; the current registry contains 167. `PLATFORMS.md` explicitly describes batch 34, while the
branch reaches batch 49. The documented per-tenant audit-chain topology differs from the global previous-hash lookup.

**Improve:** separate historical records from a generated current-state summary; link each control to its current
test/evidence and preserve prior owner decisions. **Prove:** counts come from the registry/ledger, resolved defects
are not described as current, and all recommended decisions are genuinely outstanding.

### F-131 — Ordinary navigation bypasses the report's unsaved-change protection

**P2 · medium · traced · S–M.** `web/report-library.js:105–106` guards library actions, but `web/app.js:125` and
the popstate handler at `:877` do not use that guard. Input handlers mark dirty state; reconstructing the form after
ordinary navigation can discard edits.

**Improve:** preserve an identity-scoped draft or consistently warn before losing it, including back/forward and
reload. **Prove in a browser:** cancelled navigation preserves URL and form, valid saves clear dirty state, and
identity changes deliberately remove private drafts. Do not retain another user's draft to solve data loss.

### F-132 — The website discards useful backend recovery instructions

**P2 · medium · traced · S–M.** `web/workspace.js:9–12`, `web/reporting-overview.js:14–18`, and
`web/app.js:101–109` collapse rich errors into a message or code. `src/errors.ts:763–825` already returns targeted
remedies and request identifiers.

**Improve:** preserve a typed error envelope and show a persistent, accessible explanation, safe next action, and
copyable request ID. **Prove:** expiry, missing account grants, rate limits, and uncertain mutations have distinct
recovery. Never automatically execute a provider-supplied or returned `next_call` as if it were user approval.

### F-133 — Workspace actions can lose keyboard focus after rerendering

**P2 · medium · traced · S.** `web/workspace.js:21–35` reenables an old button that a renderer may have removed.
`web/identity.js:84–132` already has stronger focus restoration in `authBind`.

**Improve:** reuse one action-binding convention with pending states and focus restoration.
**Prove in a browser:** focus returns to the corresponding control, surviving section, or heading after success and
failure; keyboard users are not silently returned to the document body.

### F-134 — Unexpected worker-loop failures lose useful operational context

**P2 · medium · traced · S.** The catch at `server/http.ts:75–76` emits a generic worker-loop failure line.
Unexpected failure location and sanitized error identity are unavailable there, despite useful job/provider metrics
elsewhere.

**Improve:** record a bounded structured event with error code, stage/job kind when known, correlation ID, and a
counter. **Prove:** synthetic worker faults produce actionable diagnostics without payloads, tokens, customer data,
or uncontrolled error-cardinality growth.

### F-135 — Website execution cannot acknowledge a confirm-policy cap breach

**P1 · medium · source-traced, not browser-reproduced · S–M.** A configured spending policy defaults to confirm
mode (`src/spend-policy.ts:604–610`); no configured policy does not imply an automatic cap. Preparation returns
`execute_requirements.cap_override_confirmed` and the exceeded-cap explanation (`src/write-review.ts:148–168`).
The website renders only request/spend acknowledgements (`web/workspace.js:123–124`) and does not submit the cap
flag (`:205–212`). No web script supplies it. The campaign schema and backend forwarding support it.

The result is a fail-closed workflow: a legitimate reviewed action that exceeds a configured confirm-mode cap cannot
be completed through this website path and returns `CAP_CONFIRMATION_REQUIRED`. This is not a policy bypass.
Existing backend tests cover required acknowledgement, refusal without it and success with it
(`tests/spend-caps-confirm.test.mjs:110–118`); the browser scenario still needs a regression.

Render the exact execution requirements, the cap/excess details and an initially unchecked acknowledgement when
required. Submit it only after that acknowledgement. Qualify within-cap execution, confirm-mode breach, block-mode
refusal, expired/changed reviews and caps exceeded between preparation and execution. Retain existing review hashes,
idempotency and policy controls.

## 6. Improvements across the whole product

### 6.1 Security, privacy, and authorization

Preserve selected-account boundaries, actor checks, credential binding, state hashes, explicit confirmations,
durable idempotency, and the distinction between accepted, refused, and uncertain outcomes. Existing tests cover
many of these well. The confirmed fixes strengthen those rules; they require no new safety loosening.

Beyond the urgent defects:

- Make mutation dispatch authority a clearly shared abstraction. It should be difficult for a new transport or
  media path to omit an owner control. Keep receipt recording separate so late revocation never erases evidence.
- Use safe audit/error projections for personal-data operations. Cover both successful and refused requests,
  including identifiers that are not hashes or emails.
- Add a control-to-test map for every high-risk promise: which actor, account, stage, and persistence surface is
  covered, and which asynchronous boundary remains untested.
- Keep a current dependency-advisory process and supply-chain inventory. The workflow already pins action SHAs;
  add vulnerability review without weakening lockfile reproducibility.
- Document audit-chain topology and retention/backup verification accurately. Test tenant export and restore
  behavior against the actual global/per-tenant design before changing it.

Success means privacy probes leave no people in storage, revoked authority stops unsent writes, and diagnostics
still explain what happened without exposing payloads.

### 6.2 Campaign building and reviewed execution

Campaign plans, recipes, cloning, preflight, state revalidation, and verification already exist. Extend them rather
than creating a second campaign engine.

- Present a visible before/after review: named account, affected entities, status/delivery changes, budget units and
  currency, dates, destructive effects, expiry, and exact confirmations. `web/workspace.js:123–125` currently puts
  the review in a collapsed JSON disclosure next to consent controls.
- Add a plan-level review summary with dependencies and which steps create, change, activate, or only inspect.
  Preserve provider-specific differences instead of hiding them behind a misleading universal campaign object.
- Extend existing preflight into an offline plan simulator that reports all locally discoverable blockers before
  preparing any step. Mark live prerequisites as unknown rather than simulated success.
- Show recovery states clearly: not submitted, accepted, verification pending, failed, and uncertain. Resume safe
  reads and known steps; never turn uncertainty into an automatic fresh write.
- Add an owner review/history view if useful for visibility, using the existing confirmation model. Do not revive
  the previously declined out-of-band spending-approval requirement.

Success means an operator can explain what a plan will do before approval and can recover a partial run without
guessing whether it is safe to repeat a mutation.

### 6.3 Reporting, measurement, and decision quality

- Fix additive-period reconciliation and valid missing-metric handling first. Add tests comparing totals with the
  sum of disjoint periods where the metric is additive.
- Strengthen provider envelope validation and aggregate request budgets. A malformed response must not look like a
  healthy empty account, and a daily report must not unexpectedly multiply the advertised request budget.
- Make metric provenance visible in the main results: native source field, objective/event definition, attribution
  context, currency, time zone, period, freshness, and completeness. Existing evidence and `metricSources` are the base.
- Keep zero, missing, not applicable, permission denied, partial, and delayed distinct in tables and exports.
  Custom formulas should retain units and explicit null behavior, with a preview against sample rows.
- Never sum unlike currencies or incompatible conversion definitions without an explicit, sourced normalization.
  Provide reconciliation views that show excluded rows and assumptions before presenting recommendations.
- Pair every scale/pull-back suggestion with its evidence, minimum-data requirement, confidence limitations, and
  what must be checked by a person. Do not let a convenient recommendation become an automatic spending change.
- Improve saved-report discovery and navigation: client/account labels, last successful run, source freshness,
  export destination, schedule state, and a visible reason when data or delivery is unavailable.
- Preserve request lineage across resumed collections, and format Sheets currency/percentage/date cells from
  explicit metric metadata while retaining an unchanged raw-evidence tab.
- Clarify the website's two destinations: campaign collection/delivery versus captured evidence/analysis.
  Test names such as “Campaign reporting” and “Evidence & analysis” with actual users before renaming.

Success means report arithmetic reconciles, missing data is honest, and a user can trace a recommendation back to
specific native evidence without reading raw JSON.

### 6.4 Media, creative preparation, and delivery

- Fence completion/removal and enforce owner pause before every remaining upload step. Preserve confirmed upload
  boundaries and allocation receipts through cancellation, revocation, restart, and uncertain responses.
- Extract source acquisition, local inspection/transformation, provider sessions, and recovery into separate seams
  from the 2,217-line coordinator, after regression coverage proves behavior is preserved.
- Expand creative QA around existing inspection/resizing: clear per-placement dimensions, duration/aspect-ratio
  findings, readable copy-length checks, and a preview of each transformation before upload.
- Add a matrix for interruption at initialization, every chunk, finalization, receipt parsing, and verification on
  each supported transport. Include expired signed URLs and credential changes without logging those URLs.
- Show durable progress and recovery actions in the website: confirmed bytes, pending processing, source expiry,
  and whether a safe continuation exists. Avoid a generic failure that invites duplicate uploads.
- Qualify actual FFmpeg/ffprobe paths in release CI and container smoke; this host's five skips remain a gap.

Success means removal stays removed, pause stops future steps, and creative transformations are reviewable and
reproducible using the exact bytes that were approved.

### 6.5 Website state, usability, and interaction design

- Introduce explicit identity and route lifetimes before a broad visual redesign. Consolidate asynchronous action
  handling, typed errors, pending controls, polling cleanup, focus restoration, and draft protection.
- Make onboarding a task checklist using existing readiness data: connect provider, select account, grant the
  intended capability, configure applicable policy, create MCP access, and run a read-only readiness check.
- Give account selectors one consistent label: provider, account name and ID, login where needed, and capability
  status. Avoid silently carrying a selection between workspaces.
- Use persistent inline states for long operations, empty results, partial reports, and recoverable failures.
  Toasts remain useful for short acknowledgements but should not carry the only recovery explanation.
- Distinguish disabled controls from unavailable capabilities with a reason and a safe next action.
- Test first-time and returning-owner journeys end to end: signup/MFA, connections/account selection, MCP issuance,
  policy review, creative preparation, reporting/export/schedules, revocation, and disconnect.

Success means users can complete those journeys by keyboard, understand why a capability is unavailable, and never
see content from a previous identity or route.

### 6.6 Visual system, accessibility, Arabic, and dark mode

The current product already has shared color tokens, visible focus, reduced-motion rules, responsive adjustments,
named dialogs, report table headers, and bidirectional user text. Retain this foundation.

- Standardize the existing components: primary/secondary/destructive actions, inputs, panels, tables, empty/error
  states, status badges, confirmations, and job progress. Reduce stylesheet overlap instead of adding another layer.
- Prioritize clear financial review hierarchy and dense-but-readable reporting over decorative redesign.
- Turn the historical accessibility audit into repeatable browser coverage. Include route races, keyboard focus,
  320/375/768/1440-width layouts, zoom/reflow, long account names, and Arabic campaign text.
- Treat full Arabic UI as a deliberate product project: message catalog, translated errors/help, logical CSS,
  mirrored navigation where appropriate, locale-aware numbers/dates, and untranslated IDs kept unambiguous.
- Build dark mode through semantic tokens and rerun contrast/visual checks. It is an enhancement, not a release
  blocker merely because it is absent today.

Success means accessibility is checked on the current product, and localization/theme changes preserve account,
currency, date, and approval meaning.

### 6.7 MCP ergonomics and assistant efficiency

- Preserve compact references and the existing “use this when” descriptions. Measure complete workflows, not only
  schema bytes: calls, response bytes, preparation latency, refusal recovery, and successful user outcomes.
- Offer a compact account-readiness response with the named account, available capabilities, blockers and exact
  next read. Reuse `amcp_workspace`; avoid adding a redundant gateway for the same workflow.
- Make error envelopes consistent across MCP and website so assistants and people receive the same safe remedy.
- Add accurate MCP tool annotations only where the whole tool has uniform semantics. A mixed read/write gateway
  must not be globally labelled read-only, non-destructive, or safely repeatable.
- Keep tool schemas and guides generated/tested together. Add response-size budgets for help, inspect, prepare,
  plan status, and report summaries, with opt-in expansion for full evidence.
- Make the existing filtered/searchable action discovery in `src/introspection.ts:43–84` easier for clients to
  discover and use; measure unnecessary full-catalog requests before adding more discovery surfaces.
- Define a small benchmark suite for common intents: “what can this account do?”, “build a paused campaign”,
  “change a budget safely”, “upload these creatives”, and “explain last week's performance”.

Success means fewer unnecessary round trips while preserving the exact review, account, and evidence boundaries.

### 6.8 Architecture, types, and maintainability

- Keep the reviewed-family registry as the extension boundary. The current 167 families should not reappear as
  provider-name conditionals inside lifecycle code.
- Refactor the largest modules along behavior seams: media stages, workflow dispatch, provider-specific targeting,
  persistence responsibilities, and plan recovery. Require unchanged ledgers plus replay/regression evidence.
- Extract repeated parsing/validation helpers only when their semantics really match: REST.li IDs, paging,
  envelope validation, bounded reads, and safe diagnostics. Similar-looking provider contracts can differ.
- Introduce discriminated types for request/job/recovery states to make impossible transitions harder to represent.
  Reduce unchecked casts at actual trust boundaries before pursuing cosmetic type cleanup.
- Separate pure normalization/calculation from transport/persistence so period arithmetic, money units, and
  validation can be property-tested without constructing an entire service.
- Establish focused module guides: how to add a family, report adapter, media transport, browser route, and job.

Success means a new provider contract needs a small, explicit set of changes and cannot silently bypass lifecycle
checks. Avoid a framework/database rewrite until measured problems justify it.

### 6.9 Responsiveness, load, and cost

- Measure preparation state reads and reporting against fake transports with controlled latency; parallelize only
  independent reads while retaining coherent snapshots and provider budgets.
- Measure public/auth page first interaction on a throttled device, then evaluate lazy loading of reporting,
  creative, and QR modules. Preserve CSP, browser caching, and straightforward deployment.
- Add aggregate job request/byte/time budgets across periods and sources, with truthful progress and resumable
  checkpoints. Consider avoiding repeated account/inventory discovery within one frozen report.
- Benchmark event-loop delay and SQLite lock waits under concurrent jobs before splitting processes or changing
  storage. Keep transactions short and examine query indexes using synthetic workloads.
- Coalesce concurrent health/credential/readiness work where identity and freshness rules permit it.
- Record trend budgets rather than absolute timings from one machine; track cold start, RSS, payloads, and suite time.

Success means measurable latency/quota reductions without stale state, hidden partial data, or weaker authorization.

### 6.10 Resilience, observability, and operations

- Add sanitized correlation across request → review → provider attempt → receipt → verification/job, without
  retaining bodies, people, tokens, or signed URLs.
- Extend existing operations health into a clear queue/recovery view: oldest job, lease/retry state, cooldown,
  uncertain write, last verified backup, and provider qualification gaps.
- Preserve retry discipline: bounded retries for safe reads; explicit reconciliation for ambiguous writes.
  Review each job kind independently before broadening worker retry eligibility.
- Test worker lease loss, restart, credential withdrawal, and concurrent job ownership. Explain to the user whether
  a task is waiting, failed, or needs manual reconciliation.
- Define operational recovery objectives and rehearse encrypted backup restoration to an isolated environment.
  Record elapsed time and successful integrity/credential checks; do not infer production recovery from unit tests.
- Give provider drift/sunset failures an owner-visible process. The current workflow records artifacts; any new
  outbound notification destination or permission should be chosen explicitly.

Success means an operator can diagnose and recover the common failures without querying secrets or guessing whether
a write occurred.
