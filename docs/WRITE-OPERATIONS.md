# Reviewed write operations

AMCP supports explicitly reviewed campaign-management mutations. The existing native gateways still provide reads and local dry runs. The additional `amcp_write` tool handles live execution when enabled. This extension is independently designed; it does not establish complete behavioral equivalence with AMCP.

## Enable access

1. In Railway variables, set `MIRROR_ALLOW_WRITES=true` and redeploy. Preserve `MIRROR_MASTER_KEY` and the persistent `/data` volume. Set the target port to the effective Railway `PORT` (**8080** in the current Railway service; local development defaults to 4317). `/healthz` reports the effective `live_writes` flag.
2. Sign in to Connections. Connect or reconnect each provider with the required app permissions. New Meta authorizations request `ads_management`; LinkedIn requests `rw_ads`; X requests write access. Existing provider tokens are not upgraded by changing an environment variable. Explicit `AMCP_<PROVIDER>_SCOPES` overrides take precedence, including an empty override.
3. Select the accounts available to the connection. New logins default to read plus reviewed write access when deployment write support is enabled. The selection screen offers an explicit read-only choice and per-account grant controls. Existing logins and manually revoked grants retain their access. Write grants are always a subset of selected accounts; deselection removes them. Every write grant a saved selection adds, including accounts added to an existing login later, needs the same explicit confirmation as the write-access panel (owner decision D19, CON-05): without `confirmed:true` the save is refused with `WRITE_ACCESS_CONFIRMATION_REQUIRED` and `details.added`, and the website lists those resources before asking. Read-only selections and removals need none. The `website_asset_selection` audit records `write_added` and `write_removed`; a sync whose complete listing no longer shows a selected account records `dropped_accounts` and `dropped_write_accounts`.
4. On Connectors, create the default **read + write** operator token and confirm its access, or choose a read-only token. New OAuth clients that omit scope default to `mcp:read mcp:write`; the authorization page still requires consent by a workspace member, who may choose read-only access instead; a viewer's consent grants `mcp:read` only. Explicit `mcp:read` requests and existing reader registrations stay read-only. Refresh cannot increase scope, also inside the refresh reuse window.

For local stdio, `MIRROR_ALLOW_WRITES=true` defaults the role to operator; explicit `MIRROR_ROLE=reader` keeps read-only access. Provide the encryption key and provision the connection's `writeAccounts` subset using the administrator CLI. HTTP role selection always comes from the authenticated connector, never client-supplied tool arguments. An explicit deployment setting of `MIRROR_ALLOW_WRITES=false` disables all live writes.

Provider permissions, account roles, app review and API access remain necessary. Broad provider permissions do not override AMCP's account grants. Stop future submissions by revoking the connector, removing account write grants, or disabling write support. Revocation is checked again after asynchronous state reads and credential refresh. Requests already received by a provider cannot be recalled.

## Inspect, prepare, review, execute

For an unfamiliar non-media operation, call `amcp_write` with `action: inspect`, `gateway` and the native `arguments`. This checks local execution-contract support, reports its state-read paths and makes no credential or network access. It does not verify live permissions or create a review. Its `account_capability.write_granted` compares the account the way enforcement does (Google dashes and the Meta `act_` prefix are normalized). Media imports use their media preparation flow.

For an offline conversion upload with `people` (Google Data Manager `DATA_MANAGER_INGEST_EVENTS`, Meta Conversions API events), inspect also returns `offline_upload_rehearsal` (MSR-03): a local dry run that hashes the people in memory with the provider's time limits applied (the contract check skips them; a refused event is reported in `time_window`), builds the exact execution request and, where the provider documents one, its no-execution form (Data Manager `validateOnly: true`, the only field in `differs_by`), and reports both as request hashes with the counts. Nothing is sent (`transmitted: false`, `network_requests: 0`), no review is created and a rehearsal is never executable (`outcome: "rehearsal"`, `executable: false`). Sending the provider's validate-only form would still transmit hashed personal data, so under owner decision P4 (2026-10-11) such a rehearsal is reviewed like an execution: it is not sent from `inspect`, and sending one waits for a reviewed rehearsal path, designated test resources and write-class authorization. Meta has no rehearsal: events sent with `test_event_code` are production events that Meta does not drop, so AMCP never offers it.

Who may change anything is checked first (MCP-09). A native gateway call of a write action with `dry_run:false` is refused before any execution check with `WRITE_REVIEW_REQUIRED`, whose `details.next_call` is the `amcp_write inspect` call for the same arguments (without `dry_run`, `confirmed` and `idempotency_key`); delegated gateways keep their `operation`. A read-only deployment lists `amcp_write` with `inspect` only (owner decision D15) and refuses `prepare` and `execute` with `LIVE_WRITES_DISABLED` before the payload is checked; the message names no operator setting. A caller authorized to read only (an AI client granted `mcp:read`, or a workspace viewer) gets `CONNECTOR_READ_ONLY` (HTTP 403) with `granted_scope` and `required_scope`, also before the payload is checked; it may still inspect. Workflow mutations through `amcp_native_action` (`update_entities`, `set_entity_status` and the like) are refused the same way, with the inspect call of their compiled native request. When ownership of a Meta object is not established, a typed action (campaign, ad set, ad, creative or custom audience) gets its one account list read as `details.next_call`; a bare ID of unknown type lists every candidate read in `details.ownership_reads`. `AMBIGUOUS_CONNECTION` names its `candidates` (connection ID, label, default flag, `account_selected`, `write_enabled`; labels are marked untrusted) and a `list_accounts` `next_call`. A disabled login (no selected assets) is never a candidate and cannot be made the default (`CONNECTION_DISABLED`).

Call `amcp_write` with a normal native gateway request. This example uses a synthetic account ID; replace it with an explicitly granted account.

```json
{
  "action": "prepare",
  "gateway": "meta_native_action",
  "arguments": {
    "action": "meta_campaign_create",
    "account_id": "123",
    "payload": {
      "name": "Reviewed draft",
      "status": "PAUSED",
      "objective": "OUTCOME_TRAFFIC",
      "special_ad_categories": [],
      "is_adset_budget_sharing_enabled": false
    }
  }
}
```

From Graph API v24.0 (including the `AMCP_META_API_VERSION=v25.0` rollback) a Meta campaign create without a campaign budget (`daily_budget` or `lifetime_budget`) must carry `is_adset_budget_sharing_enabled` as a boolean; Meta refuses it otherwise (error 4834011). AMCP refuses it first with `INVALID_META_CAMPAIGN` (`fields: ["is_adset_budget_sharing_enabled"]`), before any read or provider request. `false` keeps each ad set on its own budget, as before v24.0, and is not a spending field; `true` lets Meta move budget between the campaign's ad sets and needs `spend_change_confirmed`. AMCP never adds the field to a request you write; the guided Meta recipes send `false` because each has one ad set. A saved plan step without it fails preflight and is corrected with `amcp_campaign recover_step` and corrected `arguments`.

Preparation performs provider reads and returns `executed:false`, the frozen native request, its before-state, `state_hash`, `state_reads`, expiry, `review_id` and `idempotency_key`. `summary` is a server-authored line above it (`text`, `operation`, `entity`, `count`, `account` with the name and currency when the review read them or its last live read stored them, `money`, `status`, `changes` and `objects`): amounts are converted to account currency through the budget-unit contract with exact decimals only where the platform's unit is documented and the field names it (`micros`, and Meta's minor unit once the currency is known), and are otherwise left native; a status change names the target's current status. The line names each object (its name where the review read one, always its id), the field and the value it is given, `old → new` where the review read one; `changes` holds the first 10 rows (`changes_total` counts them; a value over 80 characters ends in `…` with `clipped: true`) and `objects` the names read. The frozen request stays the authority. The website counts down to `expires_at`, disables Execute at zero and offers Prepare again, which reads the state again and creates a new review; in a plan, a step prepared again for the same request over unchanged state carries `unchanged_since_review` with the expired review's id, and the website says the same of a review it prepares again when the new review's `fingerprint` and `state_hash` equal the expired one's. A summary lists at most 10 money and 10 status entries (`money_total`, `status_total` count the rest). Inspect the account, resources and payload. No mutation is submitted during preparation. `dry_run:true` on the original gateway is an entirely local preview and does not produce a write review.

Prepare and execute reuse the stored read plans. Raw responses are checked for provider errors, completeness and exact resource identity before projecting configuration. Google snapshots retain only `results`, excluding `queryResourceConsumption`, field masks and other envelope metadata. TikTok retains `data.list`; X/Reddit retain `data`; Microsoft retains the contract's named entity result; Apple retains `result`; Snapchat retains the requested resource records. A nonempty pagination continuation still blocks execution before projection. Flat resource responses retain unknown configuration fields; Search Console sitemap crawl/processing observations are excluded while submission identity and `lastSubmitted` remain protected. Media account reviews use the same projection.

Object keys and explicitly qualified scalar sets are normalized; unknown/ordered arrays, duplicate members and scalar types remain meaningful. Google GAQL resource rows are sorted by their validated identities, without sorting arrays inside a resource indiscriminately. Delivery telemetry, server timestamps and stats/pacing telemetry are excluded; mutable status, budgets, schedules, targeting, bids, pacing, native fingerprints and unknown resource configuration remain protected. `STATE_CHANGED` includes `expected_state_hash`, `actual_state_hash` and JSON paths in `changed_fields`; the request `fingerprint` remains a separate hash of the frozen request. Still-valid older, unsubmitted review envelopes are reprojected using their frozen read plans. Their normalized state hash may differ from the pre-upgrade value, but request fingerprints, expiry, confirmations, grants and original idempotency claims are unchanged. Completed writes replay their original receipt; uncertain claims are never reset.

See the [state-projection repair and platform coverage report](implementation/STATE-PROJECTION-2026-09-18.md) for reproductions, compatibility details and verification limits.

Submit the same review only after confirming its intended change:

```json
{
  "action": "execute",
  "review_id": "COPY_FROM_PREPARE",
  "idempotency_key": "COPY_FROM_PREPARE",
  "confirmed": true
}
```

Budget, bid, spend or activation changes additionally require `spend_change_confirmed:true`. New serving entities must explicitly be paused or draft. A TikTok create that its shape pins paused needs no `spend_change_confirmed` for its budget, bid or status fields (owner decision Q14, 2026-11-15): a campaign, or a Smart+ campaign, ad group or ad, created `DISABLE`, or a standard ad group or ad created `DISABLE`, or `ENABLE` under a parent the review reads as paused. The owner's caps, `allow_activation`, the paused-parent check (`PARENT_SERVING` when the parent's status is unread, and again at execute) and the flag on enabling an existing object or widening spend are unchanged. Under parents the review reads as serving (`ENABLE`), a TikTok ad group or ad, standard or Smart+, may also be created `ENABLE` (owner decision Q1, 2026-11-15; R2.5 M4): it serves as soon as it is created, so the review's own state asks for `spend_change_confirmed` at prepare and execute refuses without it, while `inspect` and a plan's approval, which read no state, do not (a plan's run stops at each such step once for the flag). Campaigns are still created paused only. A TikTok create is sent as the caller wrote it: AMCP adds no `request_id` of its own (TikTok's create pages say a different `request_id` is how a second object of the same name is created, and that a key de-duplicates only within 10 seconds), and a `request_id` the caller supplies, which a Smart+ create requires, is frozen with the review and sent as it is. A Google Ads create that cannot serve needs no `spend_change_confirmed` either (owner decision, 2026-11-19): a campaign create, which its shape pins `PAUSED`, and an ad group, asset group, ad, ad-group criterion or positive campaign criterion created under a campaign or ad group that the review's own state reads as `PAUSED`, at prepare and again at execute (a parent enabled in between stops the write as `STATE_CHANGED`), while a create under a serving or unread parent, every enable, budget, bid, schedule or targeting edit of an existing object, every build, `inspect` (which reads no state), the owner's caps and `allow_activation` are unchanged.

`prepare` returns `execute_requirements` — `{confirmed, idempotency_key, spend_change_confirmed, creative_edit_confirmed, reasons[]}` — decided by the same rules execute applies, so a client asks the user once instead of discovering a missing flag from a refused execute, and `expires_in_seconds`. Execute still re-checks everything. The spending acknowledgement is decided structurally as well as by field names (`src/spend-effects.ts`):

- An edit of an existing campaign, campaign group, insertion order, ad set, ad group, ad squad or line item in the generic Google Ads, Meta, TikTok, LinkedIn, X, DV360 and Snapchat families needs `spend_change_confirmed` unless every field it changes is the name, an identifier, or a status that pauses, archives or removes. Bid targets (`targetCpaMicros`, `targetRoas`, LinkedIn `unitCost`), pacing (DV360 `pacing`), schedules, targeting and optimization goals therefore need it; the refusal lists the fields. Ads, creatives and assets are content: their activation is still checked, and creative edits keep their own impact disclosure. A Snapchat creative edit's `creative_impact` lists the ads that use the creative (`affected_ad_ids`, `affected_ads` with id, name, status and ad squad) from a read of the account's ads collection of at most 25 pages of 1,000, made through the review's guarded reader and not part of its frozen state; past the bound, or when that provider read fails, the list is `null` with `incomplete: true`. `affected_ad_ids` names every matching ad, while `affected_ads` details at most the first 100 (`affected_ad_count` is the total and `listed_truncated: true` says some are not detailed).
- A status given as a number (ProtoJSON enum numbers such as Google Ads `status: 2`, which is ENABLED) cannot be shown to leave an entity paused: it needs `spend_change_confirmed`, counts as activation under `allow_activation:false`, and reviewed Google Ads mutations refuse numeric enum values outright (`INVALID_VENDOR_BODY`).
- A request that deletes or removes, publishes live (a Tag Manager version publish, a Search Console sitemap submission, a Business Profile place action link) or stops delivery (a status that pauses, archives or removes a campaign, ad set, ad group, ad squad or line item that is not already in it; TikTok `DISABLE`) is disclosed at prepare: `effects: {destructive, irreversible, publishes_live, stops_delivery}` in the response and in `execute_requirements`, one `reasons` entry per effect (`effect`, the target's id, name and current status from the before-state; a request for several entities is named by their count instead, and a list of operations that removes some is named by its removals, with what else the same request creates or updates), and a `user_approval` that names the effects. Deleting an entity that is already paused, archived or removed does not claim to stop delivery. It adds no flag and refuses nothing (`allow_deletion` stays the owner's control); other writes are unchanged. A group combines its parts' effects. In a plan, `prepare_next` repeats the effect reasons in `next_call.disclose`, and the whole-plan approval lists the steps whose arguments delete, remove or publish. A family may decide the publish effect itself (`publishes` hook).
- `amcp_campaign` never pre-fills `spend_change_confirmed` in its suggested `next_call`. When the step needs it, the response carries `execute_requirements` and `next_call.add_after_user_approval`; add those flags only after the user approves the reviewed change.
- `amcp_campaign` responses are compact and at most 12 KB whatever the number of steps: the plan header, one row per step with its resource IDs, verification status and error code, the step the call acted on (`current`, with its receipt and verification) and `next_call`. `prepare_next` shows the review's request, state hash, a summary of each state read and the spend policy, not the raw before-state. `get` with `step_id` returns one step without its request body (sizes and hashes) but with its last error, receipt and verification; `topic` (`request`, `arguments`, `before_state`, `receipt` or, for a write group, `parts`) reads one part in pages of at most 24 KB, or one subtree by the JSON pointer in `query`; `detail: "full"` returns the step whole up to 25 KB. `get` with `detail: "full"` and no `step_id` returns the whole stored plan; nothing stored changed.
- A plan step whose target already holds every value it would send is `skipped_unchanged` (COM-01): when `prepare_next` reaches it, the family's own prerequisite finds exact equality in its fresh read and refuses the write with `already_current: true` and `no_op_evidence` (for an X catalog product: catalog, product ID, the compared fields and a hash of the observed product). The plan records that evidence as the step's result, sends nothing (`submission: "not_submitted"`, no review or key) and moves on; the step counts as settled, so the plan can reach `complete`. Any difference, even one hundredth, gets an ordinary review. Execute receipts list such steps under `skipped_unchanged`, apart from `verified`. A direct `amcp_write prepare` of the same request is still refused. Only X catalog products raise this today; a Meta product that already matches is reviewed and sent again.
- A whole-plan approval (`amcp_campaign approve`) counts every budget, bid and status field of every step (`fields_total`). A step with more than 24 is aggregated (`truncated: true`): one row per field pattern with `count`, `distinct_count`, up to five `values` and, for money, `min` and `max` as sent; `approve` with that `step_id` lists every field. Each step lists what it changes, row by row (`changes`: `object`, `id` or `ids` with `count`, `field`, `new`, and `shown` for money in the account's currency), read from the compiled request, so with no old value or name; an update under a field mask lists the masked fields (one the body omits is a clear), and a date inside a value is a row of its own. A step lists 12 rows (4 for a create: its name and dates) and says `changes_total` for more, bound in `changes_digest`; a value over 80 characters is cut in the summary (`clipped: true`), never in the step's own list, which `step_fields` names (the `approval_summary` call with `step_id`). Four or more steps that make one change to one object each are one `groups` entry. The summary holds 8,192 bytes, less where the compact plan view of many steps would pass 11,264; past that the steps with the most rows, the last first, are cut to their own list (`truncated`, `aggregates: []`, `changes_total` where they have more than one row, one plan-level `changes_digest`); a plan of over about 40 one-field steps still passes the 11,264 bytes. `accounts` (stored name, currency, time zone) is display only, not in `summary_hash`. A summary read before this has another `summary_hash` and answers `PLAN_CHANGED` once. Steps that delete, remove or publish carry `effects`, repeated in `next_call.disclose`. Each write step also carries `spend_effect`, decided by compiling it locally as its review will (a step that cannot be compiled counts as spending), and `spend_steps` lists the steps that spend, bound by `summary_hash`. The list is an upper bound, decided from the plan alone and without the state of the account: a review prepared later may ask for less than it names, and a step whose review asks for more than the approval showed stops on its own. `approve` with `spend_change_confirmed` covers exactly those steps, so `run` asks for nothing more for them; a plan approved without it stops once, and that stop's `next_call` approves the same plan and summary again with the flag. An approval recorded earlier with the flag covers every step, as it did. `approve` with `confirmed: true` needs the summary's `summary_hash` as well as its `plan_hash` (`PLAN_CHANGED` otherwise); approvals recorded earlier stay valid until their 24-hour expiry, and `AMCP_PLAN_SUMMARY_HASH=false` accepts `plan_hash` alone. The website shows "(+N more)" for the rows a step does not list and keeps Save plan approval disabled until the complete list of every step that has more (truncated, `changes_total`, a cut value) was opened.
- A Google Ads mutation or Snapchat entity batch of more than 25 records (at most 1,000) is prepared as one review with `group: true` and `parts` of 25. Each part is an ordinary review with its own state reads, state hash, idempotency key, spending check and read-back; the group is approved and executed once. The owner's spending caps count the parts together, in order, as one change: the group's `spend_policy` and `execute_requirements` name a cap only the whole group crosses (`cap_override_confirmed`), and under `block` such a group is refused at prepare. `time_budget` gives the seconds each part needs (twice the slowest part's preparation, at least 3, or `AMCP_WRITE_GROUP_PART_SECONDS`) and `execute_by`, which is also the group's `expires_at`: the last moment at which every part still has that much of its own window when its turn comes. A group that cannot fit one window is refused at prepare (`WRITE_GROUP_TOO_LONG`). Before the first part is sent, execute checks every part (the owner's pause, access and grants, the acknowledgements, the caps for all parts together and the time budget); a refusal there sends and claims nothing. It then sends the parts in order and stops at the first that does not succeed: `WRITE_OUTCOME_UNCERTAIN` when that part was sent, `WRITE_PARTIAL_OR_FAILED` when earlier parts were applied and it was refused before sending. A partial stop lists `not_sent`; when the stopped part was not sent it also carries `part_submitted: false`, the remedy of the part's own cause (a pause, a policy, an expiry) and `next_call` with `not_sent_parts`, to send each part not sent as its own review once the cause is resolved. A stopped group is never run again; a completed one replays its receipt. A group a crash interrupted after a part was sent reads `uncertain` in `amcp_write status`, never `unsubmitted` or `expired`, and its execute after its window is `WRITE_OUTCOME_UNCERTAIN`. While its review is open and every part sent applied, `next_call` is its own execute (applied parts replay; only parts not sent are sent); then each part not sent has its own call. `amcp_campaign verify` with the group's `review_id` reads every part back. Operations that link through temporary IDs are not split.
- `idempotency_key` is optional at execute (in `amcp_write`, `amcp_media` and `amcp_campaign execute_next`): it is the review id, and a key that differs from it is still refused.
- `amcp_campaign create`, `create_from_recipe` and `clone` take an optional creation `idempotency_key`: the same key and input returns the original draft (a keyed clone retry reads nothing), and other input under that key is refused with `IDEMPOTENCY_CONFLICT`. The website sends one key per exact recipe brief or clone request. Recipe and clone steps are saved literally; `{{variable}}` substitution applies only to the explicit and template steps of `create`.
- The gateway, the connection and the account stand in different places in `amcp_write` and in a plan step. `amcp_write` prepare and inspect take `gateway` and `connection_id` at their top level and the account inside `arguments`, in the field the gateway takes (`account_id` for most; `amcp_tool_help` shows the field). A step of `amcp_campaign create` takes all three beside its `arguments`, and `create` also takes them once at its top level, as the default of the steps that leave them out: used only when the value fits its field and no step names another (a plan that mixes values stays refused, with `details.hint` and `details.move` naming what to put in each step), and written into each step, so the plan hash, the approval summary and every check a step's own value meets see it. A media step takes the connection and the account, never a gateway, and only when its platform is the top-level gateway's or none is given. A top-level value that no step used, in a plan that is accepted, draws `TOP_LEVEL_VALUE_NOT_USED` in `meta.argument_warnings`. A `gateway` written inside `arguments` is read as the gateway when the call or step names none of its own and the name is registered, with `GATEWAY_PLACEMENT_DEPRECATED` in `meta.argument_warnings`. A plan step's keys sent to `amcp_write` (`account_id`, `id`, `kind`, `depends_on`, `description`) are refused with `INVALID_ARGUMENT`, `details.move` naming where each goes; the help of each tool states the other's shape (`other_tool_shape`).
- `amcp_campaign run` resumes a step a crash or restart left `executing` under its original review, key and plan approval: a completed receipt is replayed, a pending or uncertain claim marks the step `uncertain` and stops the plan without sending again, and a claim never made is sent once while its review is valid. It asks for a person for the same acknowledgements as any other step.
- `amcp_campaign run_background` (MED-03) queues an approved plan whose steps are all media uploads for the worker, which runs it exactly as `run` does, under the same approval and as the same person; leaving the website or client stops nothing and `get` shows `background`. In a plan of independent uploads (no `depends_on`) a failed, uncertain or processing upload holds none of the others, and an upload refused by busy media capacity stays `pending` (`waiting`) until the run continues. A plan with any other step is refused (`BACKGROUND_RUN_UNSUPPORTED`); `AMCP_SERVER_PUSH=false` refuses all (`BACKGROUND_RUN_DISABLED`). A client that sends a `progressToken` with the call is told how many uploads have settled while the call is held (up to 25 seconds), and one that declares the MCP tasks extension is answered a task; the run itself, its approval and its rights are unchanged, and a task cannot cancel the plan (see [Following a long run](REPORTING-OVERVIEW.md#following-a-long-run-polling-progress-and-tasks)).
- An expired review (`REVIEW_EXPIRED`) was refused before anything was submitted. The error carries `details.next_call`, which prepares the same request again. Ownership bindings from account-scoped reads also last five minutes, so the re-preparation may first need that read again (`RESOURCE_SCOPE_REQUIRED`). In a campaign plan the step returns to `pending` and `prepare_next` prepares it again.
- Campaign plans, uploads, retained originals and media variants follow the person (MCP-02, owner decision D16 (4)): a website account and every AI client and connector token it authorized share them, and the administrator's password sign-in shares them with the clients and tokens approved from it. Reviews and plan approvals stay with the connection (credential) that prepared or recorded them. Another connection of the same person sees and continues the plan, but `prepare_next` and `execute_next` refuse a live review it did not prepare with `REVIEW_HELD_ELSEWHERE` before the plan changes; after `details.review_expires_at`, `details.next_call` prepares a review of its own. `run` needs an approval recorded by the same connection (`APPROVAL_REQUIRED`). Another member's client is refused unless the plan's owner (or an administrator) named that member a collaborator (`amcp_campaign assign`, CMP-05): a viewer reads the plan, an editor prepares, executes, amends and archives it, and an approver approves and runs it, each within their current account access and under their own account grant and review binding; administrators keep their exemption. A collaborator whose role does not cover an action is refused with `FORBIDDEN` and `details.plan_role`. With the owner's `require_distinct_approver` policy, a plan that changes spending or activates a launch is approved by someone other than its owner, and `execute_next` sends its steps only under a current approval of the exact plan recorded by someone other than its owner, so executing step by step cannot skip the second person (`DISTINCT_APPROVER_REQUIRED`, checked before anything is sent; the review stays valid, and a step a crash left executing still resumes). A step review of such a plan, a write group that is one of its steps and each part of that group are not executed directly through `amcp_write execute` either: each is refused with `DISTINCT_APPROVER_REQUIRED` (`details.plan_id`, `details.step_id`, the read of the step in `details.next_call`) and executes through its plan (`execute_next` or `run`); `amcp_write status` of an unsubmitted one names that call, and the refusal of an expired or changed one names the plan’s call too (`prepare_next`, `execute_next` or the read of the step), never a standalone prepare. A review a plan goes on from is retired: `recover_step` amending the step, `prepare_next` preparing it again (a group whatever its window), `cancel` and `continue_as_new` mark its unsent review (a group and its parts too), and every `amcp_write execute` of it, even one already waiting, is refused with `REVIEW_RETIRED` before anything is claimed, policy on or off, as is a plan’s review that no step holds (`details.reason` `detached`); a review that holds a claim is never retired (a cancel still retires the unclaimed parts of a stopped group). `continue_as_new` refuses an `executing` step; `cancel` leaves it `review_ready` (review retired) or `uncertain` (review claimed). A plan’s write group that stopped part-way (every part sent applied, the others refused before they were claimed) is finished by `execute_next` under the plan’s current approval while its window lasts, replaying the applied parts and sending only the others; `prepare_next`, `get` with a `step_id` and the stop name that call, and `run` stops at it. After the window no call of the plan sends the rest, and the group is never prepared again.
- Execute-time confirmation refusals (`SPEND_CONFIRMATION_REQUIRED`, `CREATIVE_EDIT_CONFIRMATION_REQUIRED`, `CONFIRMATION_REQUIRED`) keep the review valid: call execute again with the named flag after the user approves; do not prepare again.
- In enhanced mode, `native_request` is a read-only extension: `amcp_write` refuses it (`WRITE_CONTRACT_UNAVAILABLE`), because it lets a caller choose the action and the path independently. Execute cannot replace the request, account or connection. Reviews expire after five minutes and belong to the same tenant and user that prepared them. Changed, incomplete, paginated or missing state prevents submission. Successful Meta and Snapchat creates register their returned resource IDs to the owning tenant, connection and selected account, immediately allowing child prepares. Other global resources require an account-scoped collection read or an administrator binding. Existing ownership expiry and revocation rules remain enforced.

An owner spending policy separates creates from updates, because `max_budget_increase_percent` and the unambiguous-baseline rule only mean something against a prior budget. A create is recognised from an explicit REST.li `CREATE`, a `create` operation inside the payload, or a collection-scoped action name. A REST.li POST addressed to one resource — `…_{id}_post` or `…_{urn}_post`, which is how LinkedIn expresses `PARTIAL_UPDATE` — changes an existing budget and stays under the percentage and baseline rules. `max_budget_native` and `max_daily_increase_native` apply to both. Reddit campaign and ad group `goal_value` is a budget in microcurrency (pinned Reddit Ads API v3); an update that omits `goal_type` is compared with the reviewed entity's current goal of the same type.

Every money amount of a request for a capped account is either compared with a cap or reported as unsupported; a measurable amount is never dropped. A field the policy cannot measure (a cap cleared to null or zero, a removed cap, a field with no unit mapping) becomes one `POLICY_AMOUNT_UNSUPPORTED` finding beside the budget, increase, daily and bid checks of the other amounts, and the confirmed increase is still reserved. The Google Ads bid cap covers every writable bid of the pinned API version, generated from its Discovery document into `generated/google-bid-fields.json` by `npm run generate:bids` (CPC bid ceilings and floors, target CPC, CPM and CPV, fixed CPM, category bids); ratios are excluded, and `npm run generate:bids:check` fails when a newly pinned version adds an unclassified money field. Lifetime and custom-period totals (Meta and Reddit campaign `spend_cap`, Google `total_amount_micros`, other lifetime budgets) answer to `max_total_budget_native` (or `max_total_budget_currency`) when the owner sets one, otherwise to `max_budget_native`, and lowering one from its single current value is always allowed. During the rollout, `AMCP_SPEND_POLICY_UNSUPPORTED=abort` restores the earlier evaluator, in which the first unmeasurable field replaced the other findings.

A save replaces the stored policy, so it is checked against the revision the caller read (owner decision D9): `save_spend_policy` takes `expected_revision` (0 when there was no policy) and refuses a stale one with `REVISION_CONFLICT` (409), saving nothing; the response returns the new `revision`. The website always sends it. It shows the stored policy of the selected account (matched through `spend_policy_bindings` in owner health, the server's normalized policy key), keeps the settings and platform caps of the workspace default that its form does not show, and asks before a save that weakens a policy, naming each weakening: a removed or raised cap, `block` to `confirm`, activation or deletion newly allowed. A first account policy is compared with the workspace default it replaces for that account. MCP callers may omit `expected_revision`; a save that then replaced a stored policy returns a `REVISION_NOT_CHECKED` warning. Each `spend_policy_saved` audit event records the revision and whether it was checked.

A policy can be attached to one (gateway, account) pair or set once for the workspace with `scope: "workspace"`. The account-specific policy wins where one exists; otherwise the workspace default applies, so an account nobody configured individually is still protected. Each account keeps its own daily allowance under a shared default. `prepare` reports which applied as `spend_policy.scope`, and reports `configured:false` with `unprotected:true` when nothing protects the account. `amcp_workspace health` lists those accounts under `unprotected_accounts`.

Caps stated in account currency (`max_budget_currency` and the other `_currency` caps) name the currency they are in (`currency`, WRT-07): an account policy saved without one takes the account's currency from its last live read, and a workspace default states it per platform under `per_gateway`. Caps bound to a currency compare only an account that spends in it; another or an unknown account currency is `POLICY_CURRENCY_MISMATCH` or `POLICY_CURRENCY_UNKNOWN` (asked under `confirm`, refused under `block`, never converted). Caps in account currency that name no currency (saved before policies recorded one, or while the account's currency was unknown) cannot be shown to be in the account's currency, so under owner decision P5 (2026-10-11) every request with a budget or bid amount on an account they govern is refused with `POLICY_CURRENCY_UNSET` (409, under `confirm` and `block` alike, before any cap is compared or anything is reserved; no acknowledgement overrides it) until the owner saves them again with their currency. A request that only lowers budgets, each from its record's one current amount, is not refused (owner decision D7: decreases are always allowed; lowering a budget cannot raise spend in any currency) and is compared with the caps as before; a bid, a new budget, an amount without one current value or an amount AMCP cannot measure is still refused. `details.account_currency` names the account's currency when AMCP knows it. Requests without a money amount (pausing, renaming) are not affected. Before P5 such caps were compared as before, with a warning. Owner health and the save response list them (`POLICY_CURRENCY_UNSET` in `policy_warnings` and `warnings`, with `blocks: true`). `AMCP_LEGACY_CURRENCY_CAPS=warn` is a rollback only: they are compared as before, with the warning.

The owner's health view (`amcp_workspace health`, website Settings) also reads two things back from the audit, over the last 30 days. `cap_overrides`: how many reviews were executed beyond a cap with `cap_override_confirmed` under `confirm` (one per review), and the latest 20 with the account, the rules exceeded, who executed them and their role, and the review id. `review_friction`: prepares and executes, prepare-to-execute latency (nearest-rank p50, p90, p99), and the counts and rates per 100 prepares of `REVIEW_EXPIRED`, `STATE_CHANGED` (with the ten most frequent `changed_fields` paths), acknowledgement refusals (`CONFIRMATION_REQUIRED`, `SPEND_`, `CAP_`, `CREATIVE_EDIT_CONFIRMATION_REQUIRED`), `WRITE_OUTCOME_UNCERTAIN` and `write_not_sent` by code. It holds codes, counts and field paths, never values, reads at most 50,000 audit rows (`complete: false` beyond), and is the baseline the five-minute review window is kept against until it has been measured. `media` counts the media reviews apart (`amcp_media`, and a media review executed through `amcp_write`, which is not a write in the counts above): reviews prepared, uploads that reached the provider, and `REVIEW_EXPIRED` and `STATE_CHANGED` with their paths. `volatile_path_alarms` lists each path that explains more than 5 in 100 of a provider's prepares (at least three refusals, at least twenty prepares; `volatile_path_rule`), the worst ten.

`allow_activation:false` is enforced against the payload structure using a per-gateway declaration of the field and values each provider uses to start delivery — Meta `status:ACTIVE`, Google Ads `status:ENABLED`, TikTok `operation_status:ENABLE`, X `entity_status:ACTIVE`, DV360 `entityStatus:ENTITY_STATUS_ACTIVE`, Reddit `configured_status:ACTIVE`, Microsoft `Status:Active`. JSON Patch operations are resolved by their `path` and `value` in either key order. Measurement gateways declare no serving-activation surface and are not constrained by it. A gateway with no declaration is refused outright while activation is forbidden, so adding a provider without declaring its vocabulary fails closed.

`allow_deletion:false` refuses every write that deletes, at prepare and again at execute against the re-read state, before anything is sent (`POLICY_DELETION_FORBIDDEN`, with the body `field` when a value carried the deletion). Besides DELETE methods, family hooks and Google `remove` operations, a deletion carried as a body value on an update route counts: TikTok `operation_status:DELETE` on `/v1.3/{campaign|adgroup|ad}/status/update/` (the `tiktok_entity_status` family, which also lists the ad groups and ads a DELETE takes with it and refuses `allow_partial_success:true`) and on the Upgraded Smart+ routes `/v1.3/smart_plus/{campaign|adgroup|ad}/status/update/` (the `tiktok_smart_plus_deletions` family, which deletes only a target TikTok reads paused and lists the ad groups and ads it takes with it), Meta `status:DELETED`, Google `status:REMOVED` and `REMOVE` proposals and operators, Reddit `configured_status:DELETED`, DV360 `ENTITY_STATUS_SCHEDULED_FOR_DELETION`, LinkedIn `PENDING_DELETION`, and Microsoft `Status:Deleted` or `Action:Delete` (each provider adapter's `deletions` in `src/provider-adapters.ts`, read as `bodyDeletionValues` by `src/execution-risk.ts`). It also governs deletion through a Meta product feed (owner decision D8, judged on the feed's current state): a feed DELETE, a create or update that sets `deletion_enabled:true`, and a change of the `schedule` URL, interval or interval count of a feed whose deletion is on, since its next fetch removes every product the new file lacks; a name, hour or `update_schedule` change is not a deletion. `tests/deletion-policy-coverage.test.mjs` sweeps every pinned provider document for deletion values a request body can carry and every reviewed write route, and fails until a new value is classified or exempted with a reason. A saved, unsent TikTok DELETE or feed review is refused at execute once the policy forbids deletion.

The daily window is the UTC calendar day, and the cap counts requested positive budget increases rather than billed spend. A reservation taken for a write that then fails after it was sent is deliberately not released: a transport failure may still have reached the provider, and releasing it would let repeated failures walk past the cap. Only a refusal raised before the request left AMCP releases it (see [Outcomes and recovery](#outcomes-and-recovery)).

## Provider validation

Provider validation asks the provider to check a mutation without applying it: Google Ads `validate_only` on a mutate request, and Meta `execution_options: ["validate_only"]` on a campaign or ad set create or edit. It is a separate effect from a reviewed write: a remote call that applies nothing but uses write permission and API quota. It never creates a review, an idempotency claim or a spend reservation, and it never permits execute.

- `amcp_campaign validate_provider` runs it on its own. It needs `MIRROR_ALLOW_WRITES=true`, or, in a read-only deployment, the deployment owner's explicit opt-in `AMCP_PROVIDER_VALIDATION=true` (owner decision D18); otherwise it is refused with `LIVE_WRITES_DISABLED` before any credential or network access. It always needs the account's write grant (`WRITE_ACCOUNT_FORBIDDEN`). `provider_validation_started` is audited before the request is sent, then `provider_validated` (with a receipt, `executed: false`) or `provider_validation_failed` with `PROVIDER_VALIDATION_FAILED`, the provider's `field_paths` and its `provider_errors`. A lost reply is `UPSTREAM_UNAVAILABLE` with `validation_only: true`: nothing changed.
- `amcp_write prepare` with `provider_check: true` validates the reviewed request at prepare, through the review's connection and authority checks (writes must be enabled). Google Ads prepares validate by default in a deployment whose policy turns that on (the production server does): when the call says nothing about `provider_check`, a request whose route has a `validateOnly` field is checked as if it had sent `provider_check: true`, and `provider_check: false` opts out. The routes of batch jobs, billing setups and the two user-access resources have no such field: nothing is sent for them, and an explicit `provider_check: true` on one is refused with `INVALID_ARGUMENT`. A check that nobody asked for and that cannot run (the provider did not answer, or said it could not be asked now) does not refuse the prepare: the review's `provider_check` is `not_run` with the error's code and the review is prepared without it, and a check that ran by default carries `default: true`. The result is the review's `provider_check`: `provider_validated`, or `provider_rejected` with `field_paths` and `provider_errors` (the provider's rows: error code, operation and field path, policy and whether it is exemptible, and the trigger when it is the request's own text). A rejected review cannot be executed: the standalone prepare says `executable: false`, `status` reads it as `rejected`, execute is refused `PROVIDER_VALIDATION_FAILED` with the same rows, and a plan step fails at prepare, unsent, for `recover_step`. Prepare it again once corrected. Execute still reads the state again. `inspect` reports `provider_check_available` and, when it is false, `provider_check_reason`: no validate-only route is qualified for the request, and `provider_check` is not AMCP's own state check, which every execute runs and no flag skips. `provider_check` is an argument of prepare only; execute refuses it with `INVALID_ARGUMENT`.
- Reviewed writes refuse validation modes: Google `validateOnly`, and Meta `execution_options` containing `validate_only` or `include_recommendations` (`WRITE_CONTRACT_UNAVAILABLE`), because a reviewed write applies its request and would otherwise be receipted as an applied change. Other Meta `execution_options` values are unaffected.

## Human approval and the destructive tier

The acknowledgement flags (`spend_change_confirmed`, `cap_override_confirmed`, `creative_edit_confirmed`) record that the user approved in the AI client; nothing outside the client attests it. A person's own approval on the AMCP website comes in through one rule and two owner settings that are off by default (WRT-09, `src/write-approval.ts`, owner decisions P1 and P5 of 2026-10-11):

- **Only the owner executes beyond a cap (owner decision P5, always on).** Under `enforcement: confirm`, executing a review beyond a cap is the workspace owner's: the owner executes the review (the owner may execute one a member prepared, as with uploads of people), or approves that exact review on the website first, and the acknowledgement `cap_override_confirmed` is still needed. Anyone else's execute is refused with `CAP_OVERRIDE_OWNER_REQUIRED` before anything is reserved, claimed or sent; prepare names it in `approval` (`owner_required: "cap_override"`, `website_path`), and `amcp_write status` shows whether the owner has approved. A group, including one that crosses a cap only with all its parts together, is approved and checked as a whole; only the member who prepared a group executes it, so beyond a cap the owner approves it on the website. Before P5 this was the opt-in `cap_override_owner_only` (off by default: a member with write access executed beyond a cap on the acknowledgement alone). No policy turns the rule off: `save_spend_policy` refuses `cap_override_owner_only: false` with `INVALID_POLICY`, accepts `true` without storing it, and a value stored before P5 is not read; the website's workspace default form states the rule instead of offering a checkbox.
- **`approval_mode`** in the spending policy (account or workspace default; the website's workspace default form sets it): `assistant_ack` (default, unchanged), `website_approval` (a signed-in member with write access approves on the website) or `distinct_approver` (another person than the one who prepared it, or the owner). Each setting applies as the stricter of the account's own policy and the workspace default: an account policy saved for its caps never drops the default's approval (unlike caps, where an account's policy replaces the default). It applies to reviews that change spending, go beyond a cap or delete. Prepare returns `approval` (`classes`, `approver`, `website_path` = `/operations?approve=<review_id>`); execute without an approval is refused with `HUMAN_APPROVAL_REQUIRED` (`details.website_path`, `submission: "not_sent"`, `next_call` `amcp_write status`, whose `approval` says whether a person has approved), and the review stays valid. An expired review is refused as `REVIEW_EXPIRED` first: it is prepared again, not approved.
- **The approval.** A `write_approval` record bound to the review's fingerprint (a group's covers every part, and a part's page opens its group) and to the approver, minted only by `POST /api/write-approvals/:id` (a session with CSRF, recent sign-in and, where the workspace requires it, two-step verification), never by an MCP tool; it is audited (`write_approved`, then `write_approval_presented` at execute). One for another fingerprint is refused (`reason: "approval_fingerprint_mismatch"`), as is one by the preparer under `distinct_approver` (`reason: "approver_prepared_it"`). A door sign-in and every key approved from a door are one principal (`workspace-admin`), so AMCP cannot tell whose review it is: under `distinct_approver` such a review needs the owner's approval (`reason: "preparer_unidentified"`; the approval page refuses other members with `DISTINCT_APPROVER_REQUIRED`). A review is approved once (`REVIEW_ALREADY_APPROVED`): the owner's approval replaces a member's where a change beyond a cap needs the owner, and an eligible member's replaces one that no longer meets the mode. A review runs at most once, so its approval is used at most once.
- **Plans.** Each plan step that changes spending, goes beyond a cap or deletes is its own review and needs its own approval; a plan approval (`amcp_campaign approve`, and the separate CMP-05 `require_distinct_approver` plan policy) never gives it. `run` stops there with `needs_website_approval` (or `needs_owner_approval`, `needs_destructive_confirmed`), `website_path` and the call that continues; nothing was sent.
- **`require_destructive_confirmation: true`** (the opt-in `destructive_confirmed` tier; either policy turns it on): a review that deletes lists `destructive_confirmed` in `execute_requirements`, and execute without `destructive_confirmed=true` is refused with `DESTRUCTIVE_CONFIRMATION_REQUIRED`, also for a review prepared before the owner turned it on. A plan step stops for it (`needs_destructive_confirmed`); `execute_next` takes the flag. The website's review asks for it with its own checkbox.

The website's Operations page shows a review for approval at `/operations?approve=<review_id>`: its summary, what it changes and why, who prepared it and its fingerprint, never its request body; the website's own review of a change links to it. The owner health view's `review_friction.approvals` counts approvals, their latency from prepare and the refusals that waited for a person ([OPERATIONS](operations/OPERATING-CONTROLS.md#owner-review-oversight)).

## Provider report and export jobs

Every request AMCP sends has one effect class (`src/effect-class.ts`, RPT-06): `read`, `provider_validation`, `provider_job`, `destructive`, `publish`, `spend_affecting` or `config_write`. `inspect` and `prepare` return it as `effect`. A **provider job** creates a processing object at the provider and uses its quota, but changes no serving configuration or spend: X, TikTok and Meta report jobs, Criteo reports, DV360 SDF exports, TikTok change-log tasks and GA4 report tasks (a GA4 audience export lists people and stays a reviewed write). Each such family declares `effect: 'provider_job'`, and `src/provider-jobs.ts` holds their contracts (admission, lost response, retrieval).

- **The owner's switch (owner decision D18).** `AMCP_PROVIDER_JOBS` is `false` by default (only `true` or `false` is accepted): a job is a reviewed write exactly as before (live writes on, an operator role, the account's write grant). With `true`, a job is allowed while `MIRROR_ALLOW_WRITES=false` and for a reader, on an account with a **report-job grant**, which a workspace administrator gives under Connections → Manage → Report jobs (adding one needs the switch, explicit confirmation and recent sign-in; removing one always works; both are audited as `report_job_access_changed`). While writes are on, an operator's account write grant also allows a job. A read-only deployment with the switch lists `amcp_write` with `inspect`, `prepare`, `execute` and `status`, not annotated read-only. Advertising writes are never opened by the switch or the grant: they keep `LIVE_WRITES_DISABLED`, `CONNECTOR_READ_ONLY` and `WRITE_ACCOUNT_FORBIDDEN`. A job without its authority is refused with `REPORT_JOB_GRANT_REQUIRED` before anything is read.
- **Admission and receipts.** A job family without its own provider quota check (Meta, DV360, Criteo, TikTok change logs, GA4) is admitted against a deployment-wide hourly bound per provider account (`AMCP_PROVIDER_JOB_HOURLY_LIMIT`, default 1000); a full hour is `PROVIDER_JOB_QUOTA` (retryable, nothing claimed or sent). X and TikTok report jobs keep their own admission. Every submitted job leaves a `provider_job` receipt, recorded with the claim before it is sent and keyed by the review: `accepted`, `rejected` or `uncertain`, never resubmitted automatically. Receipts are kept 90 days: settled ones from when they settled, submitting and uncertain ones from when they were created (a provider keeps a job for days to weeks, and its review expired long before), so none is kept without bound; erasing an account removes its workspace’s receipts with it. Owner health counts the last seven days by provider and state (`provider_jobs`).
- **Pause scope.** `pause_writes` takes `pause_scope`: `all` (the default, and every pause saved before scopes existed), `advertising` (advertising writes and media uploads only) or `provider_jobs` (report and export jobs only). `all` and `provider_jobs` also stop the Microsoft report submission of a Reporting overview snapshot, which is a provider job; the snapshot’s other reads continue. `WRITES_PAUSED` names the scope.
- **Microsoft.** The Overview's `SubmitGenerateReport` compiles as a read and is not a reviewed family, but it is a provider job: it is admitted, refused while a pause covers provider jobs, and recorded with a receipt in the report's checkpoint before it is sent (see [reporting](REPORTING-OVERVIEW.md)).
- **Discovery.** `amcp_workspace capabilities` returns `provider_jobs` with its blockers: `provider_jobs_disabled` (writes off and the switch off), `workspace_jobs_paused`, `operator_required`, and `report_job_grant_required` or `account_write_grant_required`.

## Pinned vendor contracts

Every request whose route has a pinned, machine-readable vendor request schema is checked against it before it is sent, field by field at every depth (PRV-05, `src/wire-contracts.ts`): Google Ads (always enforced, as before), Tag Manager, GA4, Search Console and Business Profile (the route's request schema in `generated/vendor-routes.json`, resolved in its pinned Discovery document), Display & Video 360 (the pinned v4 Discovery method of the request's verb and path; uploads excepted) and Microsoft Advertising (the operation's request element in the pinned WSDL model, with JSON arrays and the REST `Type` discriminator). Reddit keeps its OpenAPI check at compile; the parked Criteo routes are unchanged. A pinned document is used only while the SHA-256 of its content matches the digest recorded when it was fetched; otherwise the check reports `unsealed`.

- `AMCP_WIRE_CONTRACTS=shadow` (the default) records a difference without refusing anything: `contract_evidence.wire_contract` of inspect and prepare (`status` `conforms`, `violations`, `unpinned`, `unsealed` or `check_failed`, the contract and its digest, `issues` as field paths and reasons), the `write_prepared` audit entry, and a provider metric of the gateway in owner health: `wire_contract_violations` for writes, `wire_contract_read_violations` for reads (never enforced) and `wire_contract_check_failures` when the validator itself failed. A failed check is never a reason to stop a request outside enforcement: it is recorded with the error class only and the request goes out.
- `AMCP_WIRE_CONTRACTS=enforce` also refuses a reviewed write whose body differs (`INVALID_VENDOR_BODY`, naming `contract`, `vendor_method` and `errors`) at inspect, prepare and execute and again before dispatch, after the family's own refusals; a write whose contract is unsealed, or whose check failed in the validator, is refused with `VENDOR_SCHEMA_UNAVAILABLE` (an enforced write is never sent unchecked). Reads are never refused. `off` skips the check. Any other value stops startup.
- Switch to `enforce` only after `node tools/wire-contract-sweep.mjs` lists no unexplained fixture difference (each reviewed exception in `tests/fixtures/wire-contract-exceptions.json` names its vendor evidence) and 14 days of deployed shadow mode record no `wire_contract_violations` (write violations) and no `wire_contract_check_failures`. `wire_contract_read_violations` does not count against the gate, because reads are never enforced and some are permanent: Discovery documents can over- or under-declare a live API (Search Console's documented filter dimensions are upper case, its examples lower case). Review read violations for a vendor change, not as a blocker. The fixture sweep is a blocking stage of full qualification (`wire_contract_sweep` in `tools/qualify.mjs`). Validation never grants anything.
- Data Manager bodies are built by AMCP from the reviewed people and checked against Google's Data Manager v1 Discovery document, pinned in `.mirror/VENDOR/datamanager-v1.json` (source `https://datamanager.googleapis.com/$discovery/rest?version=v1`, revision 20261007, read 2026-10-11, its SHA-256 recorded in the file and in `generated/vendor-routes.json` `sourceIntegrity`). A difference is refused with `INVALID_VENDOR_BODY` in every mode but `off`, before any personal data is sent, after AMCP's own exact-body check; an edited pin is refused with `VENDOR_SCHEMA_UNAVAILABLE`. `tests/wire-contracts.test.mjs` reads the committed pin (seal, provenance, each route a method of the document, an unknown nested field refused per write), and `tests/google-data-manager.test.mjs` sends the three writes AMCP builds under `enforce`. To refresh: `node tools/fetch-vendor-specs.mjs --refresh datamanager-v1` (a public Discovery GET, no credentials), review the difference and commit both files. The committed pin was read by that public, unauthenticated GET during implementation (2026-10-11), not by the owner: before release the owner runs the refresh and compares the digest with the committed one, or records that such reads were allowed.

Native reads give MCP clients 64-bit integers exactly on every gateway: when a provider response holds an integer literal beyond 2^53 (such as a numeric campaign ID 1800000000000000001), the client receives its exact decimal text instead of the rounded number JSON parsing gives (1800000000000000000, another entity's ID). The scope is MCP callers only (`withExactIntegers` in `server/mcp.ts`): website and API endpoints, report workers and Sheets exports receive the parsed JSON numbers. Every family, evidence, worker and contract check inside AMCP still sees the provider's JSON numbers, so a check that refuses an unsafe numeric identity, or a number where its contract documents a string, still refuses it.

Positive campaign location criteria (`AddCampaignCriterions` / `DeleteCampaignCriterions`, `CriterionType: Targets`) on a paused campaign, read back by ID. Campaign activation (`Status: Active`) reads the campaign's location criteria and is refused with `LOCATION_CRITERIA_REQUIRED` without a positive one (CMP-03, owner decision P7). See [setup and limits](MICROSOFT-ADS.md). |

An action also needs an implemented target-state read. Unsupported contracts return a precise error before mutation egress. [Google Drive media imports](MEDIA-UPLOADS.md) integrate with normal upload actions and `platform_media_upload`; their reviews execute through `amcp_write` or `amcp_media`. Meta/Snapchat creative creation and native Google asset mutations are included. Arbitrary binary transports, batch/tunnel requests, unqualified delegated workflows and other catalog routes remain unavailable for live execution. Catalog presence describes an interface, not live execution qualification.

## Outcomes and recovery

The database claims the exact review immediately before submission. Concurrent execution of the same review cannot send duplicate mutations. Completed outcomes replay without vendor egress; idempotency survives process restart. Mutations are never automatically retried.

Three outcomes follow the claim (owner decision D12). **Not sent:** a refusal raised before the request left AMCP (the owner's pause, an expiry, the spending check or authority re-check at dispatch, the tenant request budget `TENANT_RATE_LIMIT`, a provider cooldown `PLATFORM_RATE_LIMIT`, an open circuit `CIRCUIT_OPEN`, missing credentials, or a lost target lock `STATE_BUSY`) releases the claim and the day's spend reservation in one transaction, journals `not_sent` and audits `write_not_sent` with the code. The error carries `details.submission: "not_sent"`, and the same review executes again once the cause clears, inside its window (an expired one is prepared again). The marker is set synchronously immediately before the fetch, so a request that was sent is never treated as unsent. **Rejected (CMP-04):** once dispatched, a definitive refusal (HTTP 400, 401, 403, 404, 409, 412 or 422 with the provider's parsed error body; never a timeout, rate limit, 5xx or lost response) is `rejected` only when the request's family declares `rejectionIsNonApplied`: Google Ads per-service mutates without `partial_failure` or `validate_only`, and all-or-nothing `googleAds:mutate` builds, where Google documents that operations apply "if and only if they are all valid". The claim is kept as `rejected` (its key is never sent again; a repeat is refused with `WRITE_REJECTED`), the day's spend reservation is released (D12: only for a declared proof), the journal records `rejected` and the audit `write_rejected`; the error carries `details.submission: "rejected"` and `key_retired: true`. TikTok's proof is a closed set of return codes in the body of an HTTP 200 answer that carries no data (`src/tiktok-write-rejection.ts`): a parameter, role, consent or eligibility refusal that TikTok defines applied nothing, so the review is `rejected`, its key is retired and its remedy says TikTok refused a parameter; a throttle (40100, 40132, 40133), a 5xxxx code, a code the set does not name, a TikTok HTTP error status and a lost response stay uncertain. Meta, Snapchat, Microsoft and the other families declare no proof yet, so their refusals stay uncertain. `AMCP_WRITE_REJECTED_OUTCOME=false` restores uncertain for every refusal after dispatch. **Uncertain:** once the request was dispatched, a lost response, a 5xx or any refusal without a proof leaves the claim uncertain and the reservation taken; it is never sent again. **Complete:** the receipt replays. Media uploads follow the same rule: an upload refused before its first request is released and keeps its staged file. `AMCP_WRITE_NOT_SENT_RELEASE=false` restores the earlier always-uncertain outcome. In a campaign plan, a step refused unsent by a pause, a rate limit, an open circuit or a busy target stays `review_ready`, and `run` or `execute_next` continues it once the cause clears; an expired one is prepared again unless its review holds a claim (a write group a part of which was sent), which is only read.

Executes of one target run one at a time. Before the execute state read, the review takes an advisory lock on each record its state reads select (tenant, connection, account and read target, not the projected fields), waits up to 10 seconds (`AMCP_WRITE_TARGET_WAIT_MS`) for another execute of the same target, then reads the state again: a change the other write made is refused as `STATE_CHANGED`, and a wait that runs out is refused as `STATE_BUSY` before anything is claimed. The lock lasts 120 seconds, is renewed at dispatch and is released on success, refusal and uncertain outcomes; a crashed holder's lock lapses on its own. A second execute of the same review that waited replays the first one's receipt. Reviews whose reads only partly overlap are not serialized. `AMCP_WRITE_TARGET_LOCK=false` turns the serialization off.

A `STATE_CHANGED` says what changed and what to do next (Round 2.5, M1). Nothing was claimed or sent, but for a media resume after its claim: its remedy points to the upload's recovery record. Besides the two hashes and `changed_fields`, the details carry `submission: "not_sent"` (nothing claimed), `gateway`, `material` (the changed fields that matter: all of the targets, parents and references, then the account's but known noise such as a balance or a timestamp; at most 20, with `material_total`), `recurring_paths` (paths also changed in the provider's recent refusals; left out when the audit cannot be read) and `next_call` (the call that prepares the same request again, with no creative-edit acknowledgement; a group's is the group's; a plan's review, group or part names the plan's call instead; a media review has none). No flag skips the check, and nothing accepts a changed state or retries on its own. A plan step so refused goes back to `pending` with `prepare_next` as its `next_call`, and `recover_step` can amend it. `run` stops at it (`stopped: "state_changed"`); a later `run` prepares it again and stops with the new review, and only `execute_next` sends it.

`contract_evidence` distinguishes captured catalog metadata, official schemas and live qualification. Inspect/prepare do not infer provider permission from provenance. Its provider contract is 1.3–6.6 KB. With `evidence: "ref"`, inspect and prepare return a reference in its place: the contract's versions, review date, write status and version end, and `full_contract`, the `amcp_tool_help` call whose `data.amcp_contract` (its `result_field`) is the whole contract. The form changes nothing else in the review. `amcp_campaign` prepares its steps with references. Exact read-back retries up to three times on propagation gaps or disagreement; `VERIFICATION_INCONCLUSIVE` retains hashes and changed-field diagnostics and suggests read-only continuation of the original review only while another read can change the answer. When every read of two rounds returns the same differing state, the result is `VERIFICATION_MISMATCH` with a per-field `diff` and the observed `actual_hash`, and no read is suggested; in a campaign plan the user may accept it with `reconcile_step` and `accept_observed: true`. Never use a new mutation key to resolve it. Snapchat creative PUT also requires explicit preservation of existing configuration, including nested defaults; use PATCH for a partial edit instead of accepting accidental resets.

Provider response contracts must positively confirm success. Partial failures, missing operation results, target mismatches and malformed responses cannot be reported as successful writes. Native response details and supported request/created-ID headers are retained. A lost response leaves an uncertain durable claim: reconcile it (below) or inspect the advertising platform before preparing any replacement.

Standalone reviews are retained work (WRT-08). A review prepared directly with `amcp_write` or from the website records its origin (`standalone`; a campaign plan's step and a group's part belong to their plan or group) and appears in Operations as kind `write` (`/operations?write_id=<review_id>`), visible to the credential or person that prepared it and to administrators, and only while the account is still in their access. The feed projects metadata only: action, scope, claim state, read-back status and a not-sent code, never the request body, people, receipts or provider text. States: `unsubmitted`, `not_sent`, `expired` and `uncertain` (a claim still pending after 10 minutes counts as uncertain) need a person; `executing` and `verifying` are active; `complete`, `reconciled`, `verified`, `superseded` are complete; `failed`, `mismatch` and `inconclusive` need attention. Prepare returns `meta.workflow` with the record's path, `expires_at`, the required acknowledgements and an execute `next_call` whose acknowledgements are listed under `add_after_user_approval`, never pre-set. The `write_uncertain` and `write_result_withheld` audit events name the gateway, account and connection, so members with access to the account see them in Activity.

`amcp_write status {review_id}` reads a retained review back with zero provider requests: a redacted summary, the claim (`none`, `claimed`, `uncertain`, `complete`, `not_sent`), the receipt summary, read-back and reconciliation, the review's own state reads as suggested lookups and the one `next_call` that moves it on. It applies execute's actor rules and current account access. An uncertain execute error names this status call. `amcp_write reconcile {review_id}` classifies an uncertain write with read-only reads through the review's connection, guarded like every state read, at least 60 seconds after the claim (`AMCP_WRITE_RECONCILE_DELAY_MS`) and in two consistent rounds: `appears_applied` (every named target holds the request, or a create is found: Google Ads campaigns, budgets, ad groups and asset groups by their frozen names; Meta campaigns, ad sets and ads by name created after the claim), `appears_not_applied` (the reviewed state is unchanged and no target holds it, or no created resource exists) or `indeterminate`. The result is advisory and timestamped, sends nothing and leaves the key uncertain. Within 15 minutes, `accept_applied: true` with the shown `reconciliation_id` records the observed result as the review's receipt (`reconciled: true`, audited `write_reconciled`), so `amcp_campaign verify` and a plan's `reconcile_step` continue; a write found not applied can be replaced by a new review prepared with `supersedes_review_id`, which marks the old one `superseded`. A review that was never sent (unsubmitted, `not_sent` or expired, so it holds no claim) needs no replacement, and naming it there does not fail the prepare: it goes on as it would without the parameter and answers `supersedes_ignored` with the review, `reason: never_sent` and when it expires; the old review is not marked and expires by itself. The same person, gateway, account and connection are required, and a review that holds any other claim is refused as before. The original key is never reset and never sent again. In a campaign plan, an uncertain step's `next_call` is this reconciliation. AMCP does not automatically undo mutations or guarantee a cross-system transaction. State may still change between the final read and the provider accepting a write; no universal provider conditional-write facility exists here.

**An uncertain write is checked automatically (Round 2.5, M2).** A write that ends uncertain has a worker job, `write_reconcile`, that runs the same read-only reconciliation at its claim time plus 60 seconds, as the person who executed the write, and stores the result for `status` and the Operations page: the classification and its reason, which attempt it was, and when it looks again or that its attempts ran out. A claim is watched from the moment it is taken: its job is queued with it for ten minutes later (when a pending claim counts as uncertain), deleted in the transaction that settles the write, and moved up to 60 seconds when the write ends uncertain, so a write whose process died in a deploy or a crash is checked at ten minutes like any other. While the answer is not decisive the job looks again after 2, 5, 10, 20 and 30 minutes (six attempts in all); its reads, like the person's own `reconcile`, are reserved quota, as the read-backs of verification are. A turn whose every read was refused before it was sent (a cooldown, an open circuit, a request budget, a quota) read nothing, so it is no attempt: it looks again at the refusal's `retry_after_ms`. The job's answer never replaces a decisive record that the person wrote while it was reading. It only reads. It never sends or resends a write and never changes the outcome: the person still accepts `appears_applied` (`accept_applied`) or prepares a new review (`supersedes_review_id`). A write the person already accepted or replaced is left alone, and a review that a new one replaced is settled while that replacement stands: it is never reconciled, accepted or replaced again, so the replacement's object is never taken for its own. It stands while the replacement is unexpired, or holds a claim that is not rejected, so a replacement whose claim a refusal before dispatch released (a pause, a rate limit) executes again after the cooldown. If the provider rejected the replacement, or it expired with no claim, the supersede is lifted (audited `write_supersede_lifted`): the old review is reconcilable and acceptable again, and a status, a reconcile or the worker's next check finds an expired one.

**How a lost create is found.** The check reads the provider's own list and never guesses. TikTok campaigns, ad groups and ads, standard and Upgraded Smart+ (each on its own list): the advertiser's list in a creation window around the claim, widened by 14 hours on each side because the zone of the filter is as unconfirmed as that of `create_time`, followed page by page, under the parent the review froze; the Smart+ ad group list takes no creation filter, so the frozen campaign's whole list is read and each row is dated by its `create_time` alone (whether a Smart+ row carries one is unverified: a row without one is a doubt). The standard campaign list also shows Smart+ campaigns, so it is asked for `campaign_automation_type`, and a same-name row of another type is a doubt to either create; a standard and a Smart+ create of one name hold each other's objects. Meta campaigns, ad sets and ads: by name, parent and creation time; product sets and feeds: new since the review froze the catalog's, within 15 minutes of the claim; audiences: by `time_created`; catalogs and creatives: never found, only shown, because nothing dates them (a creative whose name has a date and a hash added still counts as a doubt). Google Ads builds and named creates (campaigns, budgets, ad groups and asset groups): by name and parent, removed objects left out, a search cut at its limit never taken as whole, and only an object that did not exist when the review was prepared is this write's: the review freezes the live objects of the frozen names under the frozen parents, because Google refuses a duplicate name and an older object is exactly why such a create fails. Where that list could not be read whole, every match is a doubt. A match counts only when the fields the review froze agree, and never when another create of the same kind already holds that object (its receipt names it). One match in a whole list is `appears_applied`; none in a whole list is `appears_not_applied`; two matches, an object that cannot be dated or that differs in a frozen field and was made in the window, an unreadable time, or a list that is not whole is `indeterminate`, with the doubtful objects shown. Absence is never answered from a cut or incomplete read.

**A create is not made twice.** A prepare of a create identical to one that is uncertain, or still being sent, is refused (`DUPLICATE_OF_UNCERTAIN_WRITE`) with the earlier review and the call that settles it. Execute checks again in the transaction that takes the claim, so two identical prepared creates never both send, and refuses one whose twin completed after it was prepared (`DUPLICATE_OF_COMPLETED_WRITE`) unless it carries the warning that a prepare gives for an identical create that completed in the last ten minutes. A create accepted as applied counts from the acceptance, not from when it was sent, so an uncertain create settled long after it was sent still warns for ten minutes. The warning covers the identical creates it named: a warned review is refused again if another identical create completed since. Identical means the same gateway, account, action, method, path, query and body, without a request ID or session (a caller's own request ID does not make two creates different). A create that looks for the same object as an unresolved one (the same kind, parent and name as its lookup compares them) is held back too, whatever its other fields, because the lookup could not tell what each made. For a create AMCP cannot look up (Snapchat, X, LinkedIn, Microsoft, Reddit, Smart+), reads can never settle the earlier review: the refusal says so (`details.earlier_checkable: false`), the person checks the provider, and a changed request, its name for example, is a new create. A colleague's unresolved create is replaced only by the person who prepared it, and the workspace owner can accept it if it was applied. In a plan, such a refusal at execute sends the step back to pending with `prepare_next` (a run stops there and shows the new review, with its warning, and sends it only when run is called again after that stop); while the earlier create is still being sent, the review stays ready and waits. A step held back at prepare is held the same way, pending and never failed: its `next_call` is the earlier create's call with `prepare_next` after it (`prepare_next` alone where the earlier create is a colleague's, with no call of theirs to name, and `prepare_next` with a wait, `retry_after_ms`, where it is still being sent), and `details.earlier_plan_id` and `details.earlier_step_id` name the plan and step that hold the earlier create when the reader may read that plan. A held step whose earlier create is the actor's own, and whose reconciliation (under fifteen minutes old) found it not applied, is prepared as that create's replacement by its next `prepare_next`: its review seals the earlier one (`superseded`), which is never sent, and a run stops at that review before anything is sent. A colleague's create is replaced where it was prepared. A run also stops once at any ready review that carries that warning (`needs_attention`, the review in `review`, nothing sent) and records on the step that it was shown (`duplicate_warning_shown_at`); a run called again after the stop, and `execute_next`, send it. The stop is once per review, whoever calls next, and it is recorded before its answer is delivered, so a run retried after a lost answer sends the review. Amending a held step needs a real change: `recover_step` with nothing changed is refused (`INVALID_ARGUMENT`), because it would lift the hold while the plan approval stands. Journey J14 in `tests/journeys` measures the recovery of a lost create: a `reconcile` and a `status` call.

Protect the SQLite volume and backups: they retain account information, review payloads, redacted outcomes and audit records. Keep the encryption key separately. Restoration of an older backup may lose recent submission claims; reconcile platform state before resuming writes after a restore.

## Verification boundary

Automated tests cover native campaign CRUD requests for all six primary platforms and DV360, response validation, expired/stale reviews, tenant/user binding, grants, paused creation, duplicate submissions, lost responses, credential revocation and restart persistence using synthetic provider responses. The container CI workflow exercises both runtime modes. New tests exercise all four measurement/Apple providers with synthetic state and responses, including every enabled Tag Manager action, required scopes, native fingerprints, optional target absence and cross-resource rejection. Live mutations were not executed against user advertising accounts during development. Production OAuth, app approvals and live endpoint qualification remain external acceptance work.

Account write grants apply to campaigns, ad sets, ads, creatives and media equally. `WRITE_ACCOUNT_FORBIDDEN` reports the chosen connection ID and the selected account, plus whether other connections for that account have write grants. Set `connection_id` explicitly when selecting a different login; AMCP never silently chooses a more privileged one. Workspace context and account listings expose the same grant status. New connections default to reviewed write access when enabled; existing reader grants are preserved. A token, AI client or member limited to a client access set (SEC-08) reaches only that set's accounts: a review, dry run or write naming any other account is refused with `ACCOUNT_SCOPE_RESTRICTED` before anything is prepared, a set never grants writes, and its `WRITE_ACCOUNT_FORBIDDEN` lists only the set's own connections for the account, never a login it would be refused ([clients in one workspace](USER-ACCOUNTS.md#clients-in-one-workspace-working-client-and-client-access-sets)).

## Google targeting and exclusion lists

Reviewed execution now supports five Google Ads native mutate endpoints: campaignCriteria, adGroupCriteria, sharedSets, sharedCriteria and campaignSharedSets. Discover their exact actions through the Google gateway. Each call remains homogeneous and uses the normal prepare/execute review, explicit confirmation and spend_change_confirmed; a negative-only create (exclusions only) narrows delivery and needs no spend_change_confirmed, and neither does a positive criterion created under a campaign or ad group that the review reads as PAUSED (the Google Ads rule above), while removals, updates, other positive criteria and list attachments still do. Under allow_activation:false, removing an exclusion counts as activation. Exclusions do not need a fabricated status.

Qualified criteria include positive/negative ad-group keywords, negative campaign keywords, locations, languages, devices, schedules, demographic exclusions, topics, existing user lists/audiences and placement exclusions where the native criterion type supports them. Shared lists use NEGATIVE_KEYWORDS or NEGATIVE_PLACEMENTS; list members must match the enabled parent list type. Criterion identity, parent and negative flag cannot be changed through an update mask: remove and recreate instead. Shared-set updates change name; shared criteria and campaign/list links support create/remove only.

Updates/removes read exact resource names and mutable configuration, including keyword bid micros. Creation reads the exact campaign/ad group/shared list and any referenced user-list/audience. Preparation and execution reuse those frozen GAQL reads. Composite criterion names must contain their native parent~criterion IDs; all customer-qualified references must belong to the selected customer. Budgets/bids retain native micros as decimal strings. Arbitrary new audiences, customer-match ingestion, all criterion variants and channel combinations are not qualified by this addition.
