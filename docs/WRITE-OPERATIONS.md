# Reviewed write operations

AMCP supports explicitly reviewed campaign-management mutations. The existing native gateways still provide reads and local dry runs. The additional `amcp_write` tool handles live execution when enabled. This extension is independently designed; it does not establish complete behavioral equivalence with AMCP.

## Enable access

1. In Railway variables, set `MIRROR_ALLOW_WRITES=true` and redeploy. Preserve `MIRROR_MASTER_KEY` and the persistent `/data` volume. Set the target port to the effective Railway `PORT` (**8080** in the current Railway service; local development defaults to 4317). `/healthz` reports the effective `live_writes` flag.
2. Sign in to Connections. Connect or reconnect each provider with the required app permissions. New Meta authorizations request `ads_management`; LinkedIn requests `rw_ads`; X requests write access. Existing provider tokens are not upgraded by changing an environment variable. Explicit `AMCP_<PROVIDER>_SCOPES` overrides take precedence, including an empty override.
3. Select the accounts available to the connection. New logins default to read plus reviewed write access when deployment write support is enabled. The selection screen offers an explicit read-only choice and per-account grant controls. Existing logins and manually revoked grants retain their access. Write grants are always a subset of selected accounts; deselection removes them.
4. On Connectors, create the default **read + write** operator token and confirm its access, or choose a read-only token. New OAuth clients that omit scope default to `mcp:read mcp:write`; the authorization page still requires consent by a workspace member, who may choose read-only access instead; a viewer's consent grants `mcp:read` only. Explicit `mcp:read` requests and existing reader registrations stay read-only. Refresh cannot increase scope, also inside the refresh reuse window.

For local stdio, `MIRROR_ALLOW_WRITES=true` defaults the role to operator; explicit `MIRROR_ROLE=reader` keeps read-only access. Provide the encryption key and provision the connection's `writeAccounts` subset using the administrator CLI. HTTP role selection always comes from the authenticated connector, never client-supplied tool arguments. An explicit deployment setting of `MIRROR_ALLOW_WRITES=false` disables all live writes.

Provider permissions, account roles, app review and API access remain necessary. Broad provider permissions do not override AMCP's account grants. Stop future submissions by revoking the connector, removing account write grants, or disabling write support. Revocation is checked again after asynchronous state reads and credential refresh. Requests already received by a provider cannot be recalled.

## Inspect, prepare, review, execute

For an unfamiliar non-media operation, call `amcp_write` with `action: inspect`, `gateway` and the native `arguments`. This checks local execution-contract support, reports its state-read paths and makes no credential or network access. It does not verify live permissions or create a review. Its `account_capability.write_granted` compares the account the way enforcement does (Google dashes and the Meta `act_` prefix are normalized). Media imports use their media preparation flow.

Who may change anything is checked first (MCP-09). A native gateway call of a write action with `dry_run:false` is refused before any execution check with `WRITE_REVIEW_REQUIRED`, whose `details.next_call` is the `amcp_write inspect` call for the same arguments (without `dry_run`, `confirmed` and `idempotency_key`); delegated gateways keep their `operation`. A read-only deployment lists `amcp_write` with `inspect` only (owner decision D15) and refuses `prepare` and `execute` with `LIVE_WRITES_DISABLED` before the payload is checked; the message names no operator setting. A caller authorized to read only (an AI client granted `mcp:read`, or a workspace viewer) gets `CONNECTOR_READ_ONLY` (HTTP 403) with `granted_scope` and `required_scope`, also before the payload is checked; it may still inspect. Workflow mutations through `amcp_native_action` (`update_entities`, `set_entity_status` and the like) are refused the same way, with the inspect call of their compiled native request. When ownership of a Meta object is not established, a typed action (campaign, ad set, ad, creative or custom audience) gets its one account list read as `details.next_call`; a bare ID of unknown type lists every candidate read in `details.ownership_reads`. `AMBIGUOUS_CONNECTION` names its `candidates` (connection ID, label, default flag; labels are marked untrusted) and a `list_accounts` `next_call`.

Call `amcp_write` with a normal native gateway request. This example uses a synthetic account ID; replace it with an explicitly granted account.

```json
{
  "action": "prepare",
  "gateway": "meta_native_action",
  "arguments": {
    "action": "meta_campaign_create",
    "account_id": "123",
    "payload": {
      "name": "Reviewed draft",
      "status": "PAUSED",
      "objective": "OUTCOME_TRAFFIC",
      "special_ad_categories": [],
      "is_adset_budget_sharing_enabled": false
    }
  }
}
```

From Graph API v24.0 (including the `AMCP_META_API_VERSION=v25.0` rollback) a Meta campaign create without a campaign budget (`daily_budget` or `lifetime_budget`) must carry `is_adset_budget_sharing_enabled` as a boolean; Meta refuses it otherwise (error 4834011). AMCP refuses it first with `INVALID_META_CAMPAIGN` (`fields: ["is_adset_budget_sharing_enabled"]`), before any read or provider request. `false` keeps each ad set on its own budget, as before v24.0, and is not a spending field; `true` lets Meta move budget between the campaign's ad sets and needs `spend_change_confirmed`. AMCP never adds the field to a request you write; the guided Meta recipes send `false` because each has one ad set. A saved plan step without it fails preflight and is corrected with `amcp_campaign recover_step` and corrected `arguments`.

Preparation performs provider reads and returns `executed:false`, the frozen native request, its before-state, `state_hash`, `state_reads`, expiry, `review_id` and `idempotency_key`. `summary` is a server-authored line above it (`text`, `operation`, `entity`, `count`, `account` with the name and currency when the review read them, `money` and `status`): amounts are converted to account currency through the budget-unit contract with exact decimals only where the platform's unit is documented and the field names it (`micros`), and are otherwise left native; a status change names the target's current status. The frozen request stays the authority. The website counts down to `expires_at`, disables Execute at zero and offers Prepare again, which reads the state again and creates a new review; in a plan, a step prepared again for the same request over unchanged state carries `unchanged_since_review` with the expired review's id, and the website says the same of a review it prepares again when the new review's `fingerprint` and `state_hash` equal the expired one's. A summary lists at most 10 money and 10 status entries (`money_total`, `status_total` count the rest). Inspect the account, resources and payload. No mutation is submitted during preparation. `dry_run:true` on the original gateway is an entirely local preview and does not produce a write review.

Prepare and execute reuse the stored read plans. Raw responses are checked for provider errors, completeness and exact resource identity before projecting configuration. Google snapshots retain only `results`, excluding `queryResourceConsumption`, field masks and other envelope metadata. TikTok retains `data.list`; X/Reddit retain `data`; Microsoft retains the contract's named entity result; Apple retains `result`; Snapchat retains the requested resource records. A nonempty pagination continuation still blocks execution before projection. Flat resource responses retain unknown configuration fields; Search Console sitemap crawl/processing observations are excluded while submission identity and `lastSubmitted` remain protected. Media account reviews use the same projection.

Object keys and explicitly qualified scalar sets are normalized; unknown/ordered arrays, duplicate members and scalar types remain meaningful. Google GAQL resource rows are sorted by their validated identities, without sorting arrays inside a resource indiscriminately. Delivery telemetry, server timestamps and stats/pacing telemetry are excluded; mutable status, budgets, schedules, targeting, bids, pacing, native fingerprints and unknown resource configuration remain protected. `STATE_CHANGED` includes `expected_state_hash`, `actual_state_hash` and JSON paths in `changed_fields`; the request `fingerprint` remains a separate hash of the frozen request. Still-valid older, unsubmitted review envelopes are reprojected using their frozen read plans. Their normalized state hash may differ from the pre-upgrade value, but request fingerprints, expiry, confirmations, grants and original idempotency claims are unchanged. Completed writes replay their original receipt; uncertain claims are never reset.

See the [state-projection repair and platform coverage report](implementation/STATE-PROJECTION-2026-09-18.md) for reproductions, compatibility details and verification limits.

Submit the same review only after confirming its intended change:

```json
{
  "action": "execute",
  "review_id": "COPY_FROM_PREPARE",
  "idempotency_key": "COPY_FROM_PREPARE",
  "confirmed": true
}
```

Budget, bid, spend or activation changes additionally require `spend_change_confirmed:true`. New serving entities must explicitly be paused or draft.

`prepare` returns `execute_requirements` — `{confirmed, idempotency_key, spend_change_confirmed, creative_edit_confirmed, reasons[]}` — decided by the same rules execute applies, so a client asks the user once instead of discovering a missing flag from a refused execute, and `expires_in_seconds`. Execute still re-checks everything. The spending acknowledgement is decided structurally as well as by field names (`src/spend-effects.ts`):

- An edit of an existing campaign, campaign group, insertion order, ad set, ad group, ad squad or line item in the generic Google Ads, Meta, TikTok, LinkedIn, X, DV360 and Snapchat families needs `spend_change_confirmed` unless every field it changes is the name, an identifier, or a status that pauses, archives or removes. Bid targets (`targetCpaMicros`, `targetRoas`, LinkedIn `unitCost`), pacing (DV360 `pacing`), schedules, targeting and optimization goals therefore need it; the refusal lists the fields. Ads, creatives and assets are content: their activation is still checked, and creative edits keep their own impact disclosure. A Snapchat creative edit's `creative_impact` lists the ads that use the creative (`affected_ad_ids`, `affected_ads` with id, name, status and ad squad) from a read of the account's ads collection of at most 25 pages of 1,000, made through the review's guarded reader and not part of its frozen state; past the bound, or when that provider read fails, the list is `null` with `incomplete: true`. `affected_ad_ids` names every matching ad, while `affected_ads` details at most the first 100 (`affected_ad_count` is the total and `listed_truncated: true` says some are not detailed).
- A status given as a number (ProtoJSON enum numbers such as Google Ads `status: 2`, which is ENABLED) cannot be shown to leave an entity paused: it needs `spend_change_confirmed`, counts as activation under `allow_activation:false`, and reviewed Google Ads mutations refuse numeric enum values outright (`INVALID_VENDOR_BODY`).
- A request that deletes or removes, publishes live (a Tag Manager version publish, a Search Console sitemap submission, a Business Profile place action link) or stops delivery (a status that pauses, archives or removes a campaign, ad set, ad group, ad squad or line item that is not already in it; TikTok `DISABLE`) is disclosed at prepare: `effects: {destructive, irreversible, publishes_live, stops_delivery}` in the response and in `execute_requirements`, one `reasons` entry per effect (`effect`, the target's id, name and current status from the before-state; a request for several entities is named by their count instead), and a `user_approval` that names the effects. Deleting an entity that is already paused, archived or removed does not claim to stop delivery. It adds no flag and refuses nothing (`allow_deletion` stays the owner's control); other writes are unchanged. A group combines its parts' effects. In a plan, `prepare_next` repeats the effect reasons in `next_call.disclose`, and the whole-plan approval lists the steps whose arguments delete, remove or publish. A family may decide the publish effect itself (`publishes` hook).
- `amcp_campaign` never pre-fills `spend_change_confirmed` in its suggested `next_call`. When the step needs it, the response carries `execute_requirements` and `next_call.add_after_user_approval`; add those flags only after the user approves the reviewed change.
- `amcp_campaign` responses are compact and at most 12 KB whatever the number of steps: the plan header, one row per step with its resource IDs, verification status and error code, the step the call acted on (`current`, with its receipt and verification) and `next_call`. `prepare_next` shows the review's request, state hash, a summary of each state read and the spend policy, not the raw before-state. `get` with `step_id` returns one step whole and `get` with `detail: "full"` the whole stored plan; nothing stored changed.
- A whole-plan approval (`amcp_campaign approve`) counts every budget, bid and status field of every step (`fields_total`). A step with more than 24 is aggregated (`truncated: true`): one row per field pattern with `count`, `distinct_count`, up to five `values` and, for money, `min` and `max` as sent; `approve` with that `step_id` lists every field. Steps that delete, remove or publish carry `effects`, repeated in `next_call.disclose`. `approve` with `confirmed: true` needs the summary's `summary_hash` as well as its `plan_hash` (`PLAN_CHANGED` otherwise); approvals recorded earlier stay valid until their 24-hour expiry, and `AMCP_PLAN_SUMMARY_HASH=false` accepts `plan_hash` alone. The website keeps Save plan approval disabled until every truncated step's complete list was opened.
- A Google Ads mutation or Snapchat entity batch of more than 25 records (at most 1,000) is prepared as one review with `group: true` and `parts` of 25. Each part is an ordinary review with its own state reads, state hash, idempotency key, spending check and read-back; the group is approved and executed once. The owner's spending caps count the parts together, in order, as one change: the group's `spend_policy` and `execute_requirements` name a cap only the whole group crosses (`cap_override_confirmed`), and under `block` such a group is refused at prepare. `time_budget` gives the seconds each part needs (twice the slowest part's preparation, at least 3, or `AMCP_WRITE_GROUP_PART_SECONDS`) and `execute_by`, which is also the group's `expires_at`: the last moment at which every part still has that much of its own window when its turn comes. A group that cannot fit one window is refused at prepare (`WRITE_GROUP_TOO_LONG`). Before the first part is sent, execute checks every part (the owner's pause, access and grants, the acknowledgements, the caps for all parts together and the time budget); a refusal there sends and claims nothing. It then sends the parts in order and stops at the first that does not succeed: `WRITE_OUTCOME_UNCERTAIN` when that part was sent, `WRITE_PARTIAL_OR_FAILED` when earlier parts were applied and it was refused before sending. A partial stop lists `not_sent`; when the stopped part was not sent it also carries `part_submitted: false`, the remedy of the part's own cause (a pause, a policy, an expiry) and `next_call` with `not_sent_parts`, to send each part not sent as its own review once the cause is resolved. A stopped group is never run again; a completed one replays its receipt. `amcp_campaign verify` with the group's `review_id` reads every part back. Operations that link through temporary IDs are not split.
- `idempotency_key` is optional at execute (in `amcp_write`, `amcp_media` and `amcp_campaign execute_next`): it is the review id, and a key that differs from it is still refused.
- `amcp_campaign create`, `create_from_recipe` and `clone` take an optional creation `idempotency_key`: the same key and input returns the original draft (a keyed clone retry reads nothing), and other input under that key is refused with `IDEMPOTENCY_CONFLICT`. The website sends one key per exact recipe brief or clone request. Recipe and clone steps are saved literally; `{{variable}}` substitution applies only to the explicit and template steps of `create`.
- `amcp_campaign run` resumes a step a crash or restart left `executing` under its original review, key and plan approval: a completed receipt is replayed, a pending or uncertain claim marks the step `uncertain` and stops the plan without sending again, and a claim never made is sent once while its review is valid. It asks for a person for the same acknowledgements as any other step.
- An expired review (`REVIEW_EXPIRED`) was refused before anything was submitted. The error carries `details.next_call`, which prepares the same request again. Ownership bindings from account-scoped reads also last five minutes, so the re-preparation may first need that read again (`RESOURCE_SCOPE_REQUIRED`). In a campaign plan the step returns to `pending` and `prepare_next` prepares it again.
- Campaign plans, uploads, retained originals and media variants follow the person (MCP-02, owner decision D16 (4)): a website account and every AI client and connector token it authorized share them, and the administrator's password sign-in shares them with the clients and tokens approved from it. Reviews and plan approvals stay with the connection (credential) that prepared or recorded them. Another connection of the same person sees and continues the plan, but `prepare_next` and `execute_next` refuse a live review it did not prepare with `REVIEW_HELD_ELSEWHERE` before the plan changes; after `details.review_expires_at`, `details.next_call` prepares a review of its own. `run` needs an approval recorded by the same connection (`APPROVAL_REQUIRED`). Another member's client is refused unless the plan's owner (or an administrator) named that member a collaborator (`amcp_campaign assign`, CMP-05): a viewer reads the plan, an editor prepares, executes, amends and archives it, and an approver approves and runs it, each within their current account access and under their own account grant and review binding; administrators keep their exemption. With the owner's `require_distinct_approver` policy, a plan that changes spending or activates a launch is approved by someone other than its owner (`DISTINCT_APPROVER_REQUIRED`).
- Execute-time confirmation refusals (`SPEND_CONFIRMATION_REQUIRED`, `CREATIVE_EDIT_CONFIRMATION_REQUIRED`, `CONFIRMATION_REQUIRED`) keep the review valid: call execute again with the named flag after the user approves; do not prepare again.
- In enhanced mode, `native_request` is a read-only extension: `amcp_write` refuses it (`WRITE_CONTRACT_UNAVAILABLE`), because it lets a caller choose the action and the path independently. Execute cannot replace the request, account or connection. Reviews expire after five minutes and belong to the same tenant and user that prepared them. Changed, incomplete, paginated or missing state prevents submission. Successful Meta and Snapchat creates register their returned resource IDs to the owning tenant, connection and selected account, immediately allowing child prepares. Other global resources require an account-scoped collection read or an administrator binding. Existing ownership expiry and revocation rules remain enforced.

An owner spending policy separates creates from updates, because `max_budget_increase_percent` and the unambiguous-baseline rule only mean something against a prior budget. A create is recognised from an explicit REST.li `CREATE`, a `create` operation inside the payload, or a collection-scoped action name. A REST.li POST addressed to one resource — `…_{id}_post` or `…_{urn}_post`, which is how LinkedIn expresses `PARTIAL_UPDATE` — changes an existing budget and stays under the percentage and baseline rules. `max_budget_native` and `max_daily_increase_native` apply to both. Reddit campaign and ad group `goal_value` is a budget in microcurrency (pinned Reddit Ads API v3); an update that omits `goal_type` is compared with the reviewed entity's current goal of the same type.

Every money amount of a request for a capped account is either compared with a cap or reported as unsupported; a measurable amount is never dropped. A field the policy cannot measure (a cap cleared to null or zero, a removed cap, a field with no unit mapping) becomes one `POLICY_AMOUNT_UNSUPPORTED` finding beside the budget, increase, daily and bid checks of the other amounts, and the confirmed increase is still reserved. The Google Ads bid cap covers every writable bid of the pinned API version, generated from its Discovery document into `generated/google-bid-fields.json` by `npm run generate:bids` (CPC bid ceilings and floors, target CPC, CPM and CPV, fixed CPM, category bids); ratios are excluded, and `npm run generate:bids:check` fails when a newly pinned version adds an unclassified money field. Lifetime and custom-period totals (Meta and Reddit campaign `spend_cap`, Google `total_amount_micros`, other lifetime budgets) answer to `max_total_budget_native` (or `max_total_budget_currency`) when the owner sets one, otherwise to `max_budget_native`, and lowering one from its single current value is always allowed. During the rollout, `AMCP_SPEND_POLICY_UNSUPPORTED=abort` restores the earlier evaluator, in which the first unmeasurable field replaced the other findings.

A save replaces the stored policy, so it is checked against the revision the caller read (owner decision D9): `save_spend_policy` takes `expected_revision` (0 when there was no policy) and refuses a stale one with `REVISION_CONFLICT` (409), saving nothing; the response returns the new `revision`. The website always sends it. It shows the stored policy of the selected account (matched through `spend_policy_bindings` in owner health, the server's normalized policy key), keeps the settings and platform caps of the workspace default that its form does not show, and asks before a save that weakens a policy, naming each weakening: a removed or raised cap, `block` to `confirm`, activation or deletion newly allowed. A first account policy is compared with the workspace default it replaces for that account. MCP callers may omit `expected_revision`; a save that then replaced a stored policy returns a `REVISION_NOT_CHECKED` warning. Each `spend_policy_saved` audit event records the revision and whether it was checked.

A policy can be attached to one (gateway, account) pair or set once for the workspace with `scope: "workspace"`. The account-specific policy wins where one exists; otherwise the workspace default applies, so an account nobody configured individually is still protected. Each account keeps its own daily allowance under a shared default. `prepare` reports which applied as `spend_policy.scope`, and reports `configured:false` with `unprotected:true` when nothing protects the account. `amcp_workspace health` lists those accounts under `unprotected_accounts`.

The owner's health view (`amcp_workspace health`, website Settings) also reads two things back from the audit, over the last 30 days. `cap_overrides`: how many reviews were executed beyond a cap with `cap_override_confirmed` under `confirm` (one per review), and the latest 20 with the account, the rules exceeded, who executed them and their role, and the review id. `review_friction`: prepares and executes, prepare-to-execute latency (nearest-rank p50, p90, p99), and the counts and rates per 100 prepares of `REVIEW_EXPIRED`, `STATE_CHANGED` (with the ten most frequent `changed_fields` paths), acknowledgement refusals (`CONFIRMATION_REQUIRED`, `SPEND_`, `CAP_`, `CREATIVE_EDIT_CONFIRMATION_REQUIRED`), `WRITE_OUTCOME_UNCERTAIN` and `write_not_sent` by code. It holds codes, counts and field paths, never values, reads at most 50,000 audit rows (`complete: false` beyond), and is the baseline the five-minute review window is kept against until it has been measured.

`allow_activation:false` is enforced against the payload structure using a per-gateway declaration of the field and values each provider uses to start delivery — Meta `status:ACTIVE`, Google Ads `status:ENABLED`, TikTok `operation_status:ENABLE`, X `entity_status:ACTIVE`, DV360 `entityStatus:ENTITY_STATUS_ACTIVE`, Reddit `configured_status:ACTIVE`, Microsoft `Status:Active`. JSON Patch operations are resolved by their `path` and `value` in either key order. Measurement gateways declare no serving-activation surface and are not constrained by it. A gateway with no declaration is refused outright while activation is forbidden, so adding a provider without declaring its vocabulary fails closed.

`allow_deletion:false` refuses every write that deletes, at prepare and again at execute against the re-read state, before anything is sent (`POLICY_DELETION_FORBIDDEN`, with the body `field` when a value carried the deletion). Besides DELETE methods, family hooks and Google `remove` operations, a deletion carried as a body value on an update route counts: TikTok `operation_status:DELETE` on `/v1.3/{campaign|adgroup|ad}/status/update/` (the `tiktok_entity_status` family, which also lists the ad groups and ads a DELETE takes with it and refuses `allow_partial_success:true`), Meta `status:DELETED`, Google `status:REMOVED` and `REMOVE` proposals and operators, Reddit `configured_status:DELETED`, DV360 `ENTITY_STATUS_SCHEDULED_FOR_DELETION`, LinkedIn `PENDING_DELETION`, and Microsoft `Status:Deleted` or `Action:Delete` (`bodyDeletionValues` in `src/execution-risk.ts`). It also governs deletion through a Meta product feed (owner decision D8, judged on the feed's current state): a feed DELETE, a create or update that sets `deletion_enabled:true`, and a change of the `schedule` URL, interval or interval count of a feed whose deletion is on, since its next fetch removes every product the new file lacks; a name, hour or `update_schedule` change is not a deletion. `tests/deletion-policy-coverage.test.mjs` sweeps every pinned provider document for deletion values a request body can carry and every reviewed write route, and fails until a new value is classified or exempted with a reason. A saved, unsent TikTok DELETE or feed review is refused at execute once the policy forbids deletion.

The daily window is the UTC calendar day, and the cap counts requested positive budget increases rather than billed spend. A reservation taken for a write that then fails after it was sent is deliberately not released: a transport failure may still have reached the provider, and releasing it would let repeated failures walk past the cap. Only a refusal raised before the request left AMCP releases it (see [Outcomes and recovery](#outcomes-and-recovery)).

## Provider validation

Provider validation asks the provider to check a mutation without applying it: Google Ads `validate_only` on a mutate request, and Meta `execution_options: ["validate_only"]` on a campaign or ad set create or edit. It is a separate effect from a reviewed write: a remote call that applies nothing but uses write permission and API quota. It never creates a review, an idempotency claim or a spend reservation, and it never permits execute.

- `amcp_campaign validate_provider` runs it on its own. It needs `MIRROR_ALLOW_WRITES=true`, or, in a read-only deployment, the deployment owner's explicit opt-in `AMCP_PROVIDER_VALIDATION=true` (owner decision D18); otherwise it is refused with `LIVE_WRITES_DISABLED` before any credential or network access. It always needs the account's write grant (`WRITE_ACCOUNT_FORBIDDEN`). `provider_validation_started` is audited before the request is sent, then `provider_validated` (with a receipt, `executed: false`) or `provider_validation_failed` with `PROVIDER_VALIDATION_FAILED` and the provider's `field_paths`. A lost reply is `UPSTREAM_UNAVAILABLE` with `validation_only: true`: nothing changed.
- `amcp_write prepare` with `provider_check: true` validates the reviewed request at prepare, through the review's connection and authority checks (writes must be enabled). The result is the review's `provider_check` (`provider_validated` or `provider_rejected` with `field_paths`). A rejected review cannot be executed (`PROVIDER_VALIDATION_FAILED`); prepare it again once corrected. Execute still reads the state again. `inspect` reports `provider_check_available`.
- Reviewed writes refuse validation modes: Google `validateOnly`, and Meta `execution_options` containing `validate_only` or `include_recommendations` (`WRITE_CONTRACT_UNAVAILABLE`), because a reviewed write applies its request and would otherwise be receipted as an applied change. Other Meta `execution_options` values are unaffected.

Arbitrary binary transports, batch/tunnel requests, unqualified delegated workflows and other catalog routes remain unavailable for live execution. Catalog presence describes an interface, not live execution qualification.

## Outcomes and recovery

The database claims the exact review immediately before submission. Concurrent execution of the same review cannot send duplicate mutations. Completed outcomes replay without vendor egress; idempotency survives process restart. Mutations are never automatically retried.

Three outcomes follow the claim (owner decision D12). **Not sent:** a refusal raised before the request left AMCP (the owner's pause, an expiry, the spending check or authority re-check at dispatch, the tenant request budget `TENANT_RATE_LIMIT`, a provider cooldown `PLATFORM_RATE_LIMIT`, an open circuit `CIRCUIT_OPEN`, missing credentials, or a lost target lock `STATE_BUSY`) releases the claim and the day's spend reservation in one transaction, journals `not_sent` and audits `write_not_sent` with the code. The error carries `details.submission: "not_sent"`, and the same review executes again once the cause clears, inside its window (an expired one is prepared again). The marker is set synchronously immediately before the fetch, so a request that was sent is never treated as unsent. **Rejected (CMP-04):** once dispatched, a definitive refusal (HTTP 400, 401, 403, 404, 409, 412 or 422 with the provider's parsed error body; never a timeout, rate limit, 5xx or lost response) is `rejected` only when the request's family declares `rejectionIsNonApplied`: Google Ads per-service mutates without `partial_failure` or `validate_only`, and all-or-nothing `googleAds:mutate` builds, where Google documents that operations apply "if and only if they are all valid". The claim is kept as `rejected` (its key is never sent again; a repeat is refused with `WRITE_REJECTED`), the day's spend reservation is released (D12: only for a declared proof), the journal records `rejected` and the audit `write_rejected`; the error carries `details.submission: "rejected"` and `key_retired: true`. Meta, Snapchat, Microsoft and other families declare no proof yet, so their refusals stay uncertain. `AMCP_WRITE_REJECTED_OUTCOME=false` restores uncertain for every refusal after dispatch. **Uncertain:** once the request was dispatched, a lost response, a 5xx or any refusal without a proof leaves the claim uncertain and the reservation taken; it is never sent again. **Complete:** the receipt replays. Media uploads follow the same rule: an upload refused before its first request is released and keeps its staged file. `AMCP_WRITE_NOT_SENT_RELEASE=false` restores the earlier always-uncertain outcome. In a campaign plan, a step refused unsent by a pause, a rate limit, an open circuit or a busy target stays `review_ready`, and `run` or `execute_next` continues it once the cause clears; an expired one is prepared again.

Executes of one target run one at a time. Before the execute state read, the review takes an advisory lock on each record its state reads select (tenant, connection, account and read target, not the projected fields), waits up to 10 seconds (`AMCP_WRITE_TARGET_WAIT_MS`) for another execute of the same target, then reads the state again: a change the other write made is refused as `STATE_CHANGED`, and a wait that runs out is refused as `STATE_BUSY` before anything is claimed. The lock lasts 120 seconds, is renewed at dispatch and is released on success, refusal and uncertain outcomes; a crashed holder's lock lapses on its own. A second execute of the same review that waited replays the first one's receipt. Reviews whose reads only partly overlap are not serialized. `AMCP_WRITE_TARGET_LOCK=false` turns the serialization off.

`contract_evidence` distinguishes captured catalog metadata, official schemas and live qualification. Inspect/prepare do not infer provider permission from provenance. Its provider contract is 1.3–6.6 KB. With `evidence: "ref"`, inspect and prepare return a reference in its place: the contract's versions, review date, write status and version end, and `full_contract`, the `amcp_tool_help` call whose `data.amcp_contract` (its `result_field`) is the whole contract. The form changes nothing else in the review. `amcp_campaign` prepares its steps with references. Exact read-back retries up to three times on propagation gaps or disagreement; `VERIFICATION_INCONCLUSIVE` retains hashes and changed-field diagnostics and suggests read-only continuation of the original review only while another read can change the answer. When every read of two rounds returns the same differing state, the result is `VERIFICATION_MISMATCH` with a per-field `diff` and the observed `actual_hash`, and no read is suggested; in a campaign plan the user may accept it with `reconcile_step` and `accept_observed: true`. Never use a new mutation key to resolve it. Snapchat creative PUT also requires explicit preservation of existing configuration, including nested defaults; use PATCH for a partial edit instead of accepting accidental resets.

Provider response contracts must positively confirm success. Partial failures, missing operation results, target mismatches and malformed responses cannot be reported as successful writes. Native response details and supported request/created-ID headers are retained. A lost response leaves an uncertain durable claim: inspect the advertising platform before preparing any replacement. AMCP does not automatically undo mutations or guarantee a cross-system transaction. State may still change between the final read and the provider accepting a write; no universal provider conditional-write facility exists here.

Protect the SQLite volume and backups: they retain account information, review payloads, redacted outcomes and audit records. Keep the encryption key separately. Restoration of an older backup may lose recent submission claims; reconcile platform state before resuming writes after a restore.

## Verification boundary

Automated tests cover native campaign CRUD requests for all six primary platforms and DV360, response validation, expired/stale reviews, tenant/user binding, grants, paused creation, duplicate submissions, lost responses, credential revocation and restart persistence using synthetic provider responses. The container CI workflow exercises both runtime modes. New tests exercise all four measurement/Apple providers with synthetic state and responses, including every enabled Tag Manager action, required scopes, native fingerprints, optional target absence and cross-resource rejection. Live mutations were not executed against user advertising accounts during development. Production OAuth, app approvals and live endpoint qualification remain external acceptance work.

Account write grants apply to campaigns, ad sets, ads, creatives and media equally. `WRITE_ACCOUNT_FORBIDDEN` reports the chosen connection ID and the selected account, plus whether other connections for that account have write grants. Set `connection_id` explicitly when selecting a different login; AMCP never silently chooses a more privileged one. Workspace context and account listings expose the same grant status. New connections default to reviewed write access when enabled; existing reader grants are preserved.

## Google targeting and exclusion lists

Reviewed execution now supports five Google Ads native mutate endpoints: campaignCriteria, adGroupCriteria, sharedSets, sharedCriteria and campaignSharedSets. Discover their exact actions through the Google gateway. Each call remains homogeneous and uses the normal prepare/execute review, explicit confirmation and spend_change_confirmed. New positive ad-group criteria require PAUSED; exclusions do not need a fabricated status.

Qualified criteria include positive/negative ad-group keywords, negative campaign keywords, locations, languages, devices, schedules, demographic exclusions, topics, existing user lists/audiences and placement exclusions where the native criterion type supports them. Shared lists use NEGATIVE_KEYWORDS or NEGATIVE_PLACEMENTS; list members must match the enabled parent list type. Criterion identity, parent and negative flag cannot be changed through an update mask: remove and recreate instead. Shared-set updates change name; shared criteria and campaign/list links support create/remove only.

Updates/removes read exact resource names and mutable configuration, including keyword bid micros. Creation reads the exact campaign/ad group/shared list and any referenced user-list/audience. Preparation and execution reuse those frozen GAQL reads. Composite criterion names must contain their native parent~criterion IDs; all customer-qualified references must belong to the selected customer. Budgets/bids retain native micros as decimal strings. Arbitrary new audiences, customer-match ingestion, all criterion variants and channel combinations are not qualified by this addition. [Google criteria](https://developers.google.com/google-ads/api/docs/targeting/criteria).
