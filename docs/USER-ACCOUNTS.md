# AMCP accounts and workspace access

People sign in with a verified email/password or an explicitly linked Google, Apple or Facebook identity. A person can belong to multiple workspaces. Connections, selected accounts and reports belong to the workspace.

## Claim the existing administrator workspace

1. Configure the email sender below. Keep the existing database and master encryption key.
2. Sign in through the "Owner sign-in" entry using the existing AMCP_ADMIN_PASSWORD or hash. The sign-in page shows it only while that password can still open the workspace (before migration), and only until anyone holds an approved account; after that, open `/login?owner=1` (SEC-05, review 2026-10-08).
3. In Account settings, choose the owner-account migration. Enter your name, an unused email address and the existing administrator password.
4. Open the emailed verification link in the same browser and choose a password of 15–128 characters.
5. Use the ordinary email/password form afterward. Migration attaches your owner identity to the existing workspace and preserves its connections, grants and reports. The legacy administrator password stops opening that workspace. Existing MCP clients must reauthorize and old administrator schedules must be explicitly resumed under the owner account.

AMCP does not generate a universal owner email or password. Migration is single-use, browser-bound and requires verified email; it cannot silently take over an existing member identity. Keep an encrypted backup and its master key before production upgrades.

## Email registration and recovery

Configure a verified sender in Resend, outside Git:

```text
AMCP_PUBLIC_ORIGIN=https://amcp.shop
AMCP_EMAIL_API_KEY=<sending-scoped Resend key>
AMCP_EMAIL_FROM=AMCP <accounts@your-verified-domain>
AMCP_ALLOW_SIGNUP=true
AMCP_RUN_WORKER=true
```

`AMCP_ALLOW_SIGNUP` is the policy. `GET /api/account/options` also reports `registrationAvailable`: true only when sign-up is allowed and a method can complete it (the email sender above, or a configured social sign-in). The landing page, its header, About and the sign-in page offer sign-up only then; otherwise they offer sign-in and "Ask your workspace owner for access", and `/signup` says registration is closed. That is the recommended closed mode for a private agency deployment (owner decision D3); configuring email or a social provider reopens it with no code change, and unsetting them closes it again.

Verify the sender domain using Resend's exact DNS records. Registration follows name/email → email link → choose password → workspace. Existing members can reset a password or change their verified recovery address. Verification can be resent; expired links have a fresh-start path. Public screens show available choices; owner Settings holds infrastructure diagnostics.

Messages enter an encrypted SQLite outbox before delivery. Delivery starts at once, but the response does not wait for it, so the time a registration or reset takes does not show whether the address has an account. Transient failures retry with an idempotency key, bounded timeout and worker lease. Single-use links expire after 30 minutes; retries do not extend them. Sent/expired queue payloads are cleared. Keep a worker running and the database persistent. Existing password sign-in continues without email configuration; registration and recovery require it.

Sign-in and email requests are limited per network address and per email address (10 sign-ins, or 5 reset, registration or email-change requests, per 15 minutes). After a completed sign-in, AMCP marks the browser as a known device of that person with an HttpOnly cookie that lasts 180 days and names no one. A known device has its own sign-in and reset budget, so failed attempts by someone else who knows the email address cannot lock the person out of a browser they already use; a password or email change makes every earlier device cookie invalid. At the per-email limit, reset, registration and email-change requests show the usual message and send nothing. Set `AMCP_KNOWN_DEVICES=false` to turn known devices off.

A new password (registration, reset, change, invitation, owner setup) must be 15–128 characters and must not be common or predictable (SEC-06, NIST SP 800-63B-4 §3.1.1.2). An offline check refuses, with `PASSWORD_COMMON`, a password built only from well-known password words, keyboard, letter or number runs, years and short numbers, repeated text, punctuation and the person's own context (AMCP, their email's name and domain, their name), including look-alike spellings such as `p@ssw0rd`. `AMCP_PASSWORD_BLOCKLIST_FILE` can name an exact list as well (one password per line, for example a vetted public list of common passwords of 15 or more characters; held only as hashes). Nothing is sent anywhere, and signing in with an existing password is never refused by it. The built-in check is a heuristic, not a breach-frequency list: conformance with the NIST requirement to compare against values known to be commonly used or compromised needs `AMCP_PASSWORD_BLOCKLIST_FILE` set to such a list, which is a deployment checklist item ([Railway deployment](DEPLOY-RAILWAY.md)).

Passwords use asynchronous scrypt (N=32768, r=8, p=3), bounded memory and at most four concurrent hashes. Existing supported hashes upgrade on successful login. The administrator and reviewer passwords configured on the server use the same parameters and the same limit; `npm run admin -- password-hash` prints a hash for `AMCP_ADMIN_PASSWORD_HASH` or `AMCP_TEST_PASSWORD_HASH`. Run `node dist/tools/password-benchmark.js` on the production-sized host. A local benchmark is not a capacity guarantee.

## Social sign-in

These credentials are separate from advertising OAuth:

| Provider | Exact callback                                 | Variables                                                                                                       |
| -------- | ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Google   | https://amcp.shop/api/signin/google/callback   | AMCP_SIGNIN_GOOGLE_CLIENT_ID, AMCP_SIGNIN_GOOGLE_CLIENT_SECRET                                                  |
| Apple    | https://amcp.shop/api/signin/apple/callback    | AMCP_SIGNIN_APPLE_CLIENT_ID, AMCP_SIGNIN_APPLE_TEAM_ID, AMCP_SIGNIN_APPLE_KEY_ID, AMCP_SIGNIN_APPLE_PRIVATE_KEY |
| Facebook | https://amcp.shop/api/signin/facebook/callback | AMCP_SIGNIN_FACEBOOK_CLIENT_ID, AMCP_SIGNIN_FACEBOOK_CLIENT_SECRET                                              |

Google uses a Web OAuth client. Apple uses a Services ID, registered HTTPS return URL and Sign in with Apple key; an externally maintained AMCP_SIGNIN_APPLE_CLIENT_SECRET can replace the signing-key configuration. Facebook needs Facebook Login and the exact valid redirect URI. Only configured providers appear publicly; configuration does not prove provider approval.

Sign in first, then link additional identities from Account settings. Matching emails never merge accounts. Linking preserves the active shared workspace. Provider subject IDs identify accounts; Google/Apple signatures, issuer, audience, nonce and expiry are checked. Facebook email is not assumed to be a verified recovery address. Social identity tokens are not stored as advertising connections.

## MFA, memberships and revocation

Account settings provides authenticator-app TOTP and ten one-use recovery codes. Store recovery codes privately outside AMCP. Scan the QR code with your authenticator app, open the link on the same device, or copy the setup key. The QR code is drawn from the vendored `qrcode-generator` (see `web/vendor/README.md`); nothing leaves the page to make it. MFA applies to both password and social sign-in once enabled. Password reset does not remove MFA. Passkeys are not included.

### Required two-step verification and recovery

Two-step verification is required of owners and administrators of write-enabled workspaces on a deployment that allows reviewed writes (owner decision P2, SEC-06). A workspace is write-enabled once one of its connections grants write access to an account (or enables it for every selected resource); a workspace without write grants, such as a new self-service sign-up's own workspace, is not covered. `AMCP_REQUIRE_MFA` sets this baseline: `admins` (the default when writes are allowed; owners and administrators of write-enabled workspaces), `everyone` (every member of every workspace), or `off` (the default for a read-only deployment, and the rollback). Each covered member has `AMCP_MFA_GRACE_DAYS` (default 14, 0–90) from the latest of the day the baseline first applied, the day they joined and, for `admins`, the day the workspace was first seen write-enabled. A workspace owner whose own account uses two-step verification can also require it in Account → Workspace security, of administrators or of everyone, after a 0–30 day grace period (`POST /api/workspaces/security-policy`, stored as `account_settings/security`, audited as `workspace_security_policy_saved`); tightening starts a new grace period, and turning it off is immediate. Members are told the date in Account. After it, a covered member without two-step verification reaches only sign-in, Account and the enrollment routes; every other workspace API refuses with `MFA_ENROLLMENT_REQUIRED`. While the workspace policy is on, owner authority (spending, retention, downloads, retained originals, turning personal data on and personal-data uploads) also needs a session opened with two-step verification (`MFA_STEP_REQUIRED`); reading health, pausing writes and turning personal data off never wait for it. The administrator and reviewer sign-ins and reviewer test accounts are never covered; MCP keys are not affected. The requirement gates the website only: connector tokens and AI-client connections a member created before the grace period ended keep working for that member until they are revoked or expire. To cut them off, revoke them in Account (or Workspace members) when the grace period ends.

People with two-step verification can create ten new recovery codes in Account (`POST /api/account/mfa/recovery-codes`) with a current authenticator or recovery code and a recent sign-in; the previous codes stop working and a security notice is sent. A member who lost both the authenticator and the recovery codes asks the AMCP owner: in Account → Workspace members, Reset two-step (recent sign-in required, never for the owner's own account), or on the server `npm run admin -- mfa-reset <email>`. Either turns two-step verification off, ends every session, connector token and AI-client connection of that person, and is audited as `account_mfa_reset`; the website reset also emails them. Support runbook: confirm the person's identity outside AMCP first (a call to a known number, or in person), reset, then ask them to sign in and set it up again at once; a covered member past the grace period can do nothing else until they do.

| Role     | Access                                                                                                                                      |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Owner    | Workspace administration, memberships, owner-only spending/retention controls and reviewed operations                                       |
| Admin    | Connections, permitted membership administration, reports and reviewed operations; cannot replace the owner or change owner-only policies   |
| Operator | Selected-account reporting, reviewed operations, exports and schedules; may connect their own AI clients with read or reviewed-write access |
| Viewer   | Read access; no writes, exports, report-file downloads, invites or schedules; may connect their own AI clients with read-only access        |

Report-file downloads (Overview CSV and source evidence, PDF and Excel packs, retained report files and detailed evidence workbooks) need an operator role or higher. The workspace owner can let viewers download them too, from Settings → Report file downloads (`POST /api/export-policy`, stored as `account_settings/exports`, audited as `export_policy_saved`); it is off by default. Viewers always read the same reports on screen, and the website hides the download controls they cannot use (SEC-05, review 2026-10-08).

Every active member may authorize an AI client or create a connector token for themselves (owner decision D16, review 2026-10-08). The access granted is capped by the member's role, and the consent screen offers read-only access to everyone. A member sees and revokes their own tokens and clients; owners and administrators revoke any of the workspace. Reviewer test accounts cannot connect AI clients.

### Clients in one workspace: working client and client access sets

An agency keeps many clients in one workspace (owner direction P1, SEC-08). Two separate controls serve it.

**Working client (a view filter, not access control).** The top bar's **Working client** lists the approved client playbooks that bind at least one account you can reach. The choices come with the session (`workingClients` in `GET /api/session`; `GET /api/working-clients` reads them again after a playbook is saved or deleted), so no page waits for them. Choosing one narrows the account pickers and lists to that playbook's bound accounts: Home (attention items, recent plans and their count, account readiness and evidence), campaign plans, operations, audit activity, media recovery, the creative library, Drive import, creative push, ad previews, the report builder's accounts and saved reports, the capabilities account picker, the campaign composer (the playbook is preselected and Page suggestions come only from the logins holding its accounts), clone and capture sources, Portfolio, Measurement and Commerce. A picker preselects an account only when exactly one remains; otherwise it shows an explicit **Choose an account** (Drive import and ad previews used to take the first account of any client). An account named by the address (`account_id`, a link) stays listed, an account typed into a filter is not narrowed further, and a picker the filter left empty says so instead of asking to connect an account. A push or plan asks for confirmation first when no one client holds all of its accounts; an account two playbooks share, or one no playbook binds, mixes nothing. The choice lives in `?client=`, which links and page states keep, and in this tab per person and workspace (`sessionStorage`); it is forgotten on sign-out and workspace switch. Sign-in and authorization steps neither show nor rewrite it: the AI-client consent screen offers only its own **Limit to client**. MCP callers use the same filter as an optional `profile_id` on `amcp_campaign list`, `amcp_workspace operations` and `history`, `amcp_media list` and `library`, and `amcp_reporting_overview bootstrap`. It is intersected with current access, so it can only hide accounts; a removed playbook, or one outside your access, is refused with `PROFILE_NOT_FOUND` instead of showing every client (the plan list then finds only plans recorded with that playbook).

**Client access sets (access control, optional).** In Account → Client access sets an owner or administrator names the accounts of one client: 1 to 200 accounts selected in this workspace's connections, at most 100 sets (`POST /api/access-sets`, which needs a recent sign-in; `DELETE /api/access-sets/:id` with `confirmed:true`; audited as `access_set_created`, `access_set_changed` and `access_set_removed`). **Limit to client** then appears when creating a connector token (AI connectors), on the AI-client consent screen, when inviting a viewer or operator, and on each member row. Access limited to a set reaches only its accounts: every listing and resolution of accounts goes through one helper (`Store.connectionsFor`), so `get_workspace_context` and `list_accounts` name only the set's accounts (and the set), reads, reports, dry runs and reviews of any other account are refused with `ACCOUNT_SCOPE_RESTRICTED` without saying whether that account exists, and playbooks, briefs, plans, saved reports, schedules and Sheets destinations outside the set are neither listed nor opened. A login the set shares with another client lists only the set's own records through it: write receipts (dashboard, capabilities), uploaded media receipts (`list_workspace_assets`, `list_media_assets`, `plan_campaign_structure`) and report tabs of its spreadsheets. A saved report, template, snapshot or schedule outside the set cannot be changed, paused or deleted by its ID either. A Facebook Page belongs to a login rather than an account, so limited access gets no Page suggestions and names its Page explicitly. A set never grants anything: writes still need the account's write grant, review, spending policy and confirmation. Owners and administrators are never limited. A member limited to a set hands on only that set, and their tokens and AI clients must carry it: changing a member's set ends their sessions, and a credential they hold for another set (or for the whole workspace) stops with `MEMBERSHIP_REVOKED`. A change to a set applies at the next request; a removed set reaches nothing until an administrator gives access again (fail closed). Tokens, AI clients and members without a set keep whole-workspace access, so nothing existing changes: the only schema change is the additive `api_keys.access_set_id` column (store step `store-0015`), and a member's set is a `member_access_set` document. Work done under a set records its `access_set_id` in the audit trail, as do token creation, AI-client approval and member changes. Rollback: remove the limits or the sets, which restores whole-workspace access.

Invitations are bound to the invited email and last 72 hours unless the workspace owner sets 1 hour to 7 days in Account → Workspace security (owner decision P2, SEC-06). Owners and administrators see pending invitations (role, sent and expiry, never the address or link) and can withdraw one (`POST /api/workspaces/invitations/:id/revoke`, audited as `workspace_invitation_revoked`): its link stops working at once. To resend, withdraw it and send a new invitation. An account created through an invitation is approved only when the instance owner sent the invitation (or sign-ups are approved automatically); an invitation from another workspace's administrator creates a pending account and asks the owner, and its membership applies once access is granted. Existing users accept while signed in as that identity; new users verify the invitation and choose a password. The inviter's current permission is checked again at acceptance. The owner cannot be demoted/removed through member editing.

Password/email security changes, MFA changes and membership changes revoke the relevant browser/MCP access. Each of them — a password change or reset, an email change (sent to the previous address), two-step verification turned on or off, a recovery code used, a sign-in method added or removed — also emails a security notice through the outbox. A browser session ends after 2 hours without a request, within its 8-hour limit. Jobs recheck membership and credential/account version before requests. Revoked schedules pause; reauthorize explicitly. Exact Origin and CSRF remain required for every change. Existing advertising and MCP OAuth redirect, PKCE, scope and resource controls remain in force.

The shared reviewer workspace (the `AMCP_TEST_PASSWORD` sign-in) does not keep evaluators' provider logins (SEC-06): when a deployment starts with a new reviewer password, every login connected in that workspace is removed, and the worker removes each one 7 days after it was connected (`AMCP_REVIEWER_CONNECTION_DAYS`, 1–90, or `off`). Removal is a local disconnect (credentials, selections and report content read through it go; receipts and audit stay; no provider request) audited as `reviewer_connections_purged`. Connections shows each reviewer login's connection date and removal date. Reviewers should use test advertising accounts; revoke the AMCP grant at the provider too if a real account was connected.

Accounts can be erased (SEC-07). Revoking access keeps the account; erasing removes it, its own workspace and everything that workspace holds, with its memberships, invitations, monitor subscriptions, keys and AI-client access elsewhere. The operator erases one with `admin erase-account <email> --dry-run`, then `--confirm` (see [operations](OPERATIONS.md#account-erasure-and-retention)). Sign-ups never approved are erased 30 days after they were made (`AMCP_PENDING_ACCOUNT_DAYS`, 1–365, or `off`; the 30-day default was chosen during implementation and the owner may revise it, [decisions](DECISIONS.md)); the owner's access list says so. A pending account that holds a membership in another workspace (someone invited by that workspace's administrator, still awaiting the owner's approval) is never erased by this sweep. Revoked accounts are erased only when the owner sets `AMCP_REVOKED_ACCOUNT_DAYS` (1–3650 days after revocation). The deployment owner's account, and an account whose workspace other members still use, are refused. There is no self-service deletion yet: it waits for the privacy policy review (owner decision P3).

### Confirm it's you (recent sign-in)

Some changes need proof of identity from the last 15 minutes: a sign-in, or a "Confirm it's you" step-up (SEC-06, review 2026-10-08). They are the account security changes (password, email, two-step verification, linking and removing sign-in methods) and every change that mints lasting access or grants authority: creating a connector token, approving an AI client, adding write access (on its own or through an asset selection), inviting a member, changing a member's role and granting account access. Removing write access, removing a member and revoking account access never wait for it, so access can always be ended at once.

Without recent proof the server refuses with `REAUTH_REQUIRED` before the change has any effect. The website then opens "Confirm it's you" in place: the account password, a two-step code (authenticator or recovery code), or a linked Google, Apple or Facebook sign-in (the administrator and reviewer sign-ins use their own password). After the server accepts it (`POST /api/account/reauthenticate`), the original request is sent once more; the page and its form keep their state. A social confirmation leaves the page and returns to it. The step-up renews only that session's recent proof (audited as `account_reauthenticated`); its 8-hour and 2-hour limits never move. Attempts count against the person and the network address (8 per 15 minutes), like sign-in.

Automated tests use synthetic identities and mail transport. Verify real inbox delivery, resend/recovery, a second browser, restart persistence, each configured social provider, owner migration on a backup copy, MFA/recovery and membership revocation before public registration. ## Reporting an account or authorization error

Keep the error code and request reference displayed by AMCP, with a short description of the
action you attempted. The reference lets the operator find its matching http_refused/http_failed
event without sending passwords, OAuth tokens, callback query parameters or request payloads.
Known authored website reasons are displayed in your selected English/Arabic language.
A reference records a refused or failed attempt; it does not authorize a retry, change your role
or prove provider eligibility. Follow the original reason before explicitly trying again. See
[website diagnostic evidence](review/DELIVERY-2026-10-05-WEBSITE-DIAGNOSTICS.md).
