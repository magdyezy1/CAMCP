Following provider pages merges each page's row collections. The other fields (paging objects, cursors, `has_more`) describe the last page read, so a visible cursor never points back at merged rows. TikTok integrated reports are the exception: they keep their first page's native counts. A collection capped by `max_pages` returns `truncated: true` and a `next_call`. That call is the same tool and arguments with the native cursor of the first unread page set where the caller supplied it, and it declares its effects (`provider_requests`, `saves`, `advertising_writes`). It is offered only when it compiles back to exactly that request. Otherwise the result carries `next_call: null` and `continuation_unavailable`. Delegated operations, whose public arguments have no aggregation controls, continue one page per call. A capped TikTok integrated report is collected again from page one, with `max_pages` covering every page. TikTok lists that page by `{cursor, has_more}` are followed to the last page; `has_more` without a usable cursor is refused (`UNKNOWN_PAGINATION`). A response that advertises another page but has no row collection to merge is also refused with `UNKNOWN_PAGINATION`, a deliberate fail-closed change of MCP-04 (before, the later pages were dropped and page one was returned as if complete); read such a response page by page. Google legacy list aliases called without `limit` or `query` stop at `LIMIT 100`. Their warnings say so, and a result of exactly 100 rows carries `truncated_possible: true`, `default_limit` and a `next_call` with `limit: 10000`, offered only when it compiles back to the same list with `LIMIT 10000` (otherwise `next_call: null` and `continuation_unavailable`).

Native read results keep provider text verbatim, except secrets inside URLs: in a string that is an absolute URL, the value of an `access_token`, `token`, `key`, `sig`, `signature` or other secret parameter becomes `[REDACTED]`, and `url_secrets_redacted` counts the changed strings. Text outside URLs, such as a name containing `token=`, is unchanged. Google generated-image links (`imageTemporaryUrl`) keep their signature. Other self-authorizing download links are withheld on purpose: Microsoft Advertising bulk and report status reads, for example, return Azure SAS links (`DownloadUrl`, `ReportDownloadUrl`) whose `sig` is redacted, so an AI client cannot fetch those files around AMCP; AMCP reads the unredacted response internally for its own Microsoft report download, so reporting is unaffected. Reads that return submitted leads (TikTok `/v1.3/lead/get/`, `/v1.3/page/lead/task/download/` and `/v1.3/page/lead/mock/get/`) are personal data and refused with `PERSONAL_DATA_READ_FORBIDDEN`, whatever resource binding exists.

## Help and introspection

Every `amcp_tool_help`, `LIST_ACTIONS` and `DESCRIBE_ACTION` result has one envelope, `{success, data, meta}` with `meta.requestId`; the captured content is kept verbatim under `data`, without its own `success` flag (MCP-05). Root help keeps the captured discovery block (`tool_count` 20 and its 19 gateways, the compatibility catalog, owner decision D17) and adds `amcp_surface`: the tools this connection lists now, each with its kind and selector, and a `surface_revision` hash that changes whenever a listed name, description or schema changes. `amcp_release` and `serverInfo.version` name the build (`0.1.0+<revision or artifact digest>`, the record `/versionz` reads). Help accepts every listed tool, including the AMCP tools and `microsoft_ads_native_action`, by a special case that leaves the captured help schema byte-identical; `amcp_tool_help {gateway: "amcp_tool_help"}` lists the arguments it accepts beyond that schema (`topic`, `include_guidance`).

Operation help on a direct gateway describes a catalog action from its record, as `DESCRIBE_ACTION` does; an operation the catalog does not list is refused with `UNKNOWN_OPERATION`, naming the value, up to five close names from the same gateway, the first 20 valid names with their count, and a `list_call` (`LIST_ACTIONS`, or `amcp_workspace contracts` where a gateway has no verified listing). It never falls back to the whole gateway's help. `LIST_ACTIONS` pages carry `total`, `offset`, `limit`, `has_more` and `next_offset` on every gateway; the captured `total_actions` and Snapchat's `next_cursor` stay as aliases. DV360 accepts `LIST_ACTIONS` and `DESCRIBE_ACTION` beyond its captured enum; the page lists the catalog AMCP validates against, with each action's contract status. Schema refusals are compact: the failing `instancePath` and keyword, the first 20 allowed values and their count, `details.field`, and for an unknown action `did_you_mean`, `list_call` and `surface_revision` (a client whose definitions are stale should list the tools again). An unknown guide URI is JSON-RPC error -32002 with `data.uri` and `data.index`; an unknown prompt or platform is -32602 with `data.allowed`. An unknown tool name stays a tool result (`UNKNOWN_TOOL`, `isError`), deliberately, so the client sees the remedy.

`amcp_tool_help` returns `amcp_contract`. `amcp_write inspect` and prepare return `contract_evidence`; with `evidence: "ref"` its provider contract is a reference (versions, version end and the `amcp_tool_help` call that returns the whole contract), and `amcp_campaign` keeps its steps that way. Errors include a category, owner and remedy. Destructive operations retain existing explicit review and policy controls; there is no new acknowledgement that could imply schema provenance makes a write safe.

`generate:vendor:check`, `generate:wsdl:check` and `contracts:check` are deterministic offline checks. The public-provider workflow separately checks remote schemas and documentation. A changed page is a maintenance signal, not proof of a breaking change. No CI job automatically upgrades versions or submits account mutations.

Each provider contract carries `contract_digest`, the SHA-256 of its content at the version AMCP sends (every field except its record metadata and test lists), and compact contract references carry it too (ACC-05). Its `contract_version` and `reviewed_at` come from `src/provider-contract-manifest.json`: when the content changes, `npm run contracts:generate -- --reviewed-at=YYYY-MM-DD` records the new digest, bumps `contract_version` and sets `reviewed_at` to the date of that review, which the person who reviewed the change supplies (the day the generator runs is never taken as a review date), and `contracts:check` fails until it has. After merging branches that change provider contract content, run it once on the merged tree with the date the merged content was reviewed, and commit the manifest diff. A row of the provider acceptance ledger applies only to the digest and version it ran under ([provider access register](PROVIDER-ACCESS.md)).
