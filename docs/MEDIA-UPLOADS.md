A file reaches AMCP in one of three ways: uploaded on the website (the **Media library** page), a public HTTPS link, or Google Drive (a public share link, or a private file or folder selected in a separate Drive connection; see [workspace operations](WORKSPACE-OPERATIONS.md)). **The AMCP server receives or downloads the file and transfers it; the MCP client/LLM never needs to download it or expose base64 bytes.** Normal native upload actions, `platform_media_upload` and `amcp_media` share the same reviewed uploader.

## Without Google Drive

**Upload on the website.** *Push creatives* on the Media library page takes PNG, JPEG, MP4 and MOV files, several at once; they are sent one after another. The browser sends each in 1 MiB parts, so each part arrives within the server's 45-second request limit even on a slow connection, and a part that fails is sent again on its own. Each part is encrypted into the same staging as reviews. On completion AMCP checks that every part arrived, that the file really is PNG, JPEG, MP4 or MOV (from its bytes, not its name), records its SHA-256, and reads its dimensions and a small preview frame with FFmpeg. The upload is then an **upload source**, `src-…`, kept until thirty minutes after upload starts; completion does not extend it. It belongs to the person who uploaded it, on the website and through every AI client or connector token that person authorized (the administrator's password sign-in and the clients and tokens approved from it are one person); workspace administrators can use every upload of the workspace, and another member's client is refused. Temporary and explicitly retained originals together may hold up to four times the media limit in bytes per workspace (25 files at most) and eight times in all (50 files), apart from the reviews each workspace may stage: a finished upload counts its size; a website upload still arriving counts the exact size it declared (sealed with its staging row, and enforced part by part), while a link or Drive download still arriving, or a reservation that cannot be read, counts the whole limit. Four full-sized files still fill a workspace while many small images fit in the same space. One member's unfinished website uploads hold at most ten files and two media limits of bytes in a workspace, so one member's abandoned uploads cannot fill it for everyone. Readers cannot upload, and neither can reviewer test accounts.

**Progress for screen readers (MED-05).** While a file transfers, the progress bar (named "Upload progress of *file*") and a visible "*file*: part N of M" move with every part, but the polite status region speaks only when the file starts, at 25, 50, 75 and 100 % and at the outcome (a failed file is named in the outcome), so a 128 MiB upload is announced about six times instead of 128. A resumed upload is first announced at the quarter it has reached. Deadline warnings have their own polite region (below).

**Unfinished uploads: release, resume and discard.** An unfinished website upload that receives no part for 10 minutes (`AMCP_MEDIA_UPLOAD_IDLE_MINUTES`, 1–30) is released early (owner decision D23: earlier, never later); each part moves that release on, never past the upload's absolute thirty-minute deadline, and a completed upload keeps exactly that deadline. The website discards an upload the server refuses at once (`DELETE /api/media/sources/:id` with `keepalive`, the same session and CSRF checks); one interrupted by a lost connection, a busy server or a page change is kept to resume. The Media library lists unfinished uploads with the parts received, when they are released if nothing more arrives, their deadline, **Resume** and **Discard**. `GET /api/media/sources/:id` returns an unfinished upload's `received_parts`, `missing_parts`, `parts_sealed` and `first_part_sha256` (read from part indexes without decrypting them). A resume checks the chosen file's size and first-part SHA-256 in the browser, sends only the missing parts, and completion still checks the whole file's SHA-256; it never extends the deadline. Completion is idempotent: a completion interrupted after sealing the parts is simply completed again (parts are then refused with `MEDIA_UPLOAD_COMPLETING`), and concurrent completions of one upload serialize under a lock (the second gets `MEDIA_UPLOAD_COMPLETING`, retryable). Responses carry `server_time`, so the page counts deadlines down on the server's clock.

**A public link.** `amcp_media` accepts `source_url`, and the website accepts a link in place of a file. The link must be HTTPS on the standard port, name a host (not an IP address or a single-label local name) and carry no user name or password. Every address the host resolves to must be public: private, loopback, link-local (cloud metadata), carrier-grade NAT, multicast, documentation and other special-purpose ranges are refused. The connection goes to the address that was checked, so the name cannot be re-pointed between the check and the download. At most three redirects are followed, each checked the same way. No cookie, credential or advertising token is sent. The download is limited to the media limit and must be PNG, JPEG, MP4 or MOV by its bytes. AMCP records the host the file came from, never the full link, which may carry a token. Google Drive links go through `drive_url` instead.

**Retain a separately imported original.** Website computer uploads cannot be retained. Their original bytes, thumbnails, variants and review copies share upload start plus thirty minutes; new reviews cannot extend that deadline. Access is refused exactly at expiry, with an independent fifteen-second cleanup timer and startup cleanup deleting encrypted copies. Legacy retained computer uploads follow the same rule. For a separately imported link/Drive original only, a current workspace owner can choose **Retain this original**, inspect its exact SHA-256 and confirm an encrypted copy kept until removal. Its `lib-…` ID works with prepare/plan/variant/eligibility inputs under the unchanged original-file count/byte ceiling. Retention never uploads to a provider or changes existing plans. Provider-hosted assets and historical receipt metadata remain separate; new encrypted backups omit transient media and legacy retained computer uploads. See [batch 191](records/DELIVERY-2026-10-07-APPEARANCE-MEDIA-DETAIL.md) for precise cleanup/backup boundaries.

**From MCP.** `amcp_media list` returns accessible temporary and retained originals under `sources`, including the ones the same person uploaded on the website. It pages upload receipts (`assets`, `total`, `has_more`) with `offset` and `limit`, and the caller's unfinished-upload recovery reviews (`recovery_reviews`, `recovery_total`, `recovery_has_more`) with their own `recovery_offset` (it defaults to `offset`, as before); `include_assets: false` leaves the receipts out. The Media library page pages recovery with `?recovery_page`, enables *Next recovery page* only on `recovery_has_more`, and keeps the creative library's search and filters in the address apart from it (MED-05). For a separately imported link/Drive original, use `retain_source` with `source_id`, `confirmed:true` and the selected `expected_sha256`; retry returns the same verified library copy. `remove_source` requires those same owner-confirmed fields for permanent removal of a library original. `prepare`, `plan`, `variant` and `inspect_eligibility` take exactly one file: `source_id`, `source_url`, `drive_url` or `variant_id`. Native upload actions and `platform_media_upload` take a public HTTPS link in `url` just as they take a Drive link; an upload is used through `amcp_media` with its `source_id`.

## Fit to each platform

With `fit_to_platform: true`, `prepare` fits the file before freezing it for review, as the owner decided on 2026-09-28:

- Media larger than **1080 pixels on its short side or 1920 on its long side** is scaled down to fit, keeping its shape: 4500 × 4500 becomes 1080 × 1080, 4500 × 8000 becomes 1080 × 1920, 3840 × 2160 video becomes 1920 × 1080. Nothing is cropped, padded or enlarged. This is AMCP's delivery size, not a limit any platform states.
- An image still above the platform's image limit (table below) is re-encoded: a PNG stays PNG when it fits, otherwise becomes JPEG unless it has transparency (then AMCP refuses and says so); a JPEG is saved at FFmpeg quality 2, then 5, then 9, until it fits.
- A MOV video for X or LinkedIn, which take only MP4, becomes MP4. Streams that are already H.264 and AAC are copied without re-encoding.
- A JPEG's EXIF orientation is applied to the pixels, since the output carries no metadata. FFmpeg 5.1 (the production image) and later versions treat EXIF orientation differently, so AMCP reads it itself and applies it once. One helper (MED-04) gives the upload record, its preview frame, `inspect_eligibility`, fit and variants the same displayed size: a photo stored 2700 × 2160 with orientation 6 is 2160 × 2700 everywhere, and every image is decoded with `-noautorotate` and turned by AMCP's own filter. A video's rotation is applied by FFmpeg itself.

Media that already fits is uploaded byte for byte. Otherwise `request.transform` in the review states `from` and `to` (dimensions, bytes, type), each step, and those steps in words for the platform. Fitting is bounded like variants: one image or video stream, at most 40 megapixels and 180 seconds, two conversions at once. One video conversion (fit or variant) may run 180 seconds (`VIDEO_CONVERSION_TIMEOUT_MS`), always within a website upload's deadline. Measured with `npm run benchmark:media-variants` ([Operations](operations/STORAGE.md#video-conversion-time)): a 180-second 1080p source took 42–64 seconds per variant on a lightly loaded workstation and up to 167 seconds under heavy load, so the earlier 120-second limit was raised and the two costliest conversions were made cheaper. A long 2160p (4K) source takes about three times longer to fit or crop and can reach the limit; it is then refused with `MEDIA_CONVERSION_TIMEOUT`, never cut short. Without `fit_to_platform`, a refusal that fitting would solve (an image over the limit, MOV for X or LinkedIn) says so.

## Push to several accounts

`amcp_media plan` takes an upload's `source_id`, `fit_to_platform` and up to 20 `destinations` (`platform`, `account_id`, optional `connection_id`, `owner_urn`, `dv360_target`). Without calling a platform, it returns for each destination whether access allows it, the exact file it would receive (SHA-256, size, type, dimensions and every change) and `existing_receipts`: upload receipts of this account and login that already hold exactly that file (same SHA-256, DV360 target and LinkedIn owner). Platforms whose limits differ only where the file is unaffected share one conversion: an image converts once per image byte limit, a video once (twice only for a MOV going to X or LinkedIn as well as elsewhere). Each ready destination is then prepared with `expected_sha256` set to its planned SHA-256 (`prepare` refuses with `MEDIA_CHANGED` if the file differs), or with `reuse_existing: true` to reuse a listed receipt after a fresh provider availability check (zero uploads; a failed check refuses with `MEDIA_NOT_AVAILABLE` or `MEDIA_NOT_READY` and nothing is sent), and executed as its own review.

**Placement check (MED-06, advisory).** Each ready destination also carries `placement_check`: the file it would receive (size as seen, duration, bytes) compared with AMCP's versioned table of provider placement specifications (`src/media-specs.ts`, version `spec_version`). For every recorded placement of that platform and kind of file (`Feed`, `Stories and Reels`, `Single Video`, `Demand Gen`, … — the provider's own names) it lists `fits` and the `issues` (`aspect_ratio`, `min_resolution`, `min_duration`, `max_duration`, `max_bytes`, each with `actual` and `expected`); facts the upload record lacks are listed under `unchecked`, never as failures. When no recorded placement takes the file, `suggested_preset` names the variant preset (`square`, `portrait`, `vertical`, `landscape`) that most placements would take; a preset only changes shape and size, so none is suggested for a duration or file-size issue. The check is warning-only: a destination stays `ready`, nothing is refused, and the provider's own processing decides. Each table entry names its provider page (`source_url`) and the day it was recorded; `verified_against_source` stays `false` until an owner-run, read-only comparison with each page records a `verified_on` date, and `stale: true` labels results once the table is more than 180 days old. The figures were recorded during implementation without reading those pages, so the whole table is unverified until that comparison: MED-06 stays open for it, and `verified_on` is set per entry only after its page was compared. A DV360 creative asset has no recorded placement and gets no check. The website shows the result under *What it receives* (English and Arabic; placement and shape names stay literal).

**Fitted copies are kept for the push (MED-03).** By default `plan` stages nothing. With `stage_fits: true` (the website's push asks for it) each changed output is kept as an encrypted staging copy, `fit-<source_id>-<key>`, keyed by the original's id and SHA-256, the limits, the fit pipeline version and the FFmpeg build's version line, so a build change never reuses another encoder's bytes or makes a planned row fail `MEDIA_CHANGED`. Every later `prepare` or `plan` of the same original and limits uses the copy after checking its bytes against its sealed SHA-256, instead of converting again; a ten-account video push converts once instead of about eleven times. A copy lapses with its original (a website upload's thirty minutes; a retained original's copy after an hour), is removed with it, counts against the original-file quota and is evicted first when an upload needs the room, so it never refuses an upload. A full quota only means no copy is kept. A saved push plan's preflight checks each step's planned file against its original and this copy (`media_checked`) without preparing, converting or staging anything; without a copy it prepares as before.

The website's *Push creatives* follows exactly this for several files: bring them in (uploaded, from a link, or from Google Drive), choose accounts (every account of a platform with one box, on as many platforms as needed), see what each account receives of each file and why, choose for a file already in an account between *Reuse it (fresh availability check)* (the default) and *Upload it again*, and confirm once. Accounts are named by their own name and ID, as the last sync of their login read them. One push reviews at most 200 uploads (files times accounts).

**The push runs on the server.** After the confirmation the website saves the rows as campaign plans of at most 50 independent uploads (each step named "file → platform · account", bound to its planned SHA-256 and the reuse choice), approves each with that confirmation (`approve` with its exact `plan_hash` and `summary_hash`) and queues it with `amcp_campaign run_background`. The worker runs the plan exactly as `run` does — every upload is still its own frozen review with its own idempotency key, executed once and recorded — as the person who queued it, one background plan per person at a time so the workspace never holds two of their staged reviews. In a plan of independent uploads one failed or uncertain upload does not hold the others. Busy media capacity (`MEDIA_MEMORY_BUSY`, `MEDIA_PROCESSOR_BUSY`, full review staging) leaves the upload pending (`waiting` in the plan view) and the run yields and continues. The page reads the plans back every four seconds while it is shown; leaving it stops nothing, the rows stay in their plans (*Open its push plan*), and *Run approved plan / continue* or *Run on the AMCP server* on the plan page resumes a run that stopped. `get` shows `background` (`queued`, `running`, `complete` or `failed`). `AMCP_SERVER_PUSH=false` is the rollback: `run_background` is refused (`BACKGROUND_RUN_DISABLED`) and the page drives each row itself, one at a time, through a durable job (`prepare`, `execute_async`, then `job_status` every four seconds), with a leave-page warning while rows still depend on it; leaving stops only the rows not yet started.

Each temporary file shows a live countdown on the server's clock; a polite status region announces only the 10-, 5- and 1-minute marks and the deletion. Rows are pushed soonest deadline first (retained originals last) with an estimate of the push time; a row whose file would be deleted before it could finish is skipped unsent ("Upload again"), and a server refusal `UPLOAD_DEADLINE_TOO_CLOSE` is shown the same way. Uploading the identical file again (the same SHA-256 the server computed) re-binds the skipped or expiring rows to the new upload — a new upload with its own thirty minutes, not an extension (D23); a different file re-binds nothing. Busy refusals (`MEDIA_MEMORY_BUSY`, `MEDIA_PROCESSOR_BUSY`) come before any claim and are retried with jitter until a minute before the file's deadline. A plan saved from the push (*Save as a resumable upload plan*, or the server push) that uses temporary files (`src-…`) is saved only after the member confirms their deadline: `amcp_campaign create` refuses such steps with `TEMPORARY_MEDIA_SOURCES` unless `acknowledge_temporary_sources: true`, refuses them with `TEMPORARY_SOURCES_EXPIRING` when the earliest is deleted within five minutes (or already was), and the plan records `temporary_sources.earliest_expires_at` and shows it as its run-by time (`run_by`, "Runnable until HH:MM"). A step whose file expired or changed (`MEDIA_SOURCE_NOT_FOUND`, `MEDIA_CHANGED`, `UPLOAD_DEADLINE_TOO_CLOSE`, `TEMPORARY_SOURCES_EXPIRING`) gets a *replace source* amendment: its `next_call` names the `amcp_media plan` call for its one destination and a `recover_step` patch of `/source_id` and `/expected_sha256`; the website's *Replace the file* does both. The step is reviewed again with the new file, the old bytes are never reused, the plan's approval is void until it is approved again, and a temporary replacement moves the run-by time and must leave five minutes too. For a plan that can wait, import the files from a link or Drive and have an owner retain them (`lib-…`).

## Normal native flow

Call `amcp_write`:

```json
{
  "action": "prepare",
  "gateway": "meta_native_action",
  "connection_id": "YOUR_CONNECTION_ID",
  "arguments": {
    "action": "meta_image_upload",
    "account_id": "YOUR_ACCOUNT_ID",
    "payload": {
      "url": "https://drive.google.com/file/d/YOUR_DRIVE_FILE_ID/view",
      "name": "September image"
    }
  }
}
```

Preparation downloads on the server, checks format/size, encrypts the exact bytes, reads account configuration and returns a five-minute review with SHA-256 and `next_call`. Review the file details before following that call:

```json
{
  "action": "execute",
  "review_id": "COPY_FROM_PREPARE",
  "idempotency_key": "COPY_FROM_PREPARE",
  "confirmed": true
}
```

Use `amcp_write` or `amcp_media` to execute. Meta images return `image_hash` / `meta_image_hash`; use that value in `object_story_spec.link_data.image_hash` in `meta_creative_create`. Use the returned creative ID in `meta_ad_create`. Both are reviewed contracts; new ads still require `status: "PAUSED"`. A Page ID with advertising permission and a destination URL are required for website link creatives. AMCP does not invent them.

Native upload calls with `dry_run:false` prepare a review and return the execution `next_call`; they never upload immediately. For a client on the v2 contract profile ([configuration](operations/CONFIGURATION.md#the-contract-profile-of-an-ai-client)) they save no review and fetch nothing: the call is refused with `MEDIA_REVIEW_REQUIRED` and a `next_call` to `amcp_media prepare` for the same file, as a native change is refused toward `amcp_write`. With `dry_run:true` or omitted, a native URL call returns a preview without downloading or calling a provider. Native source aliases in `payload` are `url`, `drive_url`, `image_url`, `video_url`, `file_url` and `source`. Conflicting aliases and unconsumed fields are rejected. Existing account-bound Snapchat `media_id` uploads reuse that allocation.

## Shared workflow

Call `amcp_native_action`:

```json
{
  "operation": "platform_media_upload",
  "arguments": {
    "action": "UPLOAD_FROM_URL",
    "platform": "snapchat",
    "account_id": "YOUR_ACCOUNT_ID",
    "url": "https://drive.google.com/file/d/YOUR_DRIVE_FILE_ID/view",
    "media_type": "image",
    "dry_run": false
  }
}
```

This returns the same review and execution `next_call`. `UPLOAD_FROM_URL_VIA_SESSION` and `QUEUE_GOOGLE_DRIVE_IMPORT` use this flow too. The latter accepts `google_drive_file_id` and optional `google_drive_resource_key`. Optional `inspect_google_drive_media` with `link` returns file metadata without file bytes. Inspection is not required before upload.

`FINALIZE_UPLOAD_SESSION` accepts the returned `upload_session_id`, matching `idempotency_key`, `confirmed:true` and `dry_run:false`; it executes the frozen review. Client-local file, browser-signed upload and external job-queue workflows are not implemented here.

Prepare one selected account per review. Names: `meta`, `tiktok`, `snapchat`, `google_ads`, `linkedin`, `x_ads`, `dv360`; shared workflows also accept `google`, `x`, `twitter`. A single `target_platforms` entry is accepted. Repeat the same link for other targets, without a client download. Use outer `amcp_write.connection_id` to select a login.

`amcp_media prepare` takes `platform`, `account_id`, one file (`source_id`, `source_url`, `drive_url` or `variant_id`), optional `connection_id`, `name` and `fit_to_platform`. Completed uploads appear in `amcp_media list` and `list_media_assets` with their platform identifiers, connection ID and `source`, the provenance of the original's bytes whichever way it was named: `amcp_upload` (uploaded on the website), `link_import` (a public link, by `source_url` or as an imported `source_id`), `server_drive_import` (Google Drive, by `drive_url` or as an imported `source_id`) or `retained_original` (an owner-retained `lib-…` copy). A variant upload keeps its original's label.

**Lineage (MED-04).** Each new review's `request.origin` names the original: `kind` (`website_upload`, `link_import`, `drive_import` or `retained_original`), `source_id` and `filename` when it was named by `source_id`, `original_sha256`, `original_size` and `original_mime`, `link_host` for a link, `imported_from` and `original_source_id` for a retained copy, and `variant` (`variant_id`, `preset`, `fit`, `source_sha256`) for a preset copy. These fields are part of the review's fingerprint; reviews prepared earlier keep their shape (`{kind: 'upload'}` or `{kind: 'link', host}`), fingerprint and label. Each receipt keeps `original_sha256`, so a fitted or variant upload still names the file it was made from after that file expired; `amcp_media library` with `original_sha256` lists the receipts of one original across accounts (the website's *Uploads of this same original*). Historical receipts are not rewritten.

## Files and processing

| Platform | Import limits | Identifiers and processing |
| --- | --- | --- |
| Meta | PNG/JPEG ≤30 MiB; MP4/MOV within the configured limit (default 128 MiB) | `image_hash` / `video_id`; videos may process |
| TikTok | PNG/JPEG ≤5 MiB; MP4/MOV within the configured limit (default 128 MiB) | `image_id` / `video_id`, native upload receipt |
| Snapchat | PNG/JPEG ≤5 MiB; MP4/MOV within the configured limit (default 128 MiB) | `media_id`; creative uses `top_snap_media_id`; native processing status |
| Google Ads | PNG/JPEG ≤5 MiB; MP4/MOV within the configured limit (default 128 MiB) | Image asset resource name; videos create UNLISTED uploads on the account's Google-managed YouTube channel |
| LinkedIn | PNG/JPEG ≤20 MiB; MP4 within the configured limit (default 128 MiB) | `linkedin_media_urn`, `image` / `video`; video needs an explicitly bound organization/person owner, not a sponsoredAccount URN; processing may continue |
| X | PNG/JPEG ≤5 MiB; MP4 within the configured limit (default 128 MiB) | `media_id`, `x_media_key`, library ID when attached |
| DV360 | PNG/JPEG ≤10 MiB; MP4/MOV within the configured limit (default 128 MiB) | `dv360_media_id` and native `asset`; availability handoff remains unqualified and is not marked ready |

Providers additionally enforce dimensions, duration, codecs, permissions and app approvals; `amcp_media plan` warns about the recorded ones in advance (see *Placement check* above) but does not enforce them. Without `fit_to_platform`, AMCP uploads the exact bytes; with it, the review states every change. Upload success does not establish ad approval. Binary upload APIs for other catalog providers are not implemented; measurement services and Apple Ads do not use this advertising-media flow.

Call `amcp_media {"action":"status","review_id":"..."}` for processing reads and follow its continuation:

- X: once processing succeeds, `prepare_library` reviews attaching the already uploaded video to the account library. Execute the new review; no re-download/re-upload occurs. This does not post a tweet.
- Google Ads: after PROCESSED, status returns `youtube_video_id` and an exact `amcp_write prepare` call for a YouTube video asset. This separate asset mutation is reviewed. Unlisted upload visibility is stated in the upload review.
- LinkedIn: default owner is the selected sponsored account. Organization/person owners require `owner_urn` and an exact administrator resource binding for `/rest/organizations/{id}` or `/rest/people/{id}`, plus provider permissions. AMCP does not replace the requested owner. Image PUT uses OAuth; video PUT uses the signed URL without OAuth.

## Permissions and failures

Deployment writes must be enabled; the connector must be operator/admin and the selected connection must grant account writes. This single grant covers campaigns, ad sets, ads, creatives and media equally. `WRITE_ACCOUNT_FORBIDDEN` identifies the chosen connection/account and whether another login has a write grant. Choose that connection explicitly or update the grant in Connections. New connections default to reviewed writes when enabled; existing reader grants are preserved.

Public Drive imports require a downloadable share link. Private files use drive_connection_id and an explicit file selection through Drive OAuth. A Drive login may also select folders: the website lists the downloadable PNG, JPEG, MP4 and MOV files directly inside a selected folder (Drive `files.list` with `'<folder>' in parents`, at most 500), and imports one only after Drive's own metadata names that folder among the file's parents. Subfolders are not opened (select them to use their files). Google Docs exports and permission/quota/confirmation HTML remain unsupported. Advertising credentials/cookies are never sent to Drive; redirects are restricted to approved download hosts. Any other link goes through `source_url` and its public-address rules (see *Without Google Drive*).

**Revoking Drive access does not reach an import (owner decision D23, MED-05).** A file imported from Drive (`origin: 'drive'`, `src-…`) is a frozen copy of the bytes AMCP downloaded, and an owner's retained copy of it (`lib-…`) is too. Disconnecting or disabling the Drive login, removing the file or folder from its selection, or reconnecting it without a download scope neither removes nor blocks such a copy: it can still be pushed until it expires or an owner removes it. New imports, folder lists and `drive_url` reviews still check the selection at every Drive step. The import records the Drive selection it came through by IDs only (`connection_id`, `file_id`, `folder_id`, never names or links), and a retained copy keeps that record. `amcp_media list` reports `drive_access` on such sources: `selected` while the same enabled login can still download that folder or file, `revoked` otherwise; the website marks the latter "Drive access since revoked". To withdraw an imported copy, delete it, or have an owner remove the retained original.

Frozen bytes prevent later Drive edits from changing the reviewed upload. Temporary staging permits two pending reviews or variants per tenant and eight application-wide, each within the configured limit (default 128 MiB); uploads waiting to be pushed have their own space: four times the media limit in bytes per tenant (25 files) and eight times application-wide (50 files). Expired files are removed on the next capacity reservation; submitted uploads delete bytes immediately on success/failure. `amcp_media cancel` discards an unsubmitted review. Receipts and audits remain.

Uploads are never automatically retried. Known allocation IDs and `retry_safe:false` survive partial failure. Lost responses leave durable uncertain claims; inspect provider state before deciding to retry. Resumable Google session state is retained encrypted and restricted to its HTTPS resumable-upload origin. LinkedIn URLs are restricted to its HTTPS upload host/path. Multi-step uploads cannot roll back atomically across providers.

## Durable transfer and eligibility

AMCP_MAX_MEDIA_MB controls the staging bound (32–512 MiB, default 128); a value outside that range is rejected, the 128 MiB default applies, and the reason is written to stderr and reported by `amcp_workspace health` under `configuration_problems` rather than stopping the server; lower provider image/format limits still apply. Files are encrypted in 4 MiB SQLite chunks with a checked manifest. Transfers use bounded memory buffers. Google video uploads use resumable chunks and authoritative offset queries; unknown finalization is never blindly repeated.

Use amcp_media inspect_eligibility with a file (`source_id`, `source_url` or `drive_url`) and square/portrait/vertical/landscape preset to inspect geometry and codec before upload. FFmpeg/ffprobe are required. These are AMCP preset checks, not a certificate of platform acceptance. A preset on prepare requires the frozen source to pass these checks. Eligibility and `variant` judge and turn the file as it is seen (EXIF orientation included, as above). A variant of a JPEG stays JPEG (FFmpeg quality 2), a PNG stays PNG, and a video becomes H.264 MP4 within the same 180-second conversion limit as fit, always within a website upload's deadline (measured above; the production image is still to be measured). A video already at the preset's size as upright H.264 and AAC is copied without re-encoding, and a crop scales only the region it keeps. Its `source_width` and `source_height` are the displayed size.

execute_async queues the confirmed frozen review; job_status exposes durable progress. Reviews still expire if execution does not begin in time. A queued upload that meets transient contention before any claim (`MEDIA_MEMORY_BUSY`, `MEDIA_UPLOAD_BUSY`, `MEDIA_PROCESSOR_BUSY`) is retried by the worker after the server's `retry_after_ms` with jitter, until the review expires; once a claim exists it is never retried. A job that failed before any claim sent nothing: recovery reports it `not_submitted` with `can_execute: true` (never `queued`), job_status says `not_submitted: true`, the website shows "Not sent — try again", and execute_async queues the same review again (audited `media_upload_requeued`). Cancellation prevents unsubmitted work; a provider request already sent can finish. Reuse performs a fresh account-scoped availability check; unsupported lookup paths require a fresh reviewed upload. No LLM file download is necessary.

**Deadline-aware start and the transfer window.** Before the claim, execute estimates the transfer from the platform's request count (Snapchat parts, X and LinkedIn 4 MiB segments, Google video chunks), a per-request budget (`AMCP_MEDIA_STEP_BUDGET_MS`, 5000), a throughput floor (`AMCP_MEDIA_TRANSFER_BYTES_PER_SECOND`, 1 MiB/s) and a margin (`AMCP_MEDIA_DEADLINE_MARGIN_MS`, 15000). A transfer that cannot finish before its deadline is refused with `UPLOAD_DEADLINE_TOO_CLOSE` (`provider_requests_sent: false`): no claim, no allocation. The five-minute review governs confirmation only; at the claim the review gets `transfer_expires_at` (`AMCP_MEDIA_TRANSFER_WINDOW_MINUTES`, 60, 5–180), always capped by a website upload's absolute deadline. Provider steps, retained upload sessions and a qualified resume (Google and LinkedIn video) use that window, so a Drive or link source may resume after the review expired, and a website source never after its thirty minutes. The journal records each completed transfer's duration (`transfer_ms`, no URLs or bytes) to tune the estimate.

## Media capacity

Every prepare, plan, variant, eligibility check, execute, resume, link/Drive import and retention takes a lease in a shared byte budget (MED-02). An operation reserves `AMCP_MEDIA_MEMORY_FACTOR` (6, 2–12) copies of its file's size when AMCP already holds the file (an upload, retained original, variant or frozen review), at least `AMCP_MEDIA_MIN_RESERVATION_MB` (64); a link or Drive file not downloaded yet reserves the worst case (six times the media limit). The budget is `AMCP_MEDIA_MEMORY_MB` (default six times the media limit, 768 MiB for 128), at most `AMCP_MEDIA_OPERATIONS` (8) operations at once and `AMCP_MEDIA_TENANT_OPERATIONS` (4) per workspace. Small operations of different workspaces therefore run together, while two maximum-sized videos still take turns under the default budget. A workspace refused for bytes keeps a waiting place for 20 seconds after each refusal, which later operations of other workspaces must leave free, so a large operation is not starved by small ones. Refusals are `MEDIA_MEMORY_BUSY` (429, retryable, `details.reason`: `bytes`, `operation_slots` or `workspace_share`). The factor and floor are conservative defaults, not measurements: FFmpeg child memory is outside Node's accounting, and per-operation peak RSS on the production image (MED-02 Stage B) and the container memory limit (Q13) are still to be measured before they are lowered. Until then the rollback is `AMCP_MEDIA_OPERATIONS=1` (one media operation at a time, as before) or `AMCP_MEDIA_MIN_RESERVATION_MB=768` (every operation reserves the whole budget), and setting `AMCP_MEDIA_PROCESS_MEMORY_MB` in the deployment bounds each FFmpeg process meanwhile. On Linux, `AMCP_MEDIA_PROCESS_MEMORY_MB` (64–16384) runs each FFmpeg/ffprobe process under `prlimit --as` (`AMCP_PRLIMIT_PATH` overrides the name), so a decoder fails like a conversion error instead of exhausting the container; unset, it runs directly. At most two media processes run per server process (`MEDIA_PROCESSOR_BUSY`, retryable). The owner's `amcp_workspace health` shows the workspace's reserved bytes and operations, the deployment totals, the limits, and this workspace's media refusal, release and transfer counts since the process started.
