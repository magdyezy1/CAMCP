# OAuth compatibility and hardening decisions

## Claude remote MCP

AMCP accepts dynamic registration with `token_endpoint_auth_method=none` or `client_secret_post`. The authorization-server metadata advertises both methods. Confidential registrations receive a fresh 256-bit random client secret, returned in the no-store registration response and stored with AES-256-GCM encryption bound to the client ID and workspace. Keep `MIRROR_MASTER_KEY` stable across deploys and back it up separately. Client secrets are non-expiring (`client_secret_expires_at=0`); access and refresh tokens retain their existing expiry and revocation behavior.

Both client types require S256 PKCE. Exact HTTPS redirect matching, the limited loopback-port exception, resource validation, scope restrictions, member consent capped by role, CSRF checks, one-use codes, refresh rotation with a bounded reuse window, and replay-family revocation remain enforced. Confidential token exchange, refresh and revocation require the registered secret. Public clients cannot inject a client secret. Basic and other unadvertised authentication methods are rejected. Authentication checks use constant-time secret comparison and retain a pre-authentication rate limit.

The HTTP test uses Claude's actual callback shape, `https://claude.ai/api/mcp/auth_callback`, and exercises registration through authenticated MCP tool access. It also covers invalid secrets, redirect/PKCE/resource/scope failures, encrypted persistence after restart and refresh replay. This is a protocol integration test with synthetic credentials; a real Claude-account round trip remains an external acceptance check after deployment. Dynamic registration behavior follows [RFC 7591](https://www.rfc-editor.org/rfc/rfc7591).

## Reviewer suggestions

| Suggestion | Decision and implementation |
| --- | --- |
| Trusted reverse proxies | Implemented as opt-in `AMCP_TRUSTED_PROXY_CIDRS`, used for website login and OAuth authentication rate-limit attribution. Default remains socket-only. Walk right to left and stop at the nearest untrusted hop; reject malformed or excessive chains. IPv4, IPv6 and mapped IPv4 are normalized. No blanket `trust proxy=true` setting. |
| Client addresses behind Cloudflare and Railway (SEC-01, review 2026-10-08) | Railway publishes no proxy range, so the CIDR walk could not separate clients there: every limit key collapsed to Railway's or Cloudflare's address. `AMCP_CLIENT_IP_SOURCE` now selects `socket`, `xff-cidrs` (the CIDR walk above), `railway` (the single address in `X-Real-IP`) or `railway+cloudflare` (as `railway`, then the single address in `CF-Connecting-IP` only when `X-Real-IP` is inside Cloudflare's published ranges, so direct traffic cannot forge it). Unset keeps the earlier behavior; an unknown value stops start-up; a bad header falls back to the socket. The ranges are a committed snapshot checked offline (`npm run generate:cloudflare:check`) and refreshed at release with `node tools/cloudflare-ranges.mjs --refresh`. The deployment owner's health shows the key source, header presence and the distinct key count of the last hour, never an address. Owner decision D5: `railway+cloudflare` on Railway. Tests: `tests/client-address-profiles.test.mjs`. |
| `/token` counts failures only (SEC-01, review 2026-10-08) | Every `/token` and `/revoke` POST used to count toward 50 per address per 15 minutes before the client was authenticated, so about 50 successful refreshes from one address refused every connector behind it. The client is now authenticated first; only failed client authentication and refused grants (any other 4xx answer) count, and the SDK's own token and revocation limiters skip successful answers. Brute-force protection is unchanged: the 51st failure from one address gets `429 too_many_requests` with `Retry-After`. Each connection (client, workspace and the person who approved it) also has its own budget of 30 successful token responses per 15 minutes, a starting value to tune from logs; a metadata-document client ID is shared by everyone who uses that app, so a budget per client ID alone would have been one budget for all of them. |
| Rate-limit attribution (review 2026-09-28) | The MCP SDK's own limiters on `/authorize`, `/token`, `/register` and `/revoke` were keyed on `req.ip`, which is the proxy's address because Express proxy trust is off, so one anonymous caller could exhaust them for every client. They now use the same resolved client address as every AMCP limit. IPv6 clients share one key per /64. Successful password and two-step sign-ins clear that person's own counter, so a person's own repeated sign-ins do not lock them out; address counters and failures still count. (This did not stop other people's failures from locking a person out; see the SEC-03 row.) Two-step codes are also limited per person (5 per 15 minutes) across all addresses. Tests: `tests/auth-hardening.test.mjs`. |
| Targeted identity lockout (SEC-03, review 2026-10-08) | The per-email counter (10 sign-ins, 5 reset, registration or email-change requests per 15 minutes) was checked before the password for every browser, so anyone who knew an email address could keep that person out indefinitely and stop their reset emails. A completed password, two-step or social sign-in now sets `__Host-amcp_device` (HttpOnly, Secure, SameSite=Lax, 180 days; sha256 of the user ID, a random nonce, the issue time and an HMAC under a key derived from `MIRROR_MASTER_KEY` with HKDF, covering the account version). A sign-in or reset from that browser uses the device's own budget (10 sign-ins per 15 minutes) instead of the email's; another person's cookie, a changed cookie, an expired cookie and every cookie issued before a password or email change are ignored. Address limits always apply, so guessing across identities stays blocked. At the per-email cap, reset, registration and email-change requests answer the same generic message and send nothing. The refusal at the per-email cap names a known browser, a linked social sign-in or a reset. The deployment owner's rate-limit panel counts withheld email requests and refusals to known devices. `AMCP_KNOWN_DEVICES=false` turns the device budget off. The sign-in cap stays 10; the 50-attempt stopgap was not needed. Tests: `tests/known-device-limits.test.mjs`, `tests/auth-hardening.test.mjs`. |
| Recent sign-in across workspaces (review 2026-09-28) | A workspace switch used to stamp a new sign-in time, which let an old session pass the 15-minute recent sign-in check for e-mail, password and two-step changes. The new session keeps the original sign-in time. |
| Client registration cap (review 2026-09-28; corrected 2026-10-08, MCP-03) | Registration is anonymous and was capped at 1,000 clients (replaced by the registration limits below). The 2026-09-28 rule released only clients without any grant row, and pruning keeps each client's newest refresh row, so revoked and abandoned clients stayed counted for good. Each registration now first releases every client registered more than 24 hours ago that has nothing live (no unused, unexpired access, refresh, code or consent request) and whose newest grant expired more than 7 days ago, with its grant rows and expired keys, in one transaction. Live clients and clients inside the grace period are untouched. The owner's health view of the deployment workspace shows the registered count, the headroom and how many the next registration would release. Tests: `tests/mcp-registration-protocol.test.ts`, `tests/claude-oauth.test.ts`. |
| Issuer in authorization responses (review 2026-10-08, MCP-03) | Every authorization response redirected to a client carries `iss`, byte for byte the metadata issuer (`https://<origin>/`): approvals, `access_denied`, and the SDK's own request-error redirects. The metadata advertises `authorization_response_iss_parameter_supported: true` ([RFC 9207](https://www.rfc-editor.org/rfc/rfc9207)). |
| Client ID Metadata Documents (review 2026-10-08, MCP-03 phase 2) | A client may use an HTTPS URL as its `client_id` instead of registering; AMCP fetches the JSON document there and uses it as the registration of a public client, without storing it. The fetch is guarded like the media-link import: HTTPS on port 443 to a host name, every resolved address public and the one connected to, no redirect, 5 seconds, at most 10 KB; the document's `client_id` must equal the URL, its `redirect_uris` must be exact HTTPS or loopback HTTP, its method `none`, and it must not carry a secret. Documents are cached for their `max-age` within 5 minutes and 24 hours, refusals for a minute. Reads are bounded (r25-mf-auth): one read per `client_id` at a time and eight at once overall (a request without a free place is refused like an unreadable document, and not remembered). `/token` and `/revoke` read a document only when the request presents a code, refresh token or token that is a grant of that `client_id`; any other is refused first, as a failed request. A saved document whose re-read gets no answer (DNS, connection, timeout, HTTP 5xx) stays in use up to 24 hours past its lifetime and is retried each minute; any answer AMCP cannot use (3xx, 4xx, too large, invalid, non-public address) replaces it, as before. The consent screen names the host that published the document. The metadata advertises `client_id_metadata_document_supported: true`. `AMCP_MCP_CLIENT_METADATA=off` turns it off; `AMCP_MCP_CLIENT_METADATA_HOSTS` accepts only listed hosts. Registration stays available for older clients. |
| Registration limits (MCP-03 phase 2, with the SEC-01 client address) | The global refusal at 1,000 registered clients let one anonymous caller fill the table for everyone. `/register` now admits at most `AMCP_MCP_REGISTRATIONS_PER_ADDRESS_DAILY` (default 30) new registrations from one client address (IPv6: one /64) and `AMCP_MCP_REGISTRATIONS_DAILY` (default 300) for the deployment within 24 hours, before the SDK registers anything; beyond them it answers 429 `too_many_requests` with `Retry-After` and a sentence naming which limit applied. The address's place is taken before registration and given back when registration fails, and registrations still in flight count against the daily limit, so concurrent requests cannot pass a limit together. Metadata-document clients never register and are not counted. 5,000 registered clients remain as a storage backstop that the daily limit and the release rule keep out of reach. The owner health view of the deployment workspace adds the registrations of the last 24 hours against both limits and an alarm at 80% of the daily limit or of the backstop; the log writes `mcp_registration_limited` and `mcp_registration_alarm` at most once an hour per kind, without addresses. Tests: `tests/mcp-registration-protocol.test.ts`. |
| One connection per person for a shared client ID (wave 1 review, MCP-08 with MCP-03) | A metadata-document client ID is the app vendor's URL, so every person and workspace using that app presents the same `client_id`. A connection is therefore identified by its client and the person who approved it: the authorized-clients panel lists one row per person (administrators see who approved each), an administrator ends one person's connection with `DELETE /api/mcp/authorizations/<client>?owner=<user>` (without `owner` every connection of that client ends), ended connections are listed per person, `mcp_oauth_family_revoked` is audited once per client and person, and the `/mcp` request limiter keys on workspace, client and approving person. Tests: `tests/mcp-authorization-lifecycle.test.ts` (two members of one app), `tests/mcp-request-limits.test.mjs`. |
| Still open (MCP-03) | Manual (ACC-02, runbook and record: [AI-client matrix](acceptance/CLIENT-INTEROP.md)): connect the real Claude.ai connector, Claude Code, ChatGPT, Codex, Cursor and VS Code to a staging deployment with `AMCP_MCP_MODERN_PROTOCOL=next`, record each client's negotiated protocol revision and confirm that removing and re-adding a metadata-document client adds no registration; then set `on`. The SDK's v2 `createMcpHandler` now serves the modern era (see the V2-MCP-13 decision in [DECISIONS](DECISIONS.md)). Deployed: the owner health view shows the registration counts and limits. |
| Bearer challenge (review 2026-10-08, MCP-03) | `WWW-Authenticate` is sent only with 401 and with a 403 that concerns the token, not on every `/mcp` response. It names the protected-resource metadata and a `scope` hint equal to the scope new clients receive (`mcp:read mcp:write` with writes enabled, otherwise `mcp:read`), and adds `error="invalid_token"` when a token was presented. An origin refusal carries no challenge. |
| Registration defaults and readable errors (review 2026-10-08, MCP-03) | A registration that omits `token_endpoint_auth_method` registers a public client and the response says `none`. The SDK put raw schema-validation JSON in `error_description`; every description from `/authorize`, `/register`, `/token` and `/revoke`, including those in error redirects, is now one sentence naming the fields. |
| Browser origins at /mcp (review 2026-10-08, MCP-03) | An origin listed in `AMCP_MCP_ALLOWED_ORIGINS` now gets its CORS preflight answered before authentication (204, its exact `Access-Control-Allow-Origin`, `POST`, the MCP request headers) and its responses carry its origin, so a browser client can read them. Every other origin keeps its 403 and gets no CORS headers. |
| Protocol revision (V2-MCP-13) | The bundled SDK v2 serves initialize-based revisions through 2025-11-25 and the modern revision below. Unsupported revisions get 400, logged at info level as `mcp_protocol_unsupported`. Client information, tokens, metadata `issuer` and callback `iss` retain the same issuer binding. The [SDK foundation record](records/QUALIFICATION-V2-R2-SDK-2026-11-04.md) holds the pins, dependency review and qualification. |
| Protocol 2026-07-28 (MCP-03 phase 3, V2-MCP-13) | The SDK’s native per-request handler serves modern tool, resource and prompt calls; both eras share AMCP’s handlers and authority checks. A revision other than the legacy ones in `MCP-Protocol-Version` or `_meta` selects modern framing; `initialize` selects legacy. Modern requests have no session, carry protocol version and client capabilities in `_meta`, and mirror `Mcp-Method` and the applicable `Mcp-Name` (Base64 sentinel accepted). A mismatch is 400 / `-32020`, an unsupported revision 400 / `-32022`, and an unknown or removed method 404 / `-32601`. Discovery returns revisions, identity, capabilities and instructions; replies carry `resultType: complete` and server identity. Lists and reads are privately cacheable; discovery is public. Unknown guides keep `-32002` on legacy transports and `-32602` on modern ones. A notification is checked for its version and `Mcp-Method` before its 202. Authentication, origin, batch/rate/in-flight limits, cancellation and GET/DELETE 405 are preserved. `AMCP_MCP_MODERN_PROTOCOL` remains `off` by default, `next` serves both eras at `/mcp/next`, and `on` also serves them at `/mcp`; the stdio server reads the same variable (`off` or unset serves the earlier revisions only, `next` and `on` also the modern one). |
| Client conformance (MCP-03 phase 3, owner decision D14) | Synthetic SDK v2 clients shaped like the must-pass clients (Claude.ai and Claude Desktop connector, Claude Code, ChatGPT, Codex, Cursor, VS Code) run on loopback against a synthetic store: discovery through the 401 challenge, registration or a client metadata document, consent, `iss` on the callback, token exchange with the resource indicator, refresh with the issuer-bound refresh token, tool calls in the client's era (dual-era clients stay on 2026-07-28, the others initialize), 401 after revocation in both eras, and a reconnect that adds no registration for metadata-document clients. A custom-scheme redirect (older Cursor builds) is refused with a readable reason. Tests: `tests/mcp-client-conformance.test.ts`. The real clients remain the manual ACC-02 check. |
| Transport headers (review 2026-09-28) | Every response now carries `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Resource-Policy: same-origin`, and `Strict-Transport-Security: max-age=31536000` when an HTTPS public origin is configured (without `includeSubDomains`, so other hosts of the domain are unaffected). CORS requests from web MCP clients are not affected by CORP. |
| Authorization code replay (review 2026-09-28) | A code is single-use, but a second presentation used to be refused without consequence. It now revokes the access and refresh tokens its first exchange issued ([RFC 6749 §4.1.2](https://www.rfc-editor.org/rfc/rfc6749#section-4.1.2)), before PKCE is checked, because whoever replays it holds a code that should never have left the client. Test: `tests/claude-oauth.test.ts`. |
| Grant table growth (review 2026-09-28) | Every refresh left an expired access grant, its key and a rotated refresh grant behind for good. Issuing tokens now removes expired access grants with their keys and expired refresh grants already rotated away. Each client keeps its newest refresh grant while it may still be used; once nothing of the client is live past the grace period, registration releases the client with its grant rows (see the registration cap row). |
| Refresh reuse window (review 2026-10-08, MCP-08, owner decision D16) | Strict rotation ended the whole connection when one client sent two refreshes at once or retried after a lost response. Each rotation now records when and by which refresh grant it was replaced. The same client presenting the just-rotated token again within `AMCP_MCP_REFRESH_REUSE_SECONDS` (default 60, 0–60), while its direct successor is still unused, gets a fresh pair in the same family; the unused successor and its access token stop working, and the superseded successor gets the same window, so a client that kept the other answer recovers by refreshing promptly. Reuse after the window, reuse of an older token, or reuse after the successor was used still ends the family. Refresh cannot add scope on either path. Each reuse is audited as `mcp_oauth_refresh_reused` (client, age). A thief inside the window avoids revocation once, bounded by the window and the successor-unused rule. Tests: `tests/mcp-authorization-lifecycle.test.ts`, `tests/claude-oauth.test.ts`. |
| Revocation audit (review 2026-10-08, MCP-08) | Approvals and denials record the client ID, its name (at most 120 characters, provided by the client and not verified), the return host, the requested and granted scope and the approving person. Every connection AMCP ends records one `mcp_oauth_family_revoked` row per client with its reason: `refresh_replay`, `code_replay`, `client_revoke` (RFC 7009), `membership_change`, `password_change`, `email_change`, `mfa_change`, `account_access_revoked`, `owner_migration` or `door_password_change`; a revocation on the connector page keeps its `mcp_oauth_revoked` row, now with `reason: workspace_revoke`. Ended grant rows keep the reason, so the token endpoint says why a refresh failed instead of "replay detected", and the connector page lists connections ended in the last 14 days with their reason. No token or token hash is written to audit. |
| One token validation path (review 2026-10-08, SEC-05) | `/mcp` used to read only a bearer token's API-key row, so an AI client's ended grant, the door password its access was approved under and the resource it was issued for were never checked there, and every revocation path had to revoke the key as well. `/mcp` and the SDK's `verifyAccessToken` now share one validator (`validateMcpToken`): the API-key row and the person's account and membership as before, and for an AI-client token its live access grant: not ended or superseded, unexpired, the same client, workspace, role and person, issued for this `/mcp` resource, and door-approved access only while the door keeps its password. The grant check is bound to the request's actor, so a revocation during a long request ends it at the next check. AI-client tokens are refused where the website (the authorization server) is not configured; API keys keep working. `tools/list` now checks the credential like every other handler, and `UNAUTHORIZED` carries category `auth`, owner `user` and a reconnect remedy instead of "correct the argument". Tests: `tests/mcp-token-validation.test.ts` covers owner revoke, RFC 7009, family revoke, membership change, password change, connector revoke and door rotation. |
| Member consent capped by role (review 2026-10-08, MCP-08, owner decision D16) | Any active workspace member may authorize an AI client or create a connector token for themselves; reviewer test accounts may too, in their test workspace, until the reviewer password changes. The granted scope is the requested scope intersected with the member's cap: a viewer receives `mcp:read` even when write was requested (the token response's `scope` says so), an operator, administrator or owner may also approve `mcp:write`. One exception (owner decision of 2026-11-21): an owner of the deployment's workspace may approve owner-level access, which the grant carries as `ownerAccess` (its keys have the administrator role) and which ends with their ownership; see [second owner](operations/SECOND-OWNER.md#ai-clients-and-connector-tokens). Per-account write grants, spending policy, write pauses and reviews still apply to every write. Tokens carry the person, so a membership change or demotion ends them. |
| Consent choice (review 2026-10-08, MCP-08) | The consent screen names the workspace, shows the return host in large type with a warning for loopback addresses, says the client name is not verified, and offers "read only" or "read and reviewed changes" within what the client asked for and the member's role allows; write stays preselected where offered (owner decision 2026-09-28). `POST /api/mcp/consent` accepts `scope` and refuses any value outside those choices. |
| Client limit (review 2026-10-08, SEC-08, owner direction P1) | The consent screen also offers **Limit to client**: the client access sets of the workspace, or none for the whole workspace. A member limited to a set can approve only that set. `POST /api/mcp/consent` accepts `access_set_id`; the code, every access token and every refresh carry it, `/mcp` checks it on each request like the scope, and an AI client limited to a set reaches only that set's accounts (`ACCOUNT_SCOPE_RESTRICTED` otherwise). The approval audit and the authorizations list name the set. See [clients in one workspace](USER-ACCOUNTS.md#clients-in-one-workspace-working-client-and-client-access-sets). |
| Account enumeration by timing (review 2026-09-28) | Password reset sends only for an existing account and registration only for a new address, and both used to wait for the email provider, so response time showed which case applied. Delivery now starts without the response waiting; the worker retries what stays queued. Test: `tests/user-accounts.test.ts`. |
| Challenge capacity (review 2026-09-28) | All single-use challenges shared one 10,000 cap, which anonymous social sign-in starts could fill, blocking resets, invitations and two-step sign-in for everyone. Each kind now has its own cap. |
| Reviewer sessions (review 2026-09-28) | Everyone signed in with the reviewer password shares one subject, so the session list showed, and let one reviewer end, other reviewers' sessions. A reviewer now sees and ends only their own session. |
| Idle sessions and security notices (owner decision 2026-09-28) | A website session ends after 2 hours without a request, inside the 8-hour limit; activity is recorded at most every five minutes, and sessions from before the rule start counting at their next request. Password, email, two-step and sign-in-method changes, and each recovery code used, email a notice at an address the change does not control (an email change notifies the previous address). Tests: `tests/user-accounts.test.ts`. |
| Nested SQLite transactions | Implemented depth-based savepoints. Caught inner failures roll back only their work; an outer failure rolls back released inner work too. Callbacks must be synchronous. |
| TikTok refresh rotation | Not added to the current advertiser flow. TikTok documents `/oauth2/access_token/` as long-term and deprecates `/oauth2/refresh_token/`. Its short-term TikTok-account flow uses separate `tt_user` endpoints. Applying that refresh mechanism to advertiser tokens would be incorrect. Revoked/unsupported expired advertiser credentials require reauthorization. |
| Meta long-lived tokens | Implemented after initial code redemption using `fb_exchange_token`. The returned token and actual provider expiry are retained; the server does not invent a 60-day lifetime. Invalid exchange results fail explicitly. A separately documented incompatible token type can opt out with `AMCP_META_LONG_LIVED_TOKEN=false`. |
| Hardcoded script paths | The Windows runtime launcher already uses `$PSScriptRoot`. Removed the fixed workstation root from the publication helper and replaced bootstrap's fixed specification path with a CLI argument or `AMCP_SPEC_FILE`. Publication was not executed as part of this change. |

On Railway, use `AMCP_CLIENT_IP_SOURCE=railway+cloudflare` (or `railway` without Cloudflare proxying) instead of CIDRs; see [client addresses for rate limits](DEPLOY-RAILWAY.md#client-addresses-for-rate-limits). For `xff-cidrs`, proxy operators must verify that trusted ingress servers overwrite or correctly append forwarding headers, and must limit CIDRs to actual trusted peers. The algorithm follows the trust-chain principle in [Express's proxy guidance](https://expressjs.com/en/guide/behind-proxies/). Do not blindly trust private address space, arbitrary hop counts, or all sources. Global Express host/protocol trust remains disabled.

## Validation boundary

Run `npm run check`. Tests cover local protocol and database behavior with synthetic upstream responses. They do not establish approved provider applications, working production credentials, a completed live OAuth round trip, or the unresolved deployment volume attachment. No advertising objects were changed by these tests.

## Selected website refusal diagnostics — 5 October 2026

The common non-MCP HTTP error handler adds meta.requestId and an optional matching six-field
http_refused/http_failed event. Its new log omits URL/query, headers, cookies, credentials, body,
identity, message and stack. An unavailable sink does not prevent the original refusal response.
server/http.ts already writes configured events to stdout/stderr; deployment retention is separate.
The original MCP JSON-RPC branch and MCP finish log remain byte-identical. These local contracts
do not establish live OAuth-provider acceptance or privacy of every other existing log. See
[website diagnostic evidence](records/DELIVERY-2026-10-05-WEBSITE-DIAGNOSTICS.md).
